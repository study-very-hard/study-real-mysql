# 8장. 인덱스
- 인덱스는 쿼리 성능을 언급할 때 빼놓을 수 없는 부분
- MySQL 8.0에서 기능이 많이 개선됐지만, 인덱스에 대한 기본 지식은 여전히 개발자·관리자에게 중요하며 쿼리 튜닝의 기본

# 1. 디스크 읽기 방식

- 데이터베이스 성능 튜닝은 결국 **디스크 I/O를 어떻게 줄이느냐**가 관건인 경우가 많음

## 1.1. HDD와 SSD

- CPU·메모리 같은 전자식 장치에 비해 HDD는 기계식 장치 -> 데이터베이스 서버에서는 항상 디스크가 병목
- SSD: 기존 하드 디스크 드라이브에서 데이터 저장용 원판(플래터)을 제거하고 대신 플래시 메모리 사용 -> 기계적 회전이 없어 빠름
    - 인터페이스(SATA, SAS)는 HDD와 동일
    - 처리 속도: 메모리와 디스크는 10만 배 이상 차이, SSD는 그 사이 (HDD보다 약 1000배 빠름)
- 순차 I/O에서는 SSD가 HDD보다 조금 빠르거나 비슷하지만, **랜덤 I/O에서 SSD가 훨씬 빠름**
    - 데이터베이스 작업은 대부분 작은 데이터를 읽고 쓰는 랜덤 I/O → SSD는 DBMS용 스토리지에 최적
    - 벤치마크: SSD 초당 436 트랜잭션, HDD 초당 60 트랜잭션

## 1.2. 랜덤 I/O와 순차 I/O

- 랜덤 I/O: 디스크 헤더를 데이터 위치로 이동시킨 뒤 읽음 (순차 I/O도 과정은 같음)
- 예) 3개의 페이지(3 × 16KB)를 기록할 때
    - 순차 I/O: 시스템 콜 1번, 디스크 헤더 1번 이동
    - 랜덤 I/O: 시스템 콜 3번, 디스크 헤더 3번 이동 → 순차 I/O보다 약 3배 느림
- 디스크 성능은 **헤더 위치 이동 없이 얼마나 많은 데이터를 한 번에 기록하느냐**로 결정됨
    - 그래서 MySQL에는 그룹 커밋, 바이너리 로그 버퍼, InnoDB 로그 버퍼 같은 기능이 있음
- SSD에서도 랜덤 I/O는 순차 I/O보다 처리량이 떨어짐
- 쿼리 튜닝으로 랜덤 I/O를 순차 I/O로 바꿀 방법은 많지 않음
    - **쿼리 튜닝 = 랜덤 I/O 자체를 줄이는 것** = 꼭 필요한 데이터만 읽도록 개선

> 참고
> - 인덱스 레인지 스캔은 주로 랜덤 I/O, 풀 테이블 스캔은 순차 I/O를 사용
> - 큰 테이블의 레코드 대부분을 읽는 작업(데이터 웨어하우스, 통계)에서는 인덱스 대신 풀 테이블 스캔을 유도하기도 함

# 2. 인덱스란?

- 책의 "찾아보기(색인)"에 비유
    - 찾아보기 = 인덱스, 책 내용 = 데이터 파일, 페이지 번호 = 레코드 주소
- 칼럼 값과 레코드 주소를 키-값(key-value) 쌍으로 만들어 **정렬된 상태로 보관**
- 자료구조 비유
    - 인덱스 = **SortedList**: 저장 시 항상 정렬 → 저장(INSERT, UPDATE, DELETE)은 느리지만 검색(SELECT)은 빠름
    - 데이터 파일 = **ArrayList**: 저장된 순서대로 별도 정렬 없이 보관
- **인덱스는 저장 성능을 희생하고 읽기 속도를 높이는 기능**
    - WHERE 조건절 칼럼이라고 전부 인덱스로 만들면 저장 성능이 떨어지고 인덱스 크기가 커져 역효과

## 2.1. 인덱스 분류

- 역할별
    - 프라이머리 키(Primary key): 레코드를 대표하는 칼럼(조합)으로 만든 인덱스. 식별자 역할, NULL·중복 불허
    - 세컨더리 인덱스(Secondary index): 프라이머리 키를 제외한 나머지 모든 인덱스 (유니크 인덱스는 대체 키로 분류하기도 함)
- 데이터 저장 방식(알고리즘)별
    - **B-Tree**: 가장 일반적. 칼럼 값을 변형하지 않고 원래 값으로 인덱싱. R-Tree도 B-Tree의 응용
    - **Hash**: 칼럼 값으로 해시값을 계산해 인덱싱. 매우 빠르지만 값을 변형하므로 전방 일치(Prefix) 검색·범위 검색 불가. 주로 메모리 기반 DB에서 사용
    - 그 외 Fractal-Tree, 로그 기반 Merge-Tree 등
- 데이터 중복 허용 여부별
    - 유니크(Unique) / 유니크하지 않은(Non-Unique)
    - 유니크 인덱스에 동등 조건(=)으로 검색하면 항상 1건 → 옵티마이저가 더 찾지 않아도 된다는 것을 알 수 있음
- 기능별: 전문 검색용 인덱스, 공간 검색용 인덱스 등

# 3. B-Tree 인덱스

- 가장 먼저 도입됐고 가장 범용적인 인덱스 알고리즘
- DBMS에서는 주로 B+-Tree 또는 B*-Tree 사용
- B-Tree의 "B"는 Binary가 아니라 **Balanced**
- 칼럼의 원래 값을 변형하지 않고 항상 정렬된 상태로 유지

## 3.1. 구조 및 특성

- 루트 노드(Root node) – 브랜치 노드(Branch node) – 리프 노드(Leaf node)
- 리프 노드는 항상 실제 데이터 레코드를 찾아가기 위한 주솟값을 가짐
- 인덱스 키 값은 모두 정렬돼 있지만, **데이터 파일의 레코드는 정렬돼 있지 않고 임의의 순서**로 저장
    - INSERT 순서대로 저장되는 것도 아님 (삭제로 생긴 빈 공간을 재활용하기 때문)

> 참고
> - InnoDB 테이블은 레코드가 클러스터링되어 디스크에 저장되므로 기본적으로 프라이머리 키 순서로 정렬되어 저장됨

- 리프 노드가 가리키는 레코드 주소
    - **MyISAM**: 물리적인 주소 (ROWID, 데이터 파일 내 위치 오프셋)
    - **InnoDB**: **프라이머리 키** 값 (논리적인 주소)
- InnoDB는 세컨더리 인덱스 검색 후 레코드를 읽으려면 **프라이머리 키 인덱스를 한 번 더 검색**해야 함
    - 성능이 떨어져 보이지만 각각 장단점이 있음 → 8.8절 클러스터링 인덱스 참고

## 3.2. B-Tree 인덱스 키 추가 및 삭제

### 3.2.1. 인덱스 키 추가

- 저장될 키 값으로 B-Tree상 적절한 위치를 검색해 리프 노드에 키 값과 레코드 주소 저장
- 리프 노드가 꽉 차면 **분리(Split)** 필요 → 상위 브랜치 노드까지 영향 → 쓰기 비용이 큼
- 비용 대략 계산법: 테이블에 레코드 추가 비용을 1이라 하면 인덱스 1개당 1.5 정도
    - 인덱스 3개 → 1.5 × 3 + 1 = 5.5
    - 이 비용 대부분은 메모리·CPU가 아니라 **디스크에서 인덱스 페이지를 읽고 쓰는 시간**
- MyISAM, MEMORY: INSERT 즉시 인덱스 변경
- InnoDB: 필요하면 인덱스 키 추가를 지연시켜 나중에 처리 가능 (체인지 버퍼)
    - 단, **프라이머리 키나 유니크 인덱스는 중복 체크가 필요해 즉시 반영**

### 3.2.2. 인덱스 키 삭제

- 해당 키 값이 있는 리프 노드를 찾아 **삭제 마크**만 하면 완료
- 마킹도 디스크 쓰기 → 디스크 I/O 필요
- MySQL 5.5 이상의 InnoDB는 이 작업도 버퍼링되어 지연 처리 가능

### 3.2.3. 인덱스 키 변경

- 키 값에 따라 리프 노드 위치가 결정되므로 단순히 키 값만 바꿀 수 없음
- **기존 키 값 삭제 후 새 키 값 추가**로 처리
- InnoDB는 이 작업 모두 체인지 버퍼로 지연 처리 가능

### 3.2.4. 인덱스 키 검색

- 루트 → 브랜치 → 리프 노드로 이동하며 비교 = **트리 탐색**
- SELECT뿐 아니라 UPDATE, DELETE 처리 시 레코드를 먼저 검색할 때도 사용
- 사용 가능한 경우: 100% 일치, 값의 앞부분(Left-most part) 일치, 부등호 비교
- 사용 불가능한 경우
    - 키 값의 뒷부분만 검색
    - **키 값에 변형이 가해진 후 비교** (함수나 연산 수행 결과로 정렬·검색)
- InnoDB에서 인덱스는 더 특별한 의미
    - 레코드 잠금, 넥스트 키 락(갭 락)이 **인덱스를 잠그는 방식**으로 구현
    - UPDATE, DELETE 시 적절한 인덱스가 없으면 불필요하게 많은 레코드를 잠금 (최악은 테이블 전체)

## 3.3. B-Tree 인덱스 사용에 영향을 미치는 요소

- 인덱스 칼럼의 크기, 레코드 건수, 유니크한 인덱스 키 값의 개수 등

### 3.3.1. 인덱스 키 값의 크기

- **페이지(Page) / 블록(Block)**: 디스크 읽기·쓰기의 최소 단위, 버퍼 풀 버퍼링 단위. 인덱스도 페이지 단위로 관리
- DBMS의 B-Tree는 자식 노드 개수가 가변적 → 인덱스 페이지 크기와 키 값 크기로 결정
- 키 값이 커지면 인덱스 크기가 커지고, 버퍼 풀에 캐시할 수 있는 레코드 수가 줄어 메모리 효율이 떨어짐

### 3.3.2. B-Tree 깊이

- 직접 제어할 방법은 없음
- 깊이 3일 때 담을 수 있는 키 값 수
    - 키 16바이트: 약 2억 개 (585 × 585 × 585)
    - 키 32바이트: 약 5천만 개 (372 × 372 × 372)
- 깊이는 값을 검색할 때 몇 번 랜덤하게 디스크를 읽어야 하는지와 직결
- 결론: **인덱스 키 값은 가능하면 작게** 만드는 것이 좋음
    - 실제로는 대용량 DB라도 깊이가 5단계 이상 깊어지는 경우는 흔치 않음

### 3.3.3. 선택도(기수성)

- 인덱스에서 선택도(Selectivity) 또는 기수성(Cardinality)은 거의 같은 의미로 사용: 전체 인덱스 키 값 중 유니크한 값의 수
    - 선택도: 이 칼럼 값으로 검색하면 레코드를 얼마나 잘 골라낼(선택할) 수 있는가
    - 예) 전체 100개 중 유니크한 값 10개 → 기수성 10
- 선택도가 높을수록 검색 대상이 줄어 빠르게 처리

## 3.4. B-Tree 인덱스를 통한 데이터 읽기

### 3.4.1. 인덱스 레인지 스캔

- 가장 대표적인 접근 방식. 검색할 인덱스 범위가 결정됐을 때 사용
    ```sql
    SELECT * FROM employees WHERE first_name BETWEEN 'Ebbe' AND 'Gad';
    ```
- 루트 → 브랜치 → 리프 노드로 시작 지점을 찾고, 거기서부터 리프 노드를 차례대로 읽음 (= 스캔)
    - 리프 노드 끝까지 읽으면 리프 노드 간 링크로 다음 리프 노드로 이동
- 어떤 방식으로 스캔하든 **인덱스 칼럼의 정순/역순으로 정렬된 상태**로 레코드를 가져옴 (별도 정렬 과정 없음)
- 리프 노드에서 찾은 레코드 주소로 데이터 파일의 레코드를 읽을 때 **레코드 1건마다 랜덤 I/O 발생**
    - 그래서 인덱스로 읽을 레코드가 20~25%를 넘으면 테이블 직접 읽기가 더 효율적

### 3.4.2. 인덱스 풀 스캔

- 인덱스를 처음부터 끝까지 모두 읽는 방식
- 쿼리 조건절에 사용된 칼럼이 인덱스의 첫 번째 칼럼이 아닐 때 사용
    - 예) 인덱스 (A, B, C), 조건은 B나 C 칼럼
- 인덱스 크기 < 테이블 크기이므로, **쿼리가 인덱스 칼럼만으로 처리 가능할 때** 테이블 풀 스캔보다 효율적
    - 데이터 레코드까지 읽어야 하면 이 방식으로 처리되지 않음
- 인덱스 레인지 스캔보다는 느리지만 테이블 풀 스캔보다는 효율적


### 3.4.3. 루스(Loose) 인덱스 스캔

- 다른 DBMS의 "인덱스 스킵 스캔"과 비슷. 인덱스 레인지 스캔, 풀 스캔은 반대 의미로 "타이트(Tight) 인덱스 스캔"
- MySQL 5.7까지는 기능이 제한적, 8.0부터 최적화를 조금씩 지원
- 중간에 필요 없는 인덱스 키 값은 무시(SKIP)하고 넘어감
- 주로 GROUP BY 또는 집합 함수 MAX(), MIN() 최적화에 사용

### 3.4.4. 인덱스 스킵 스캔

- 인덱스의 핵심은 값이 정렬돼 있다는 것 → **칼럼 순서가 매우 중요**
    ```sql
    ALTER TABLE employees ADD INDEX ix_gender_birthdate (gender, birth_date);

    -- 인덱스를 사용하지 못하는 쿼리
    SELECT * FROM employees WHERE birth_date>='1965-02-01';
    -- 인덱스를 사용할 수 있는 쿼리
    SELECT * FROM employees WHERE gender='M' AND birth_date>='1965-02-01';
    ```
    - 이전에는 birth_date로 시작하는 인덱스를 새로 생성해야 했음
- MySQL 8.0부터 **선행 칼럼(gender)을 건너뛰고** birth_date 조건만으로 인덱스 검색 가능
    - 루스 인덱스 스캔은 GROUP BY에만 적용 가능했지만, 스킵 스캔은 WHERE 조건절 검색까지 용도 확장

- 단점 (8.0에 새로 도입된 기능이라)
    1. **WHERE 조건에 없는 선행 칼럼의 유니크한 값 개수가 적어야 함**
        - 많으면 시작 지점을 검색하는 작업이 많아져 오히려 느려짐 (예: (emp_no, dept_no) 인덱스면 사원 수만큼 탐색)
    2. **쿼리가 인덱스 칼럼만으로 처리 가능해야 함 (커버링 인덱스)**
        - `SELECT *`로 바꾸면 스킵 스캔을 못 쓰고 풀 테이블 스캔(type=ALL) → 옵티마이저가 개선되면 해결될 부분

## 3.5. 다중 칼럼(Multi-column) 인덱스

- 2개 이상의 칼럼으로 구성된 인덱스 = 복합 칼럼 인덱스 = Concatenated Index
- 루트와 리프 노드는 항상 존재 (레코드 건수가 적으면 브랜치 노드는 없을 수도)
- **두 번째 칼럼은 첫 번째 칼럼에 의존해서 정렬됨**
    - 두 번째 칼럼의 정렬은 첫 번째 칼럼이 같은 레코드에서만 의미가 있음
    - 칼럼이 4개면 세 번째는 두 번째에, 네 번째는 세 번째에 의존
    - 예) emp_no "10003"이 dept_no 순서상 뒤라서 리프 노드 맨 마지막에 위치
- 그래서 다중 칼럼 인덱스는 **칼럼 순서를 신중히 결정**해야 함

## 3.6. B-Tree 인덱스의 정렬 및 스캔 방향

- 인덱스 키 값은 항상 오름차순 또는 내림차순으로 정렬되어 저장
- 오름차순 인덱스라도 거꾸로 읽으면 내림차순처럼 사용 가능 → 읽는 방향은 옵티마이저가 실행 계획으로 결정

### 3.6.1. 인덱스의 정렬

- MySQL 5.7까지는 칼럼 단위로 정렬 순서 혼합(ASC와 DESC 혼합) 불가 → 숫자 칼럼에 -1을 곱한 값을 저장하는 우회 방법 사용
- MySQL 8.0부터 정렬 순서 혼합 인덱스 생성 가능
    ```sql
    CREATE INDEX ix_teamname_userscore ON employees (team_name ASC, user_score DESC);
    ```


#### 인덱스 스캔 방향

```sql
SELECT * FROM employees ORDER BY first_name DESC LIMIT 1;
```
- 인덱스를 처음부터 끝까지 읽는 게 아니라, **역순으로 접근해 첫 번째 레코드만** 읽으면 됨
- 오름차순 인덱스도 정순으로 읽으면 오름차순, 역순으로 읽으면 내림차순
    ```sql
    SELECT * FROM employees WHERE first_name>='Anneke' ORDER BY first_name ASC LIMIT 4;
    SELECT * FROM employees ORDER BY first_name DESC LIMIT 5;
    ```
- ORDER BY나 MIN(), MAX() 최적화가 필요할 때도 옵티마이저는 읽기 방향을 전환해 사용

#### 내림차순 인덱스
- 용어
    - 오름차순 인덱스: 작은 값의 키가 B-Tree 왼쪽
    - 내림차순 인덱스: 큰 값의 키가 B-Tree 왼쪽
    - 인덱스 정순 스캔(Forward index scan): 키 크기와 관계없이 리프 노드 왼쪽 → 오른쪽
    - 인덱스 역순 스캔(Backward index scan): 키 크기와 관계없이 리프 노드 오른쪽 → 왼쪽
- 테스트: 약 1,260만 건 테이블에서 프라이머리 키를 정순/역순으로 풀 스캔
    - `ORDER BY tid ASC LIMIT 12619775,1`: 4.15초
    - `ORDER BY tid DESC LIMIT 12619775,1`: 5.35초
    - **역순 정렬이 28.9% 더 느림**
- 역순 스캔이 느린 이유
    1. **페이지 잠금이 인덱스 정순 스캔에 적합한 구조**
    2. **페이지 내에서 인덱스 레코드가 단방향으로만 연결된 구조** (페이지 간에는 양방향 연결 리스트)

- 선택 기준
    - 일반적으로 ORDER BY ... DESC 쿼리가 소량 레코드에 드물게 실행되면 내림차순 인덱스는 굳이 고려할 필요 없음
    - 예) `SELECT * FROM tab WHERE userid=? ORDER BY score DESC LIMIT 10;` → (userid ASC, score ASC)와 (userid DESC, score DESC) 모두 적절
    - 많은 레코드를 조회하며 빈번하게 실행되면 **내림차순 인덱스가 더 효율적**
    - 많은 쿼리가 인덱스 한쪽만 집중적으로 읽어 특정 페이지 잠금이 병목이 될 것 같으면, 자주 쓰는 정렬 순서대로 인덱스를 생성하면 완화에 도움

## 3.7. B-Tree 인덱스의 가용성과 효율성

### 3.7.2. 인덱스의 가용성

- B-Tree는 **왼쪽 값 기준(Left-most)으로 오른쪽 값이 정렬**됨
    - 하나의 칼럼 내에서뿐 아니라 다중 칼럼 인덱스의 칼럼에도 적용
- 값의 왼쪽 부분이 없으면 인덱스 레인지 스캔 불가
    ```sql
    -- INDEX (first_name)
    SELECT * FROM employees WHERE first_name LIKE '%mer';
    ```
    - 왼쪽부터 비교해야 하는데 상수값의 왼쪽 부분이 고정되지 않음 → 레인지 스캔 불가
- 다중 칼럼 인덱스도 왼쪽 칼럼 값을 모르면 레인지 스캔 불가
    ```sql
    -- INDEX (dept_no, emp_no)
    SELECT * FROM dept_emp WHERE emp_no>=10144;
    ```
    - 선행 칼럼 dept_no 조건 없이 emp_no만으로는 인덱스를 효율적으로 사용 불가
- 이 규칙은 GROUP BY, ORDER BY에도 똑같이 적용

# 4. R-Tree 인덱스

- 공간 인덱스(Spatial Index): R-Tree 알고리즘으로 **2차원 데이터**를 인덱싱, 검색
- 내부 메커니즘은 B-Tree와 흡사. B-Tree는 1차원 스칼라 값, R-Tree는 2차원 공간 개념 값
- MySQL 공간 확장(Spatial Extension)의 세 가지 기능
    - 공간 데이터를 저장할 수 있는 데이터 타입
    - 공간 데이터 검색을 위한 공간 인덱스(R-Tree)
    - 공간 데이터 연산 함수 (거리 또는 포함 관계 처리)
- 자세한 내용은 12.2절 '공간 검색'

## 4.1. 구조 및 특성

- 데이터 타입: POINT, LINE, POLYGON, GEOMETRY (GEOMETRY는 나머지 3개의 슈퍼 타입)
- **MBR(Minimum Bounding Rectangle)**: 도형을 감싸는 최소 크기의 사각형
    - 이 사각형들의 포함 관계를 B-Tree 형태로 구현한 인덱스 = R-Tree
- MBR 레벨 예시
    - 최상위 레벨(R1, R2) → R-Tree 루트 노드
    - 차상위 레벨(R3~R6) → 브랜치 노드 (중간 크기 MBR, 도형 객체의 그룹)
    - 최하위 레벨(R7~R14) → 리프 노드 (각 도형 데이터의 MBR)

## 4.2. R-Tree 인덱스의 용도

- Rectangle의 'R' + B-Tree의 'Tree'
- 주로 WGS84(GPS) 기준 위도·경도 좌표 저장에 사용, CAD/CAM이나 회로 디자인 등 좌표 시스템 기반 정보에도 적용
- 반경 5km 검색 방법
    - 반경 5km 원을 포함하는 최소 사각형(MBR)으로 포함 관계 비교
    - 사각형 모서리 쪽 점(P6처럼 5km 밖이지만 사각형 안)도 포함됨

# 5. 전문 검색 인덱스

- B-Tree는 칼럼 값을 1,000바이트(MyISAM) / 3072바이트(InnoDB)까지 잘라서 키로 사용, 전체 일치·좌측 일부 일치 검색만 가능
- 문서 내용 전체를 인덱싱해 특정 키워드가 포함된 문서를 검색하는 **전문(Full Text) 검색**에는 B-Tree 사용 불가
- MySQL 8.0은 InnoDB 중심으로 설명

## 5.1. 인덱스 알고리즘

- 키워드 분석 및 인덱스 구축 방식에 따라 **어근 분석**과 **n-gram 분석**으로 구분
- 구분자(Stopword) 방식은 8.0부터 어근 분석과 n-gram에 포함

### 5.1.1. 어근 분석 알고리즘

- 두 가지 과정으로 색인
    - **불용어(Stop Word) 처리**: 가치 없는 단어를 필터링해 제거. MySQL은 소스코드에 정의돼 있지만 사용자가 별도로 정의 가능
    - **어근 분석(Stemming)**: 검색어로 선정된 단어의 뿌리인 원형을 찾는 작업
- MySQL은 오픈소스 형태소 분석 라이브러리 **MeCab**을 플러그인으로 사용 가능
    - 한글·일본어는 어근 분석보다 형태소 분석으로 명사와 조사를 구분하는 기능이 더 중요
    - MeCab은 일본어용이지만 한국어가 일본어와 비슷해 한글 분석 가능
    - 서구권 언어는 Snowball(MongoDB에서 사용)
- MeCab을 제대로 쓰려면 단어 사전, 문장 구조 인식 학습 등이 필요 → 한글에 맞게 완성도를 갖추는 데 많은 시간과 노력 필요

### 5.1.2. n-gram 알고리즘

- 형태소 분석이 문장을 이해하는 알고리즘이라면, n-gram은 단순히 키워드를 검색하기 위한 인덱싱 알고리즘
- 본문을 무조건 몇 글자씩 잘라서 인덱싱
    - 알고리즘이 단순하고 언어별 이해·준비 작업이 필요 없음
    - 대신 인덱스 크기가 상당히 큼
- n = 인덱싱할 키워드의 최소 글자 수. 일반적으로 **2-gram(Bi-gram)** 사용

## 5.2. 전문 검색 인덱스의 가용성

- 반드시 두 가지 조건을 갖춰야 함
    - 쿼리 문장이 전문 검색을 위한 문법(`MATCH ... AGAINST ...`) 사용
    - 테이블이 전문 검색 대상 칼럼에 대해 전문 검색 인덱스 보유
    ```sql
    CREATE TABLE tb_test (
        doc_id INT,
        doc_body TEXT,
        PRIMARY KEY (doc_id),
        FULLTEXT KEY fx_docbody (doc_body) WITH PARSER ngram
    ) ENGINE=InnoDB;

    -- 결과는 나오지만 풀 테이블 스캔
    SELECT * FROM tb_test WHERE doc_body LIKE '%애플%';

    -- 전문 검색 인덱스 사용
    SELECT * FROM tb_test WHERE MATCH(doc_body) AGAINST('애플' IN BOOLEAN MODE);
    ```
    - 전문 검색 인덱스를 구성하는 칼럼들은 모두 MATCH 절 괄호 안에 명시해야 함

# 6. 함수 기반 인덱스

- 칼럼 값을 변형해서 만든 값에 인덱스를 구축할 때 사용. MySQL 8.0부터 지원
- 구현 방법 두 가지
    - 가상 칼럼을 이용한 인덱스
    - 함수를 이용한 인덱스
- 인덱싱할 값을 계산하는 과정만 다를 뿐, 내부 구조·유지관리 방법은 B-Tree 인덱스와 동일

## 6.1. 가상 칼럼을 이용한 인덱스

```sql
CREATE TABLE user (
    user_id BIGINT,
    first_name VARCHAR(10),
    last_name VARCHAR(10),
    PRIMARY KEY (user_id)
);
```
- first_name + last_name으로 검색해야 할 때
    - 이전 버전: full_name 칼럼을 추가하고 모든 레코드를 업데이트해야 인덱스 생성 가능
    - 8.0: 가상 칼럼을 추가하고 그 칼럼에 인덱스 생성
    ```sql
    ALTER TABLE user
        ADD full_name VARCHAR(30) AS (CONCAT(first_name,' ',last_name)) VIRTUAL,
        ADD INDEX ix_fullname (full_name);

    EXPLAIN SELECT * FROM user WHERE full_name='Matt Lee';
    -- type=ref, key=ix_fullname
    ```
- VIRTUAL, STORED 어떤 옵션이든 인덱스 생성 가능
- 단점: 테이블에 새 칼럼을 추가하는 것과 같아 **테이블 구조가 변경됨**
- VIRTUAL과 STORED의 차이는 15.8절 '가상 칼럼(파생 칼럼)'

## 6.2. 함수를 이용한 인덱스

- MySQL 5.7에서도 가상 칼럼은 가능했지만, 함수를 직접 인덱스 생성 구문에 쓸 수는 없었음
- 8.0부터 **테이블 구조를 변경하지 않고** 함수를 직접 사용하는 인덱스 생성 가능
    ```sql
    CREATE TABLE user (
        user_id BIGINT,
        first_name VARCHAR(10),
        last_name VARCHAR(10),
        PRIMARY KEY (user_id),
        INDEX ix_fullname ((CONCAT(first_name,' ',last_name)))
    );

    EXPLAIN SELECT * FROM user WHERE CONCAT(first_name,' ',last_name)='Matt Lee';
    -- type=ref, key=ix_fullname
    ```
- **조건절에 함수 기반 인덱스에 명시된 표현식이 그대로 사용돼야 함**
    - 표현식이 다르면 (결과가 같더라도) 옵티마이저가 다른 표현식으로 간주해 인덱스 사용 불가
- 위 예제에서 인덱스를 못 쓰면 CONCAT의 공백 문자 리터럴 때문일 가능성이 높음
    - `collation_connection`, `collation_database`, `collation_server` 값을 동일 콜레이션(예: utf8mb4_0900_ai_ci)으로 일치시킨 후 다시 테스트

# 7. 멀티 밸류 인덱스

- 전문 검색 인덱스를 제외한 모든 인덱스는 레코드 1건 = 인덱스 키 값 1개 (1:1)
- **멀티 밸류(Multi-Value) 인덱스**: 하나의 레코드가 여러 개의 키 값을 가질 수 있음
    - 정규화에 위배되지만, JSON 배열 타입 필드의 원소들에 대한 인덱스 요구 때문에 등장
- MongoDB는 처음부터 지원, MySQL은 8.0부터 지원하면서 JSON 관리 기능이 MongoDB에 비해 부족함이 없어짐
    ```sql
    CREATE TABLE user (
        user_id BIGINT AUTO_INCREMENT PRIMARY KEY,
        first_name VARCHAR(10),
        last_name VARCHAR(10),
        credit_info JSON,
        INDEX mx_creditscores ( (CAST(credit_info->'$.credit_scores' AS UNSIGNED ARRAY)) )
    );

    INSERT INTO user VALUES (1, 'Matt', 'Lee', '{"credit_scores":[360, 353, 351]}');
    ```
- 일반적인 조건 방식이 아니라 **반드시 다음 함수를 이용해 검색**해야 옵티마이저가 인덱스를 사용
    - `MEMBER OF()`
    - `JSON_CONTAINS()`
    - `JSON_OVERLAPS()`
    ```sql
    SELECT * FROM user WHERE 360 MEMBER OF(credit_info->'$.credit_scores');
    -- EXPLAIN: type=ref, key=mx_creditscores
    ```

# 8. 클러스터링 인덱스

- 클러스터링 = 여러 개를 하나로 묶음
- MySQL의 클러스터링: 테이블 레코드를 **비슷한 것(프라이머리 키 기준)끼리 묶어서 저장**
    - 비슷한 값들을 동시에 조회하는 경우가 많다는 점에 착안
- **InnoDB에서만 지원**

## 8.1. 클러스터링 인덱스

- 프라이머리 키에 대해서만 적용
- **프라이머리 키 값에 의해 레코드의 저장 위치가 결정됨**
    - 프라이머리 키 값이 바뀌면 레코드의 물리적 저장 위치도 바뀜
    - → 프라이머리 키 값에 대한 의존도가 크므로 신중히 결정해야 함
- 인덱스 알고리즘이라기보다 테이블 레코드의 저장 방식
    - "클러스터링 인덱스" = "클러스터링 테이블", 기준이 되는 프라이머리 키 = "클러스터링 키"
- 프라이머리 키 기반 검색은 매우 빠르지만, 레코드 저장이나 프라이머리 키 변경은 상대적으로 느림

- 구조는 일반 B-Tree와 비슷하지만 **리프 노드에 레코드의 모든 칼럼이 저장**됨 → 테이블 자체가 하나의 거대한 인덱스
- 프라이머리 키 변경 예: `UPDATE tb_test SET emp_no=100002 WHERE emp_no=100007;`
    - emp_no 100007 레코드가 3번 페이지에서 2번 페이지로 이동
    - 실제로 프라이머리 키 값을 변경하는 경우는 거의 없음

- 프라이머리 키가 없는 InnoDB 테이블의 클러스터링 키 선택 우선순위
    1. 프라이머리 키가 있으면 프라이머리 키
    2. NOT NULL 옵션의 유니크 인덱스 중 첫 번째 인덱스
    3. 자동으로 유니크한 값을 가지도록 증가되는 칼럼을 내부적으로 추가한 후 선택
- 3번의 자동 추가 칼럼은 사용자에게 노출되지 않고 쿼리에 사용할 수 없음 → 아무 혜택이 없음
- 클러스터링 인덱스는 테이블당 하나만 가질 수 있는 엄청난 혜택 → **가능하면 프라이머리 키를 명시적으로 생성**

## 8.2. 세컨더리 인덱스에 미치는 영향

- MyISAM, MEMORY: 레코드는 INSERT 시 저장된 공간에서 절대 이동하지 않음 (클러스터링을 안함)
    - 프라이머리 키와 세컨더리 인덱스 모두 레코드 주소(ROWID)를 가짐 → 구조적 차이 없음
- InnoDB에서 세컨더리 인덱스가 실제 레코드 주소를 가진다면?
    - 클러스터링 키 값이 변경될 때마다 모든 인덱스에 저장된 주소값을 변경해야 함
    - → 이 오버헤드를 없애기 위해 **InnoDB의 세컨더리 인덱스는 레코드 주소가 아니라 프라이머리 키 값을 저장**

## 8.3. 클러스터링 인덱스의 장점과 단점

- 장점
    - 프라이머리 키로 검색할 때 처리 성능이 매우 빠름 (특히 프라이머리 키 **범위 검색**)
    - 모든 세컨더리 인덱스가 프라이머리 키를 가지고 있어 인덱스만으로 처리 가능한 경우가 많음 (커버링 인덱스, 10장)
- 단점
    - 모든 세컨더리 인덱스가 클러스터링 키를 가지므로 키 값이 크면 전체적으로 인덱스 크기가 커짐
    - 세컨더리 인덱스로 검색할 때 프라이머리 키로 다시 한번 검색해야 하므로 느림
    - INSERT 시 프라이머리 키에 의해 저장 위치가 결정되므로 느림
    - 프라이머리 키 변경 시 DELETE 후 INSERT가 필요해 느림
- 정리: 장점은 **빠른 읽기(SELECT)**, 단점은 **느린 쓰기(INSERT, UPDATE, DELETE)**

# 9. 유니크 인덱스

- 인덱스라기보다 **제약 조건**에 가까움: 같은 값이 2개 이상 저장될 수 없음
- MySQL에서는 인덱스 없이 유니크 제약만 설정할 방법이 없음
- 유니크 인덱스에서 NULL은 특정 값이 아니므로 2개 이상 저장 가능
- 프라이머리 키는 기본적으로 NULL을 허용하지 않는 유니크 속성이 자동 부여
    - MyISAM, MEMORY의 프라이머리 키는 NULL 불허 유니크 인덱스와 같지만, InnoDB 프라이머리 키는 클러스터링 키 역할도 하므로 근본적으로 다름

## 9.1. 유니크 인덱스와 일반 세컨더리 인덱스의 비교

- 인덱스 구조상 아무런 차이가 없음

### 9.1.1. 인덱스 읽기

- "유니크 인덱스는 1건만 읽으면 되지만 일반 세컨더리 인덱스는 한 번 더 읽어야 해서 느리다"는 **사실이 아님**
    - 추가 작업은 디스크 읽기가 아니라 CPU에서 칼럼 값을 비교하는 작업 → 성능상 영향 거의 없음
- 일반 세컨더리 인덱스는 중복 값이 허용되므로 읽어야 할 레코드가 많아서 느린 것이지, 인덱스 자체 특성 때문이 아님
    - 레코드 1건 읽는 데 0.1초, 2건에 0.2초 걸렸다고 후자가 느리다고 할 수 없는 것과 같음
- 하나의 값을 검색할 때 실행 계획이 다르긴 하지만, 읽어야 할 레코드 건수가 같다면 **성능상 차이는 미미**

### 9.1.2. 인덱스 쓰기

- 유니크 인덱스는 키 값을 쓸 때 **중복 체크 과정이 한 단계 더 필요** → 일반 세컨더리 인덱스보다 느림
- 중복 값 체크 시 읽기 잠금, 쓰기 시 쓰기 잠금 → 이 과정에서 **데드락이 아주 빈번하게 발생**
- InnoDB는 인덱스 키 저장·변경을 **체인지 버퍼**로 빠르게 처리하지만, 유니크 인덱스는 반드시 중복 체크를 해야 해서 **버퍼링 불가**
- → 유니크 인덱스는 일반 세컨더리 인덱스보다 변경 작업이 더 느림

## 9.2. 유니크 인덱스 사용 시 주의사항

- 성능이 좋아질 거라 생각하고 불필요하게 유니크 인덱스를 생성하지 않는 것이 좋음
- 같은 칼럼에 유니크 인덱스와 일반 인덱스를 중복 생성하는 경우가 있는데 불필요

- 같은 칼럼에 프라이머리 키와 유니크 인덱스를 동일하게 생성하는 것도 불필요한 중복
- 유니크 인덱스는 쿼리 실행 계획이나 테이블 파티션에도 영향 (10장, 13장)
- 결론: **유일성이 꼭 보장돼야 하는 칼럼에 대해서는 유니크 인덱스를 생성하되, 꼭 필요하지 않다면 일반 세컨더리 인덱스를 고려**

# 10. 외래키

- MySQL에서 외래키는 **InnoDB에서만** 생성 가능
- 외래키 제약이 설정되면 연관 테이블 칼럼에 인덱스까지 자동 생성
- 외래키가 제거되지 않은 상태에서는 자동 생성된 인덱스 삭제 불가
- InnoDB 외래키 관리의 두 가지 특징
    1. **테이블의 변경(쓰기 잠금)이 발생하는 경우에만 잠금 경합(잠금 대기)이 발생**
    2. **외래키와 연관되지 않은 칼럼의 변경은 최대한 잠금 경합을 발생시키지 않음**
