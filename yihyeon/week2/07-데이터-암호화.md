## 1. MySQL 암호화는 무엇을 보호할까?

MySQL의 **TDE(Transparent Data Encryption)**는 디스크에 저장되는 데이터를 암호화하는 기능이다. InnoDB가 디스크에 쓰기 전에 암호화하고 읽은 후 복호화하므로, 애플리케이션은 일반 테이블과 동일하게 조회·수정할 수 있다.

여기서 중요한 구분은 **디스크에 저장된 데이터(Data at Rest)**와 **메모리·네트워크의 데이터**다. TDE를 켜도 SQL 조회 결과나 버퍼 풀의 데이터가 자동으로 숨겨지는 것은 아니다. 네트워크 보호에는 TLS, 특정 민감 정보 보호에는 애플리케이션 암호화나 접근 제어가 별도로 필요하다.

## 2. 키를 두 단계로 나누는 이유

MySQL은 데이터 파일을 암호화하는 **테이블스페이스 키**와 그 키를 보호하는 **마스터 키**를 구분한다.

```text
마스터 키 (Keyring / 키 관리 시스템)
    └─ 테이블스페이스 키를 암호화
           └─ 실제 데이터 페이지를 암호화
```

테이블스페이스 키는 암호화된 형태로 데이터 파일 헤더에 보관되고, 마스터 키는 Keyring을 통해 관리한다. 이 구조 덕분에 마스터 키를 바꿀 때 데이터 파일 전체를 다시 암호화하지 않아도 된다.

```sql
ALTER INSTANCE ROTATE INNODB MASTER KEY;
```

위 명령은 **마스터 키 로테이션**이다. 테이블스페이스 키를 새 마스터 키로 다시 보호하는 작업이지 모든 데이터 페이지를 재암호화하는 작업은 아니다.

## 3. 테이블 암호화 사용 방식

```sql
CREATE TABLE secure_orders (
  id BIGINT PRIMARY KEY,
  order_info VARCHAR(200)
) ENCRYPTION='Y';
```

테이블 생성 시 `ENCRYPTION='Y'`를 지정할 수 있고, `default_table_encryption` 설정으로 기본값을 관리할 수도 있다. 사용 가능한 설정과 Keyring 구성은 MySQL 버전·에디션·배포 환경에 따라 확인해야 한다.

**TDE와 애플리케이션 암호화의 차이**는 다음과 같다.

| 항목 | TDE | 애플리케이션 암호화 |
|---|---|---|
| 암호화 위치 | InnoDB 디스크 I/O | 애플리케이션 |
| SQL 조회 | 일반 테이블처럼 처리 | 복호화 설계 필요 |
| DB 계정으로 평문 조회 | 가능 | 설계에 따라 제한 가능 |
| 범위 | 저장 매체 보호 | 특정 필드의 노출 범위 통제 |

따라서 TDE는 **디스크 유출 위험을 줄이는 수단**이지, DB 계정 탈취까지 해결하는 기능은 아니다.

## 4. 암호화하면 성능이 얼마나 느려질까?

암호화된 페이지도 메모리의 InnoDB 버퍼 풀에서는 복호화된 상태로 사용한다. 이미 버퍼 풀에 올라온 데이터를 조회할 때마다 암호화를 반복하지는 않는다.

반면 디스크에서 새 페이지를 읽거나 변경된 페이지를 기록할 때 암호화·복호화 비용이 발생한다. CPU의 AES 가속 지원, 버퍼 풀 적중률, I/O 패턴에 따라 영향이 달라지므로 **일률적인 성능 저하율을 적용하면 안 된다.**

압축과 암호화를 함께 사용하면 일반적으로 **압축 후 암호화**한다. 암호문은 압축이 잘되지 않기 때문이다.

## 5. 데이터 파일 이외에 놓치기 쉬운 것

테이블을 암호화하더라도 로그나 백업이 자동으로 모두 보호되는 것은 아니다.

- **Undo / Redo 로그:** 테이블 데이터와 별도로 암호화 설정을 확인해야 한다. 기존 로그와 신규 로그의 암호화 상태가 다를 수 있다.
- **바이너리 로그 / 릴레이 로그:** 복제·복구에 쓰이므로 별도의 암호화 및 키 관리가 필요하다.
- **테이블스페이스 이동:** 암호화된 테이블을 다른 서버로 가져갈 때 원본·대상 서버의 키가 다를 수 있어 내보내기·가져오기 절차와 관련 키 파일 관리가 중요하다.
- **백업:** 데이터 파일만 보관하고 키를 잃어버리면 복구하지 못할 수 있다.

바이너리 로그 암호화 키를 변경하는 예시는 다음과 같다.

```sql
ALTER INSTANCE ROTATE BINLOG MASTER KEY;
```

암호화된 바이너리 로그는 파일을 직접 읽는 방식에 제약이 있을 수 있어 MySQL 서버를 통한 접근 방법을 확인해야 한다.

## 6. 운영에서 가장 중요한 것은 키 관리

암호화 알고리즘을 적용하는 것만큼 **키의 보관·백업·접근 권한·로테이션·복구 절차**가 중요하다. 특히 복제 서버는 각자 키를 관리할 수 있으므로 서버마다 키 관리 설정을 점검해야 한다.

키를 안전하게 별도 보관하고, 복구 환경에서 **백업 데이터와 키를 함께 사용해 실제 복원 가능한지** 정기적으로 검증해야 한다.

## 7. 핵심 정리

- TDE는 **디스크 저장 데이터 보호**에 초점을 맞춘다.
- **마스터 키 → 테이블스페이스 키 → 데이터 페이지**의 2단계 키 관리 구조를 사용한다.
- 테이블 암호화와 **Undo/Redo·바이너리 로그 암호화는 별도로 확인**해야 한다.
- TDE를 사용해도 DB에 접근할 권한이 있으면 평문을 조회할 수 있다.
- 암호화 운영의 핵심은 **키 관리와 복구 가능성 검증**이다.
