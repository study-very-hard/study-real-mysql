## 1. 압축을 도입하면 무엇이 달라질까?

데이터 압축의 목표는 **디스크 사용량과 디스크 I/O를 줄이는 것**이다. 하지만 압축·해제에 CPU가 필요하고, 변경이 잦은 데이터에서는 오히려 처리 비용이 커질 수 있다. 따라서 저장 공간이 줄었다는 사실만으로 성능 개선을 판단하면 안 된다.

InnoDB의 기본 페이지 크기는 16KB다. MySQL은 크게 **페이지 압축**과 **테이블 압축** 두 가지 방식을 제공한다.

## 2. 페이지 압축: 파일 시스템에 공간 반환

페이지 압축은 페이지를 디스크에 기록할 때 압축하고, 남는 공간을 **Punch Hole** 기능으로 파일 시스템에 반환한다. 논리적인 파일 크기는 그대로일 수 있지만 실제 점유하는 디스크 블록은 줄어든다.

- 장점: InnoDB의 기본 페이지 구조를 유지하면서 저장 공간을 절약할 수 있다.
- 전제: OS·파일 시스템이 Punch Hole을 지원해야 한다.
- 주의: 희소 파일을 제대로 처리하지 못하는 백업·복사 도구를 쓰면 공간 절약 효과가 사라질 수 있다.

```sql
CREATE TABLE page_compressed (
  id BIGINT PRIMARY KEY
) COMPRESSION='zlib';
```

**기억할 점:** 페이지 압축은 MySQL 설정뿐 아니라 파일 시스템과 백업 도구까지 함께 검토해야 한다.

## 3. 테이블 압축: InnoDB가 압축 페이지 관리

테이블 압축은 `ROW_FORMAT=COMPRESSED`와 `KEY_BLOCK_SIZE`를 사용한다. 압축된 페이지를 InnoDB가 직접 관리하므로 Punch Hole에 의존하지 않는다.

```sql
CREATE TABLE table_compressed (
  id BIGINT PRIMARY KEY,
  content TEXT
) ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8;
```

`KEY_BLOCK_SIZE=8`은 압축 페이지의 목표 크기를 8KB로 설정하는 예시다. 모든 페이지가 반드시 8KB 이하로 쉽게 압축되는 것은 아니다.

**변경 작업의 비용:** 레코드를 수정하면서 압축 페이지에 공간이 부족하면 압축을 다시 수행하거나 페이지를 분할해야 할 수 있다. 특히 갱신이 많은 테이블은 CPU 사용량과 지연이 증가할 수 있다.

## 4. 두 방식은 어떻게 선택할까?

| 비교 항목 | 페이지 압축 | 테이블 압축 |
|---|---|---|
| 공간 절약 방식 | Punch Hole로 블록 반환 | InnoDB 압축 페이지 사용 |
| 파일 시스템 의존성 | 높음 | 상대적으로 낮음 |
| 주요 고려 사항 | 파일 시스템·백업 호환성 | 재압축·페이지 분할 비용 |
| 공통점 | 압축률과 실제 I/O·CPU 비용 측정 필요 | 압축률과 실제 I/O·CPU 비용 측정 필요 |

테이블 압축에서는 버퍼 풀에서 압축 페이지와 압축 해제된 페이지를 함께 관리할 수 있다. 따라서 **디스크 절약량이 곧 메모리 절약량을 의미하지는 않는다.**

## 5. 실무에서는 무엇을 확인할까?

읽기 위주이며 데이터가 잘 압축되는 테이블은 압축의 이점이 클 수 있다. 반면 쓰기·수정이 빈번하거나 압축률이 낮은 데이터는 효과가 제한적일 수 있다.

검증할 지표는 **실제 디스크 점유량, 버퍼 풀 적중률, 디스크 읽기·쓰기, CPU 사용률, 쿼리 지연(p95/p99), 백업·복구 시간**이다. 같은 데이터로 압축 전후 부하 테스트를 하는 것이 가장 확실하다.

## 6. 핵심 정리

- 페이지 압축은 **파일 시스템의 Punch Hole**이 핵심이다.
- 테이블 압축은 **InnoDB가 압축 페이지를 직접 관리**한다.
- 압축은 저장 공간을 줄이지만 **CPU·메모리·쓰기 비용**을 늘릴 수 있다.
- 실제 도입 여부는 압축률이 아니라 **전체 워크로드의 성능과 운영 안정성**으로 결정한다.
