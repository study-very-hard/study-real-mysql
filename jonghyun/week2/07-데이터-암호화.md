# Ch.7 데이터 암호화
- MySQL의 데이터 암호화:
  - MySQL 5.7에서는 데이터 파일(테이블스페이스) 암호화부터 지원
  - MySQL 8.0에서는 리두 로그, 언두 로그, 바이너리 로그까지 암호화 범위가 넓어짐
- 보안 감사에서는 거의 필수로 언급되는 부분
  - 핀테크처럼 중요한 정보를 다루는 서비스는 애플리케이션에서 암호화한 데이터를 DB에서 한 번 더 암호화하는 이중 암호화를 쓰기도 함
  - 애플리케이션 암호화: 보통 민감한 칼럼 단위
  - MySQL 암호화: 보통 테이블 단위
    - MySQL의 TDE 
      - **디스크에 저장된 데이터**를 암호화하는 기능
  - 쿼리를 처리하는 MySQL 내부에서는 암호화 여부를 신경 쓰지 않도록 투명하게 동작
  - 키링 파일/마스터 키를 잃어버리면 암호화된 데이터도 복구할 수 없음. 암호화만 해놓고 키 백업을 안 하면 아무 의미가 없다.

---
## 7.1 MySQL 서버의 데이터 암호화
- MySQL의 암호화는 DB 서버와 디스크 사이의 I/O 레이어에서 수행됨
  - 디스크로 쓸 때 암호화
  - 디스크에서 읽을 때 복호화
  - 버퍼 풀에 적재된 후에는 복호화된 상태로 처리
  - 즉 InnoDB의 I/O 레이어에서 실행된다는 말
- 그래서 사용자의 쿼리나 MySQL 내부 로직은 해당 테이블이 암호화됐는지 구분할 필요가 없음
  - 가져오는 시점에 이미 암복호화가 끝나니, 사용하는 클라는 영향이 없는 것
  - 이런 방식을 TDE(Transparent Data Encryption)라고 함
  - Data at Rest Encryption이라고도 함
    - 메모리에 있는 데이터나 네트워크로 전송 중인 데이터가 아닌, 디스크에 저장된 상태의 데이터를 암호화한다는 의미

### 7.1.1 2단계 키 관리
- MySQL TDE의 암호화 키는 Keyring 플러그인이 관리
- MySQL 8.0에서 제공하는 키링 플러그인:
  - `keyring_file`: 파일 기반
  - `keyring_encrypted_file`: 암호화된 파일 기반
  - `keyring_okv`: KMIP 기반
  - `keyring_aws`: AWS Keyring 사용
- 커뮤니티 에디션에서는 `keyring_file`만 사용 가능하고 나머지는 엔터프라이즈 에디션에서 제공
- TDE에서 사용하는 두 가지 키:
  - 마스터 키(Master Key)
  - 테이블스페이스 키(Tablespace Key / Private Key)
- 동작 방식:
  1. MySQL이 외부 KMS나 키링 파일에서 마스터 키를 가져옴
  2. 암호화 테이블을 만들 때마다 해당 테이블의 테이블스페이스 키를 생성
  3. 테이블스페이스 키를 마스터 키로 암호화해 데이터 파일 헤더에 저장
  4. 실제 데이터 파일은 테이블스페이스 키로 암호화
- 테이블스페이스 키는 테이블이 삭제되기 전까지 변경되지 않음
  - MySQL 외부로 노출되지 않으므로 주기적으로 바꾸지 않아도 큰 문제가 없다고 함
- 반면 마스터 키는 외부 파일/KMS와 연결되어 노출될 가능성이 있으니 주기적인 변경이 필요
```mysql
ALTER INSTANCE ROTATE INNODB MASTER KEY;
```
- 마스터 키를 바꾸면:
  - 기존 마스터 키로 테이블스페이스 키를 복호화
  - 새 마스터 키로 다시 암호화
  - 실제 테이블 데이터 전체는 다시 암호화하지 않음
- 단계를 나눈 이유는 키 하나 바꿀 때마다 대용량 데이터 파일 전체를 다시 암/복호화하는 참사를 막기 위해서라고 보면 될 듯하다.
- 암호화 알고리즘:
  - 테이블스페이스 키: AES-256 ECB
  - 실제 데이터 파일: AES-256 CBC

### 7.1.2 암호화와 성능
- TDE는 디스크 I/O 시점에서만 암/복호화함
  - 한 번 읽은 페이지는 복호화된 상태로 버퍼 풀에 적재
  - 이후에는 암호화되지 않은 테이블과 거의 같게 처리됨
- 성능 영향이 생기는 부분:
  - 버퍼 풀에 없는 페이지를 디스크에서 읽을 때 복호화 시간이 추가됨
  - 변경된 페이지를 디스크에 쓸 때 암호화 시간이 추가됨
    - 쓰기는 백그라운드 스레드가 처리하므로 사용자 쿼리에 바로 드러나는 지연은 읽기보다 작을 수 있음
- 암호화해도 데이터 파일의 크기는 거의 달라지지 않음
  - 데이터 페이지가 암호화 키보다 훨씬 크기 때문에 암호문의 크기도 평문과 같음
  - 따라서 암호화 하나 때문에 버퍼 풀 효율이 떨어지는 것도 아님
- 압축 + 암호화를 함께 쓰면 **압축을 먼저 하고 암호화를 나중에 함**
  - 암호화된 데이터는 랜덤한 바이트 배열처럼 보여 압축률이 상당히 떨어짐
  - 먼저 압축해 용량을 줄인 후 암호화해야 압축의 이득을 가져갈 수 있음
  - 버퍼 풀의 압축 페이지는 압축/해제 상태가 모두 있을 수 있는데, 암호화를 먼저 하면 이런 페이지까지 계속 암/복호화해야 함
- 책의 테스트에서는 암호화 테이블의 디스크 읽기/쓰기가 더 느렸지만, 밀리초 단위이므로 실제 체감은 워크로드와 버퍼 풀 히트율에 따라 달라질 것 같다.
```mysql
SELECT
  (SUM(SUM_TIMER_READ) / SUM(COUNT_READ)) / 1000000000 AS avg_read_latency_ms,
  (SUM(SUM_TIMER_WRITE) / SUM(COUNT_WRITE)) / 1000000000 AS avg_write_latency_ms
FROM performance_schema.file_summary_by_instance
WHERE file_name LIKE '%DB_NAME/TABLE_NAME%';
```

### 7.1.3 암호화와 복제
- 복제 구조에서도 각 MySQL 서버는 **서로 다른 마스터 키**를 가져야 함
  - 소스의 마스터 키는 레플리카로 복제되지 않음
  - 테이블스페이스 키도 복제되지 않음
- 그래서 소스/레플리카의 논리적인 데이터는 같아도 디스크에 저장된 암호화 파일의 내용은 완전히 다름
- `ALTER INSTANCE ROTATE INNODB MASTER KEY`라는 SQL 문장 자체는 바이너리 로그로 레플리카에 전달됨
  - 그러나 실제 마스터 키 값이 전달되는 것은 아님
  - 각 서버가 자신의 키링 플러그인을 통해 새 마스터 키를 각각 발급받음
- 백업할 때 데이터 파일만 받고 키링 파일을 빼면 복구가 불가함
  - 보안을 위해 키링 파일은 데이터 파일과 별도로 보관하는 것이 좋지만, 각 백업 시점의 키링 파일도 함께 관리해야 함
  - 마스터 키는 계속 로테이션될 수 있으니 백업 시점과 키 변경 이력도 잘 맞춰야 함

## 7.2 keyring_file 플러그인 설치
- `keyring_file`: MySQL 커뮤니티 에디션에서 사용할 수 있는 파일 기반 키링 플러그인
  - 마스터 키를 로컬 디스크의 파일로 관리
  - 마스터 키가 암호화되지 않은 상태로 저장되므로 파일이 노출되면 TDE는 무의미해짐
- TDE 플러그인은 MySQL 서버가 시작되는 아주 초기 단계에서 먼저 초기화되어야 함
  - `my.cnf`의 `early-plugin-load`에 등록
```ini
early-plugin-load = keyring_file.so
keyring_file_data = /very/secure/directory/tde_master.key
```
- `keyring_file_data`에 지정한 파일은 하나의 MySQL 서버만 사용해야 함
  - 한 리눅스 서버에 MySQL 인스턴스가 여러 개라면 인스턴스별로 다른 키링 파일을 사용
- 플러그인 초기화 여부 확인:
```mysql
SHOW PLUGINS;
```
- 플러그인이 초기화되면 지정한 경로에 빈 키링 파일이 생성됨
  - 아직 암호화 테이블을 만들지 않았고 키 로테이션도 하지 않았다면 실제 키 내용은 비어 있을 수 있음
```mysql
ALTER INSTANCE ROTATE INNODB MASTER KEY;
```
  - 이 명령을 실행하면 마스터 키가 초기화/로테이션됨
  - SQL 문장은 Query Event로 바이너리 로그에 남지만 실제 키 값이 로그에 남는 것은 아님

## 7.3 테이블 암호화
- 키링 플러그인은 마스터 키를 만들고 관리하는 부분까지만 담당
- 암호화 테이블을 만들고 쓰는 방법은 어떤 키링 플러그인을 쓰든 같음

### 7.3.1 테이블 생성
```mysql
CREATE TABLE tab_encrypted (
  id INT,
  data VARCHAR(100),
  PRIMARY KEY(id)
) ENCRYPTION = 'Y';

INSERT INTO tab_encrypted VALUES (1, 'test_data');
SELECT * FROM tab_encrypted;
```
- 일반 테이블 생성문에 `ENCRYPTION='Y'`만 추가하면 됨
  - 디스크에 쓸 때 자동 암호화
  - 디스크에서 읽을 때 자동 복호화
- 암호화된 테이블 확인:
```mysql
SELECT table_schema, table_name, create_options
FROM information_schema.tables
WHERE table_name = 'tab_encrypted';
```
- 모든 새 테이블에 기본으로 암호화를 적용하려면 `default_table_encryption=ON`으로 설정
  - 매번 `ENCRYPTION='Y'`를 빼먹지 않고 지정해야 하는 불안함을 줄일 수 있음

### 7.3.2 응용 프로그램 암호화와의 비교
- 애플리케이션에서 먼저 암호화한 값은 MySQL 입장에서 그냥 의미를 알 수 없는 문자열/바이트
  - 이 칼럼에 인덱스를 만들어도 인덱스의 기능을 100% 쓸 수 없음
```mysql
SELECT *
FROM app_user
WHERE enc_birth_year = #{encryptedYear};

SELECT *
FROM app_user
WHERE enc_birth_year BETWEEN #{encryptedMinYear} AND #{encryptedMaxYear};

SELECT *
FROM app_user
ORDER BY enc_birth_year
LIMIT 10;
```
- 동등 비교:
  - 암호화된 값을 그대로 비교하면 되므로 가능
- 범위 검색/정렬:
  - MySQL은 암호화 전 값의 순서를 모르기 때문에 원본 값 기준으로 제대로 처리할 수 없음
- TDE는 MySQL이 인덱스 검색/정렬을 모두 끝낸 후 디스크에 쓰는 순간에만 암호화하므로 이런 제약이 없음
- 둘의 목적은 다르다:
  - DB 데이터 파일 유출 방지가 목적이라면 TDE가 더 자연스러움
  - DB에 로그인한 사용자에게도 평문을 숨겨야 한다면 애플리케이션 암호화가 필요
  - 결국 보안 요건/성능을 보고 둘 중 하나를 선택하거나 둘 다 사용해야 함

### 7.3.3 테이블스페이스 이동
- 테이블스페이스 Export/Import:
  - 테이블을 다른 서버로 옮기거나 특정 테이블만 빠르게 백업/복구할 때 사용
  - 레코드를 모두 덤프했다가 복구하는 방식보다 빠름
- 암호화되지 않은 테이블의 기본 흐름:
```mysql
FLUSH TABLES source_table FOR EXPORT;
-- source_table.ibd, source_table.cfg 복사
UNLOCK TABLES;
```
  - 저장되지 않은 변경 내용을 모두 디스크에 기록
  - 테이블에 락을 걸어 다른 사용자의 접근을 막음
  - 테이블 구조를 `.cfg` 파일에 저장
- TDE 테이블은 `.cfp` 파일이 추가로 생성됨
  - 원본/목적지 MySQL 서버의 마스터 키가 다르기 때문에 임시 마스터 키를 만들어 `.cfp`에 저장
  - 테이블스페이스 키를 기존 마스터 키로 복호화한 후 임시 마스터 키로 다시 암호화해 데이터 파일 헤더에 저장
- 암호화 테이블을 이동할 때 같이 복사해야 하는 파일:
  - `.ibd`
  - `.cfg`
  - `.cfp`
- `.cfg`는 없어도 경고 후 복구할 수 있는 경우가 있지만 `.cfp`가 없으면 암호화된 테이블스페이스를 복구할 수 없음

## 7.4 언두 로그 및 리두 로그 암호화
- 테이블에 TDE를 적용해도 메모리에서는 데이터가 복호화된 평문으로 존재
  - 이 평문이 언두/리두/바이너리 로그에 기록되면 데이터 파일만 암호화해도 로그에서 내용이 노출될 수 있음
- MySQL 8.0.16부터 아래 설정으로 언두/리두 로그 암호화를 지원:
  - `innodb_undo_log_encrypt`
  - `innodb_redo_log_encrypt`
- 언두/리두 로그는 암호화 설정을 켠다고 기존 로그 전체가 즉시 암호화되는 것은 아님
  - ON으로 바꾼 시점부터 새로 생성되는 로그만 암호화
  - OFF로 바꾸면 그 시점부터 새 로그만 평문으로 저장
- 그래서 암호화를 꺼도 기존에 암호화된 로그가 남아 있다면 해당 키가 계속 필요할 수 있음
  - 특히 언두 로그는 상황에 따라 며칠~몇 달까지 암호화된 로그가 남아 있을 수도 있음
- 리두/언두 로그는 각각 전용 프라이빗 키로 암호화
  - 프라이빗 키는 마스터 키로 암호화되어 각 로그 파일 헤더에 저장
  - `ALTER INSTANCE ROTATE INNODB MASTER KEY`를 실행하면 이 키들도 새 마스터 키로 다시 암호화됨
```mysql
SHOW GLOBAL VARIABLES LIKE 'innodb_redo_log_encrypt';
SET GLOBAL innodb_redo_log_encrypt = ON;
```
- 암호화가 제대로 됐는지 간단히 확인하는 방법:
  - 설정을 켜기 전/후에 서로 다른 문자열을 저장
  - 리두 로그 파일에서 `grep`으로 검색
  - 암호화 전에 저장한 문자열은 검색되지만 암호화 후의 문자열은 평문으로 검색되지 않음
```bash
grep 'Real-MySQL' ib_logfile0 ib_logfile1
echo $?

grep 'Real-MongoDB' ib_logfile0 ib_logfile1
echo $?
```

## 7.5 바이너리 로그 암호화
- 테이블을 암호화해도 바이너리/릴레이 로그는 기본적으로 평문을 저장
  - 리두/언두 로그는 비교적 짧은 시간만 보관하는 경우가 많지만, 바이너리 로그는 증분 백업 등을 위해 오랜 시간 보관하기도 함
  - 그래서 상황에 따라 바이너리 로그 암호화가 더 중요할 수 있음
- 바이너리/릴레이 로그 암호화는 **디스크에 저장된 로그 파일**만 암호화
  - MySQL 메모리 내부의 로그는 암호화 대상이 아님
  - 소스-레플리카 간 네트워크 구간도 자동으로 암호화하지 않음
  - 복제 네트워크 구간까지 암호화하려면 복제 계정에 SSL을 적용해야 함

### 7.5.1 바이너리 로그 암호화 키 관리
- 바이너리/릴레이 로그도 2단계 키 관리 방식을 사용:
  - 바이너리 로그 암호화 키
  - 파일 키(File Key)
- 바이너리/릴레이 로그의 실제 데이터는 파일 키로 암호화
- 파일 키는 바이너리 로그 암호화 키로 다시 암호화해 각 로그 파일 헤더에 저장
  - 바이너리 로그 암호화 키 = 테이블 암호화의 마스터 키와 같은 역할
  - 파일 키 = 바이너리/릴레이 로그 파일마다 새로 생성되어 해당 파일에만 사용

### 7.5.2 바이너리 로그 암호화 키 변경
```mysql
ALTER INSTANCE ROTATE BINLOG MASTER KEY;
```
- 로테이션 과정:
  1. 증가된 시퀀스 번호와 함께 새 바이너리 로그 암호화 키를 발급해 키링 파일에 저장
  2. 바이너리/릴레이 로그를 새 파일로 로테이션
  3. 새 로그 파일의 파일 키를 생성하고 새 마스터 키로 암호화해 헤더에 저장
  4. 기존 로그 파일의 파일 키도 읽어서 새 마스터 키로 다시 암호화
  5. 모든 파일의 처리가 끝나면 기존 바이너리 로그 암호화 키를 키링에서 제거
- 기존 로그 파일이 많으면 4번 작업이 상당히 오래 걸릴 수 있음
  - 그래서 바이너리 로그 암호화 키는 시퀀스 번호로 버전을 관리
  - 로테이션을 연속으로 실행하면 작업이 끝날 때까지 여러 버전의 키가 키링 파일에 함께 남아 있을 수 있음
- 암호화 여부 확인:
```mysql
SHOW BINARY LOGS;
```
  - 결과의 `Encrypted` 컬럼으로 각 바이너리 로그 파일의 암호화 여부를 확인 가능

### 7.5.3 mysqlbinlog 도구 활용
- 암호화된 바이너리 로그 파일은 `mysqlbinlog`로 로컬 파일을 직접 열어 볼 수 없음
```bash
mysqlbinlog -vvv mysql-bin.000011
```
  - 실행하면 `Reading encrypted log files directly is not supported`라는 오류가 발생
  - 해당 로그를 만든 MySQL 서버만 바이너리 로그 암호화 키를 가지고 있기 때문
- 내용을 확인하려면 해당 MySQL 서버에 접속해 로그를 가져와야 함
```bash
mysqlbinlog \
  --read-from-remote-server \
  --host=127.0.0.1 \
  --user=root \
  --password \
  mysql-bin.000011
```
- 이 명령의 `mysql-bin.000011`은 로컬 파일 경로가 아니라 MySQL 서버에 요청할 로그 파일의 이름
- 결국 암호화 환경에서는 바이너리 로그 파일만 따로 복사해 놓는 방식으로는 분석/복구를 보장할 수 없음
  - 키링 파일과 해당 MySQL 서버를 통한 접근 방법까지 함께 고려해야 함
