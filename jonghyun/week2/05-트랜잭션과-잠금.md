# Ch.5 트랜잭션과 잠금
- 트랜잭션: 작업의 완전성을 보장해 주는 것
  - 논리적인 작업 전체를 완벽히 처리하거나, 하나라도 처리하지 못할 시 원 상태로 복구시켜 partial update를 방지하는 기능
- 잠금과 트랜잭션의 차이:
  - 잠금: 동시성을 제어하기 위한 기능
  - 트랜잭션: 데이터의 정합성을 보장하기 위한 기능
- 격리 수준:
  - 여러 트랜잭션이 동시에 실행될 때 서로의 변경 내용을 어느 정도까지 볼 수 있게 할지 결정하는 레벨

---
## 5.1 트랜잭션
- 이번 절에서는 트랜잭션을 지원하는 InnoDB와 지원하지 않는 MyISAM의 처리 방식 차이를 살펴볼 예정.
- + 트랜잭션 사용시의 주의 사항

### 5.1.1 MySQL에서의 트랜잭션
```mysql
-- 먼저 실행된 쿼리
INSERT INTO tab_xxx(fdpk) VALUES (3);

-- 다음에 실행될 쿼리
INSERT INTO tab_xxx(fdpk) VALUES (1), (2), (3);
```
- 위 쿼리를 실행했을 때 (3이 중복 키라 가정)
- 트랜잭션을 지원하는 InnoDB의 경우:
  - 3이 이미 중복임. 전체 1, 2, 3에 대한 INSERT를 전체 롤백
- 트랜잭션 미지원인 MyISAM/MEMORY의 경우:
  - 중복인 3만 실패하고 1, 2는 INSERT 성공
  - INSERT 문이 실행되면서 앞순에 있던 1, 2가 먼저 저장된 후 3을 넣을 때 오류가 발생했기 때문에 트랜잭션이 없다면 그 앞의 1, 2는 정상 저장됨.
- 트랜잭션이 없다면 정합성의 보장을 위해 IF-ELSE로 가득한 참담한 코드를 짜야하나, 트랜잭션 덕에 안 그래도 된다!

### 5.1.2 주의사항
- 트랜잭션은 DB 커넥션과 동일하게 꼭 필요한 범위에만 걸어야 한다.
  - 범위를 최소화해야 좋다.
- 피해야하는 것:
  - 데이터베이스 커넥션과 트랜잭션에 포함될 필요없는 데이터의 유효성 처리나 외부 서버와의 통신 등은 최대한 트랜잭션에서 분리해야 한다.
    - 커넥션을 가지고 있는 시간이 길어질수록 가용 커넥션을 기다리는 상황이 발생할 수 있음
    - 트랜잭션 중간에 외부 서버와 통신할 수 없는 상황이 발생하면 애플리케이션 서버만이 아닌 DB 서버도 위험해질 수 있음.
    - 별도의 트랜잭션으로 뺄 수 있는 작업은 별도로 관리하는 것이 더 좋다.
      - ex: 사용자 입력 정보 + 첨부파일 정보 저장은 하나의 트랜잭션으로 묶어야하지만 알림 발송 내역은 별도 트랜잭션으로 관리하는 것이 더 좋을 것 같다.

- 문제라고 봤다는 예제:
```text
1) 처리 시작
	-> 커넥션 생성
	-> 트랜잭션 시작
2) 로그인 여부 확인
3) 글쓰기 오류 확인
4) 첨부로 업로드된 파일 저장
5) 사용자의 입력 내용을 DBMS에 저장
6) 첨부 파일 정보를 DBMS에 저장
7) 저장된 내용 또는 기타 정보를 DBMS에서 조회
8) 게시물 등록에 대한 알림 메일 발송
9) 알림 메일 발송 이력을 DBMS에 저장
10) 처리 완료
	-> 트랜잭션 COMMIT
	-> 커넥션 반납
```

- 개선한 버전:
```text
1) 처리 시작
2) 로그인 여부 확인
3) 글쓰기 오류 확인
4) 첨부로 업로드된 파일 저장
	-> 커넥션 생성
	-> 트랜잭션A 시작
5) 사용자의 입력 내용을 DBMS에 저장
6) 첨부 파일 정보를 DBMS에 저장
	-> 트랜잭션A COMMIT
7) 저장된 내용 또는 기타 정보를 DBMS에서 조회
8) 게시물 등록에 대한 알림 메일 발송
	-> 트랜잭션B 시작
9) 알림 메일 발송 이력을 DBMS에 저장
	-> 트랜잭션B COMMIT
	-> 커넥션 반납
10) 처리 완료
```

- 그러나 모든 상황에 이게 최적이라는 말은 아니고, 구현하고자 하는 업무의 특성에 따라 달라질 수 있다고 한다.
  - 포인트는 커넥션을 가지고 있는 범위와 트랜잭션이 활성화되어 있는 범위를 최소화하는 게 DB 관점에서의 베스트 프랙티스다 정도.

## 5.2 MySQL 엔진의 잠금
- MySQL의 락:
  - 스토리지 엔진 레벨 락
  - MySQL 엔진 레벨 락
    - MySQL 엔진 락은 모든 스토리지 엔진에 영향을 끼침
    - 스토리지 엔진 락은 MySQL 엔진이나 다른 스토리지 엔진에는 영향을 끼치지 않음
    - 제공하는 락:
      - 테이블 락: 테이블 데이터 동기화 용도
      - 메타데이터 락: 테이블의 이름이나 구조를 잠금
      - 네임드 락: 사용자가 정한 문자열을 기준으로 필요에 맞게 사용 가능

### 5.2.1 글로벌 락
- 글로벌 락(Global Lock): MySQL에서 제공하는 락 중 가장 범위가 큼
  - `FLUSH TABLES WITH READ LOCK`으로 획득 가능
    - 테이블을 FLUSH하는 명령이기에 이 명령은 실행 즉시 모든 테이블에 락을 걸며 대기함.
      - 락 획득 명령이 실행되기 전 실행된 모든 구문이 종료될 때까지 대기한 후 락을 획득함
      - 최악의 케이스에는 이 락을 얻기 위한 대기 + 락이 잡힌 후의 대기가 합쳐져 지연 시간이 굉장히 길어질 수 있음
      - 이런 이유로 운영 중인 서버에서 사용하는 것은 지양해야 함.
        - `mysqldump`같은 백업 프로그램이 내부적으로 이 락을 사용할 수도 있으니 옵션을 잘 살펴야 함.
  - 한 세션이 글로벌 락을 획득하면 다른 세션에서는 SELECT를 제외한 DDL, DML이 락이 해제될 때까지 대기 상태가 됨.
  - MyISAM이나 MEMORY 테이블을 `mysqldump`로 백업받아야 할 때 사용
- InnoDB가 대세가 되고 MySQL 8.0부터 기본 스토리지 엔진으로 채택되면서, 백업 때 모든 데이터 변경을 멈출 필요가 적어짐
  - 이 때문에 나온 게 글로벌 락보다 가벼운 백업 락.
```mysql
LOCK INSTANCE FOR BACKUP;
UNLOCK INSTANCE;
```
- 백업 락을 획득하면 모든 세션에서 아래 작업이 불가함:
  - DB/테이블 등 모든 객체의 생성, 변경, 삭제
  - `REPAIR TABLE`, `OPTIMIZE TABLE`
  - 사용자 관리 및 비밀번호 변경
- 그래도 일반적인 테이블의 데이터 변경은 허용됨.
  - XtraBackup/Enterprise Backup 등이 백업하는 도중 DDL이 실행되어 백업이 망가지는 것을 방지하려는 용도.

### 5.2.2 테이블 락
- 테이블 락(Table Lock): 개별 테이블 단위로 설정되는 락
- 명시적인 획득:
```mysql
LOCK TABLES table_name READ;
LOCK TABLES table_name WRITE;
UNLOCK TABLES;
```
  - MyISAM, InnoDB 모두 사용 가능
  - 글로벌 락과 마찬가지로 영향 범위가 크기 때문에 일반적인 애플리케이션에서는 쓸 일이 거의 없다고 함.
- 묵시적인 획득:
  - MyISAM/MEMORY 테이블에 데이터를 변경하는 쿼리가 실행되면 자동으로 획득되고, 쿼리가 끝나면 바로 해제됨
  - InnoDB는 스토리지 엔진에서 레코드 기반 락을 제공해서 DML의 묵시적 테이블 락은 대부분 무시됨
    - DDL로 스키마를 변경할 때는 영향을 받음

### 5.2.3 네임드 락
- 네임드 락(Named Lock): 임의의 문자열에 대해 걸 수 있는 락
  - 테이블이나 레코드 같은 DB 객체를 잠그는 게 아니라 사용자가 지정한 문자열을 잠그는 방식
```mysql
SELECT GET_LOCK('mylock', 2);
SELECT IS_FREE_LOCK('mylock');
SELECT RELEASE_LOCK('mylock');
SELECT RELEASE_ALL_LOCKS();
```
  - `GET_LOCK('mylock', 2)`: `mylock`이라는 문자열에 대한 락을 얻되, 다른 세션이 사용 중이면 2초까지 대기
  - 정상적으로 획득/해제하면 1, 그렇지 않으면 0 또는 NULL을 리턴
- 사용처:
  - DB 한 대에 여러 애플리케이션 서버가 붙어 있을 때 서로 같은 작업을 동시에 실행하지 못하게 막는 용도
  - 많은 레코드를 바꾸는 배치 프로그램에서 같은 데이터를 다루는 작업끼리 직렬화해 데드락을 줄이는 용도
- MySQL 8.0부터는 네임드 락을 중첩해 획득할 수 있고, 현재 세션이 얻은 락을 `RELEASE_ALL_LOCKS()`로 한 번에 해제할 수 있음

### 5.2.4 메타데이터 락
- 메타데이터 락(Metadata Lock): 테이블/뷰 같은 DB 객체의 이름이나 구조를 변경할 때 획득되는 락
  - 직접 얻거나 해제하는 락은 아니고 MySQL 서버가 자동으로 관리함
- 서비스에서 쓰는 `rank` 테이블을 새 테이블로 교체한다면:
```mysql
RENAME TABLE rank TO rank_backup, rank_new TO rank;
```
  - 하나의 명령으로 실행하면 원본/변경될 이름을 모두 한 번에 잠그므로 `rank` 테이블이 없는 순간이 생기지 않음
```mysql
RENAME TABLE rank TO rank_backup;
RENAME TABLE rank_new TO rank;
```
  - 이렇게 나눠서 실행하면 짧은 시간이라도 `rank`가 없어져 `Table not found`가 발생할 수 있음
- 대용량 테이블의 구조를 바꾸는 경우:
  - Online DDL로 바꾸면 시간이 너무 오래 걸리고, 언두 로그나 Online DDL 버퍼가 지나치게 커질 수 있음
  - 새 구조의 테이블을 먼저 만든 후, PK 범위별로 나눠 여러 스레드에서 기존 데이터를 복사
  - 마지막에 테이블 쓰기 락을 잡고 남은 데이터만 복사한 후 `RENAME TABLE`로 교체
  - 미리 최근 데이터까지 복사해 두면 실제 락을 잡고 있는 시간은 짧게 가져갈 수 있음

## 5.3 InnoDB 스토리지 엔진의 잠금
- InnoDB는 MySQL 엔진의 락과 별개로 스토리지 엔진 내부에서 레코드 기반의 락을 제공함
  - MyISAM의 테이블 단위 락보다 훨씬 높은 동시성을 제공할 수 있음
- 레코드 락이 페이지 락이나 테이블 락으로 승격되는 Lock Escalation은 없다고 함

### 5.3.1 InnoDB 스토리지 엔진의 잠금
- 레코드 기반의 잠금 기능을 제공하고, 잠금 정보가 상당히 작은 공간으로 관리됨
  - 때문에 락이 레벨업(락 에스컬레이션)이 없다

#### 5.3.1.1 레코드 락
- 레코드 자체만 잠그는 락
  - InnoDB는 실제 레코드가 아니라 **인덱스의 레코드**를 잠그는 방식
  - 인덱스가 하나도 없는 테이블이라도 내부적으로 생성된 클러스터 인덱스를 이용해 락을 걸게 됨
- 보조 인덱스를 이용한 변경은 대부분 갭 락/넥스트 키 락을 사용하지만, PK나 유니크 인덱스로 변경할 때는 보통 갭까지 잠그지 않고 레코드만 잠그게 됨

#### 5.3.1.2 갭 락
- 레코드 자체가 아니라 레코드와 바로 인접한 레코드 사이의 **간격**을 잠그는 락
  - 해당 간격에 새로운 레코드가 INSERT되는 것을 제어함
  - 단독으로 쓰이기보다 넥스트 키 락의 일부로 더 자주 사용됨

#### 5.3.1.3 넥스트 키 락
- 레코드 락 + 갭 락을 합친 형태
- 주목적:
  - STATEMENT 포맷 바이너리 로그를 사용할 때, 소스 서버와 레플리카에서 같은 결과가 만들어지게 보장하는 것
- 문제는 갭까지 잠그므로 데드락이나 락 대기가 자주 발생할 수 있다는 것
  - 가능하다면 바이너리 로그를 ROW 포맷으로 사용해 불필요한 갭 락/넥스트 키 락을 줄이는 것이 좋다고 함
    - MySQL 8.0은 ROW 포맷이 기본값

#### 5.3.1.4 자동 증가 락
- AUTO_INCREMENT 값을 중복 없이 안전하게 채번하기 위한 테이블 수준의 락
  - 새 레코드를 저장하는 쿼리에서만 필요
    - INSERT/REPLACE
  - UPDATE/DELETE에는 걸리지 않음
  - 테이블 레벨 락으로 테이블에 하나만 존재하기에 동시에 INSERT가 실행되면 락을 먼저 획득한 쪽이 실행되고 다른쪽은 대기하다 실행됨
    - AUTO_INCEMENT되는 값을 지정해서 INSERT하더라도 마찬가지이다.
  - 명시적으로 획득/해제하는 방법은 없음
- `innodb_autoinc_lock_mode` 환경 변수로 락의 작동 방식 변경 가능
  - `0`: 모든 INSERT에 AUTO_INCREMENT 락을 사용
  - `1`:
    - 넣을 레코드 수를 미리 알 수 있는 단순 INSERT는 가벼운 래치를 사용
    - `INSERT ... SELECT`처럼 건수를 알 수 없는 경우는 AUTO_INCREMENT 락을 사용
    - 하나의 INSERT 문장 안에서는 연속된 증가 값을 보장함
  - `2`:
    - AUTO_INCREMENT 락을 사용하지 않고 래치(뮤텍스)만 사용
    - 동시성은 좋지만 하나의 INSERT 문장 안에서도 연속된 값을 보장하지는 않음
    - 유니크한 값이 생성된다는 것만 보장
- MySQL 8.0은 ROW 포맷이 기본이 되면서 `innodb_autoinc_lock_mode=2`가 기본값이 됨
  - STATEMENT 포맷에서 모드 2를 쓰면 소스와 레플리카의 AUTO_INCREMENT 값이 달라질 수 있어 모드 1을 쓰는 것이 안전하다고 함
- 자동 증가 값은 한 번 증가하면 INSERT가 실패해도 다시 줄어들지 않음

### 5.3.2 인덱스와 잠금
- InnoDB는 **변경할 레코드를 찾기 위해 검색한 인덱스의 레코드를 모두 잠그는 방식**
```mysql
-- first_name에만 인덱스가 있다고 가정
UPDATE employees
SET hire_date = NOW()
WHERE first_name = 'Georgi'
  AND last_name = 'Klassen';
```
- 위 쿼리 실행시 실제로 바뀔 레코드가 1건이라도:
  - 인덱스로 검색할 수 있는 조건은 `first_name='Georgi'`뿐
  - `first_name='Georgi'`인 253건을 모두 잠그고 그중 `last_name='Klassen'`인 1건만 변경함
- 적절한 인덱스가 없다면 테이블 풀 스캔을 하면서 스캔한 모든 레코드에 락을 걸 수 있음
  - 그 세션이 UPDATE하는 동안 다른 세션의 변경이 거의 막혀버릴 수도 있음
  - 결국 InnoDB에서 인덱스는 조회 성능뿐만 아니라 **락의 범위와 동시성**에도 직접적으로 영향을 줌.
    - 인덱스가 중요한 이유가 하나 더 늘었다.

### 5.3.3 레코드 수준의 잠금 확인 및 해제
- 레코드 락은 테이블 락보다 문제를 찾기가 어렵다.
  - 테이블 자체가 아닌 특정 레코드만 잠겨 있을 수 있기 때문
- MySQL 8.0에서는 아래 performance_schema 테이블로 확인 가능:
  - `performance_schema.data_locks`: 현재 잡힌 락
  - `performance_schema.data_lock_waits`: 어떤 트랜잭션이 어떤 락을 기다리는지
```mysql
SELECT
  r.trx_id AS waiting_trx_id,
  r.trx_mysql_thread_id AS waiting_thread,
  b.trx_id AS blocking_trx_id,
  b.trx_mysql_thread_id AS blocking_thread
FROM performance_schema.data_lock_waits AS w
JOIN information_schema.innodb_trx AS b
  ON b.trx_id = w.blocking_engine_transaction_id
JOIN information_schema.innodb_trx AS r
  ON r.trx_id = w.requesting_engine_transaction_id;
```
- 오랜 시간 락을 잡고 있는 세션이 문제라면 해당 스레드를 `KILL`해 락을 풀 수 있음
```mysql
KILL {thread_id};
```

## 5.4 MySQL의 격리 수준
- 트랜잭션의 격리 수준(Isolation Level): 여러 트랜잭션이 동시에 처리될 때, 특정 트랜잭션이 다른 트랜잭션의 변경/조회 데이터를 볼 수 있게 할지 결정하는 수준
- 4가지 격리 수준:

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | 발생 | 발생 | 발생 |
| `READ COMMITTED` | 없음 | 발생 | 발생 |
| `REPEATABLE READ` | 없음 | 없음 | 발생<br>(InnoDB는 없음) |
| `SERIALIZABLE` | 없음 | 없음 | 없음 |

- 아래로 갈수록 데이터 정합성은 높아지지만 동시 처리 성능은 떨어짐
  - 근데 SERIALIZABLE 아니면 크게 성능 저하는 없다고 함
- 일반적인 온라인 서비스에서는 `READ COMMITTED` 또는 `REPEATABLE READ`를 사용
  - Oracle: `READ COMMITTED`가 기본
  - MySQL InnoDB: `REPEATABLE READ`가 기본

- SQL 표준에서는 `REPEATABLE READ`에서도 Phantom Read가 발생할 수 있음
  - 다만 InnoDB는 갭 락과 넥스트 키 락을 이용해 일반적인 Phantom Read를 막아줌

### 5.4.1 READ UNCOMMITTED
- 다른 트랜잭션이 아직 COMMIT하지 않은 변경 내용까지 읽을 수 있는 격리 수준
  - 이를 Dirty Read라고 함
- A 트랜잭션이 새 레코드를 INSERT한 후 COMMIT하지 않았는데도 B가 이를 조회할 수 있음
  - 이후 A가 ROLLBACK하면 실제로는 없었던 데이터를 B가 정상 데이터라고 생각하고 처리하게 됨
- 데이터가 보였다가 사라지는 상황이 생기므로 정합성에 문제가 많음
  - MySQL을 쓴다면 최소 `READ COMMITTED` 이상을 쓰는 것이 좋다고 함

### 5.4.2 READ COMMITTED
- COMMIT이 완료된 데이터만 다른 트랜잭션에서 조회할 수 있음
  - Dirty Read는 발생하지 않음
- 다른 트랜잭션이 변경 중인 레코드를 읽으면 InnoDB는 언두 영역에 백업된 변경 전 값을 리턴함
- 그런데 같은 트랜잭션 안에서 같은 SELECT를 두 번 실행해도 결과가 달라질 수 있음
  - 첫 조회 후 다른 트랜잭션이 데이터를 변경하고 COMMIT하면 두 번째 조회에서는 이 변경 결과가 보임
  - 이를 Non-Repeatable Read라고 함

### 5.4.3 REPEATABLE READ
- MySQL InnoDB의 기본 격리 수준
- 같은 트랜잭션 안에서는 같은 SELECT의 결과를 보장함
  - MVCC와 언두 로그를 이용해 구현
  - 각 트랜잭션은 고유한 트랜잭션 번호를 가짐
  - 트랜잭션이 시작된 후에 다른 트랜잭션이 변경하고 COMMIT해도, 자신의 트랜잭션에서는 이전 버전의 데이터를 계속 보게 됨
- 장시간 열린 트랜잭션이 있으면 그 트랜잭션에서 필요한 언두 데이터를 지울 수 없음
  - 언두 영역이 무한정 커지고 서버 성능이 떨어질 수도 있으니, 여기서도 트랜잭션을 짧게 유지해야 하는 이유가 나온다.
- Phantom Read:
  - 다른 트랜잭션의 변경으로 인해 같은 조건의 조회에서 레코드가 보였다가 안 보이는 현상
  - InnoDB는 갭 락과 넥스트 키 락으로 일반적인 Phantom Read를 막음
  - 다만 `SELECT ... FOR UPDATE`, `SELECT ... FOR SHARE`처럼 락을 걸어야 하는 SELECT는 언두 레코드에 락을 걸 수 없기 때문에 현재 레코드를 읽음
    - 이런 예외적인 경우에는 Phantom Read가 발생할 수 있음

### 5.4.4 SERIALIZABLE
- 가장 단순하면서도 가장 엄격한 격리 수준
  - 그만큼 동시 처리 성능은 가장 떨어짐
- 일반적인 InnoDB의 SELECT는 락을 걸지 않는 Non-Locking Consistent Read로 동작함
- SERIALIZABLE로 설정하면 읽기 작업도 공유 락을 획득해야 함
  - 한 트랜잭션이 읽고 있는 레코드를 다른 트랜잭션이 변경하지 못함
- InnoDB는 `REPEATABLE READ`에서도 갭 락/넥스트 키 락으로 Phantom Read를 대부분 막아주므로, 특별한 이유가 없다면 굳이 SERIALIZABLE까지 사용할 필요는 적어 보임
