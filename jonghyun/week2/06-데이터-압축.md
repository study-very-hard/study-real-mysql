# Ch.6 데이터 압축
- DB 서버에 저장된 데이터 파일의 크기는 단순히 디스크 용량만의 문제가 아님
  - 파일이 커질수록 쿼리를 처리하기 위해 더 많은 페이지를 InnoDB 버퍼 풀로 읽어야 할 수 있음
  - 새 페이지가 계속 적재되면 더티 페이지도 디스크로 더 자주 write 해야함
  - 백업/복구 시간과 스토리지 비용도 당연히 커짐
  - 위와 같은 문제들을 해결하기 위해 데이터 압축 기능이 제공됨
- MySQL이 제공하는 압축 방식:
  - 페이지 압축(Page Compression)
  - 테이블 압축(Table Compression)

---
## 6.1 페이지 압축
- 페이지 압축은 Transparent Page Compression이라고도 함
  - MySQL이 데이터 페이지를 디스크에 쓸 때 압축
  - 디스크에서 읽어올 때 압축 해제
  - 버퍼 풀에 올라온 후에는 압축이 해제된 상태로 관리됨
- 즉 InnoDB 내부에서는 압축 여부를 상관하지 않고 동작하기 때문에 `Transparent`라고 부르는 듯함
- 문제:
  - InnoDB 페이지는 보통 16KB로 고정된 크기를 가짐
  - 그런데 16KB를 압축했을 때 결과가 7KB가 될지 10KB가 될지 미리 알 수 없음
  - 하나의 테이블은 같은 크기의 페이지를 써야하는데 압축 결과는 매번 다르니, 여기서 문제가 생김
- 이를 해결하기 위해 OS/파일 시스템의 **Punch Hole 기능을 사용**

예를 들어 16KB 페이지를 압축했더니 7KB가 됐다면:

1. 16KB 페이지를 압축 -> 결과 7KB
2. MySQL은 압축된 7KB + 빈 데이터 9KB를 합쳐 디스크에 16KB를 기록
3. 7KB 뒤의 빈 9KB 영역에 Punch Hole을 생성
4. 파일 시스템이 빈 9KB를 OS에 돌려줘서 실제 디스크에서는 7KB만 사용

- 문제:
  - OS & 파일 시스템 & 하드웨어가 Punch Hole을 지원해야 함
  - `cp`나 일부 백업 툴이 Punch Hole을 그대로 유지하지 못할 수 있음
    - 실제 사용량은 1GB였던 파일이 복사 후 원본 크기인 10GB로 불어날 수도 있음
- 이런 제약 때문에 실무에서는 많이 사용되지 않는다고 함
  - 그래서 설명도 없이 간다함

## 6.2 테이블 압축
- 테이블 압축은 페이지 압축과 달리 OS나 하드웨어에 대한 제약 없이 사용 가능
  - 그래서 페이지 압축보다는 활용도가 높음
- 단점:
  - 버퍼 풀 공간 활용률이 낮아짐
  - 압축/해제에 CPU를 쓰므로 쿼리 처리 성능이 낮아질 수 있음
  - 데이터가 빈번하게 변경되면 압축률이 떨어짐
- 디스크를 아끼는 대신 CPU/메모리를 더 쓰는 구조라고 보면 될 듯하다.

### 6.2.1 압축 테이블 생성
- 압축 테이블 생성 방법:
  - 압축할 테이블이 독립된 테이블스페이스를 사용해야 함
    - `innodb_file_per_table=ON`인 상태에서 테이블이 생성되어야 함
    - 테이블 생성시 `ROW_FORMAT=COMPRESSED` 옵션을 명시
    - `KEY_BLOCK_SIZE` 옵션을 추가해 압축된 페이지의 목표 크기(KB) 설정
- ex:
```mysql
SET GLOBAL innodb_file_per_table = ON;

CREATE TABLE compressed_table (
  c1 INT PRIMARY KEY
)
ROW_FORMAT = COMPRESSED
KEY_BLOCK_SIZE = 8;
```
- InnoDB 페이지 크기가 16KB라면 `KEY_BLOCK_SIZE`는 4KB 또는 8KB로 설정 가능
  - 페이지 크기가 32KB/64KB인 경우에는 테이블 압축을 사용할 수 없음
  - `KEY_BLOCK_SIZE`만 지정해도 `ROW_FORMAT=COMPRESSED`는 자동으로 적용됨

- 압축이 작동하는 방식:
```
1. 16KB 데이터 페이지를 압축
2. 결과가 `KEY_BLOCK_SIZE` 이하면 그대로 디스크에 저장
3. 결과가 목표 크기보다 크면 원본 페이지를 2개로 split한 후 다시 압축
4. 목표 크기 이하가 될 때까지 반복
```
- `KEY_BLOCK_SIZE`를 너무 작게 잡으면 페이지 split + 재압축이 반복되어 성능이 급격히 떨어질 수 있음

### 6.2.2 KEY_BLOCK_SIZE 결정
- 실제 압축률은 데이터의 특성에 따라 달라지므로 미리 계산만 해서는 알기 어려움
  - 4KB/8KB 테이블을 각각 만들고 샘플 데이터를 넣어보는 것이 좋음
  - 샘플은 많을수록 좋고, 최소한 데이터 페이지가 10개 정도는 생길 만큼 INSERT해야 함
- 인덱스별 압축 통계를 수집하려면:
```mysql
SET GLOBAL innodb_cmp_per_index_enabled = ON;

SELECT
  table_name,
  index_name,
  compress_ops,
  compress_ops_ok,
  (compress_ops - compress_ops_ok) / compress_ops * 100 AS compression_failure_pct
FROM information_schema.INNODB_CMP_PER_INDEX;
```
- 통계의 의미:
  - `compress_ops`: 압축을 시도한 횟수
  - `compress_ops_ok`: 압축에 성공한 횟수
  - 압축 실패: 압축 시도 횟수가 성공 횟수보다 큼 -> 압축 결과가 너무 커서(KEY_BLOCK_SIZE보다 커서) 페이지를 split하고 다시 압축했다는 의미
- 일반적으로 압축 실패율이 3~5% 미만이 되도록 `KEY_BLOCK_SIZE`를 결정하는 것이 좋다고 함
- 그런데 실패율만 보고 압축 여부를 결정하면 안 됨:
  - INSERT 후 거의 변경되지 않는 로그 테이블은 처음 한 번의 압축 비용보다 디스크 절약이 더 중요할 수 있음
  - 반대로 조회/변경이 빈번한 테이블은 실패율이 낮아도 계속 발생하는 압축/해제 CPU 비용이 더 클 수 있음
  - 테이블 압축은 zlib을 쓰는데 생각보다 CPU를 많이 쓴다고 함.

### 6.2.3 압축된 페이지의 버퍼 풀 적재 및 사용
- InnoDB는 압축 테이블의 페이지를 버퍼 풀에 올리면 두 가지 버전을 관리:
  - 압축된 상태의 페이지
  - 압축이 해제된 상태의 페이지
- 관리하는 리스트:
  - LRU 리스트:
    - 압축되지 않은 테이블의 페이지
    - 압축 테이블의 압축된 페이지
      - MySQL은 압축된 테이블과 압축되지 않은 테이블이 공존할 수 있음.
  - Unzip_LRU 리스트:
    - 압축 테이블의 압축 해제된 페이지만 관리
- 결국 압축 테이블의 페이지는 압축/해제 버전이 둘 다 메모리에 있을 수 있어 버퍼 풀을 이중으로 사용하는 효과가 생김
  - 데이터를 읽거나 변경할 때 압축 해제가 필요하므로 CPU도 더 쓰게 됨
- InnoDB는 요청 패턴을 보고 이 두 리스트를 적응적으로 관리함:
  - 버퍼 풀 공간이 필요하면 LRU의 압축 페이지는 남기고 Unzip_LRU의 해제된 버전을 제거
  - 자주 사용되는 압축 페이지는 Unzip_LRU에 유지해 반복적인 압축 해제를 줄임
  - 압축 페이지가 LRU에서 제거되면 Unzip_LRU의 해제 버전도 함께 제거
- CPU 사용량이 높으면 압축/해제를 줄이기 위해 Unzip_LRU 비율을 높이고, Disk I/O가 높으면 버퍼 풀 공간을 더 확보하기 위해 Unzip_LRU 비율을 낮추는 방향으로 동작

### 6.2.4 테이블 압축 관련 설정
- `innodb_cmp_per_index_enabled`
  - 인덱스별 압축 시도/성공 횟수를 수집할지 설정
  - OFF면 테이블 단위 통계만 수집
  - 테이블 단위: `information_schema.INNODB_CMP`
  - 인덱스 단위: `information_schema.INNODB_CMP_PER_INDEX`
- `innodb_compression_level`
  - zlib 압축 레벨. 0~9 중 선택할 수 있음
  - 값이 낮으면 빠르지만 압축률은 낮아질 수 있음
  - 값이 높으면 압축률은 높아지지만 CPU를 더 쓰고 느려질 수 있음
  - 기본값은 6
- `innodb_compression_failure_threshold_pct`
  - 테이블의 압축 실패율이 이 값보다 커지면 압축 전에 원본 페이지 끝에 일정한 빈 공간(Padding)을 추가
  - 빈 공간이 늘면 실제 데이터가 줄어 `KEY_BLOCK_SIZE` 안에 들어갈 가능성이 커짐
- `innodb_compression_pad_pct_max`
  - 위 Padding을 얼마까지 추가할지 페이지 크기 대비 %로 설정
- `innodb_log_compressed_pages`
  - 압축된 페이지를 그대로 리두 로그에 기록할지 설정
  - zlib 버전이 달라져도 복구가 실패하지 않도록 도와주는 설정
  - 기본값은 ON
  - 단점은 데이터 페이지 전체가 리두 로그에 들어가 로그 용량이 빠르게 증가할 수 있다는 것
  - 압축을 적용한 후 리두 로그가 너무 빨리 커지거나 더티 페이지 기록 패턴이 크게 바뀌다면 OFF로 테스트해볼 수는 있지만, 가능하면 기본값 ON을 유지하는 것이 좋다고 함
