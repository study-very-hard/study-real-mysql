## 4.1 MySQL 엔진 아키텍처
- MySQL은 다른 DBMS에 비해 구조가 상당히 독특하다.
  - 개발자 입장에서는 차이가 거의 느껴지지 않게 인터페이스화 되어있다.
  - 이 독특한 구조 때문에 다른 DBMS와 비교해 이득도 있지만, 문제되는 것들도 동시에 같이 존재한다.
- MySQL 서버 구조:
  - MySQL 엔진: 요청된 SQL 문장을 분석/최적화하는 두뇌
    - 커넥션 핸들러
    - SQL 인터페이스
    - SQL 파서
    - SQL 옵티마이저
    - 캐시 & 버퍼
  - 스토리지 엔진: 실제 데이터를 디스크 스토리지(파일 시스템)에 저장하거나 디스크 스토리지로부터 데이터를 읽어오는 부분은 스토리지 엔진이 전담
    - InnoDB
    - MySIAM
    - Memory
    - MySQL 서버에서 MySQL 엔진은 하나지만, 스토리지 엔진은 여러개를 동시 사용이 가능함
      - 테이블 생성시 명령어에 엔진을 명시해서 해당 엔진으로 실행되게 지정할 수 있고 해당 테이블의 읽기 쓰기 작업은 정의한 스토리지 엔진으로 처리함
- 위는 MySQL 서버의 구조이고, 통신을 위한 프로그래밍 API와 운영체제 영역은 별도
  
#### 4.1.1.3 핸들러 API
- **핸들러 요청**: MySQL 엔진의 쿼리 실행기에서 스토리지 엔진에 보내는 쓰기/일기 요청 
- **핸들러 API**: 핸들러 요청 처리를 위한 API.
- 어떤 핸들러가 얼마나 사용되었는지 알 수 있게 해주는 명령어: `SHOW GLOBAL STATUS LIKE 'Handler%'`

### 4.1.2 MySQL 스레딩 구조
- MySQL 서버는 프로세스 기반이 아닌 스레드 기반으로 동작하며 크게는 아래 두 타입으로 나뉨 
  - MySQL 서버에서 실행중인 스레드는 performance_schema의 threads 테이블을 통해 확인 가능함
    - 동일한 이름의 스레드가 2개씩 보이는 경우가 있는데 이는 MySQL 서버 설정에 의해 여러 스레드가 동일 작업을 병렬 처리하는 경우
  - 다만 이 장에서 설명하는 MySQL의 스레드 모델은 커뮤니티 에디션의 스레드 모델이고, 상용 버전에서는 스레드 풀을 사용한다고 함
- Foreground Thread (클라이언트/사용자 스레드)
  - 각 클라의 사용자 요청 쿼리를 처리하는 역할을 함
    - 데이터를 버퍼나 캐시로부터 가져오며, 버퍼나 캐시에 없는 경우 직접 디스크의 데이터나 인덱스 파일로부터 데이터를 읽어와 작업을 처리함
      - MyISAM의 경우는 디스크 쓰기까지 포그라운드에서 직접 진행
        - 지연된 쓰기가 있으나 일반적이진 않음
      - InnoDB의 경우 데이터 버퍼나 캐시까지만 진행하고, 버퍼 -> 디스크로의 쓰기는 백그라운드에서 진행함
  - MySQL 서버에 접속된 클라의 수만큼 존재
  - 클라 작업이 완료되면 스레드 캐시로 돌아가나, `thread_cache_size` 이상의 스레드가 캐시에 있다면 스레드를 종료시킴
- Background Thread
  - MyISAM 엔진은 해당되지 않음. InnoDB 의 작업.
  - 주된 작업 예시:
    - 인서트 버퍼를 병합하는 스레드
    - 로그를 디스크로 기록하는 스레드 
    - InnoDB 버퍼풀의 데이터를 디스크에 기록하는 스레드
    - 데이터를 버퍼로 읽어오는 스레드
    - 잡금이나 데드락을 모니터링하는 스레드
  - 제일 중요한건 로그 스레드와 쓰기 쓰레드일 것.
  - 5.5 버전부터 쓰기/읽기 쓰레드의 수를 2개 이상으로 지정할 수 있게 되었고, 일반적인 경우에는 변경할 일이 없으나 DAS/SAN등 스토리지를 사용하는 경우에 디스크 최적화를 위해 쓰기 스레드를 늘릴 수 있다.
    - 읽기는 어차피 포그라운드/클라이언트/사용자 스레드에서 처리되니 설정은 불필요

### 4.1.3 메모리 할당 및 사용 구조
- 글로벌 메모리 영역: 
  - 서버 기동시 운영체제로부터 할당
  - 클라이언트 수와 무관히 하나의 메모리 공간만 할당됨 (수는 필요에 따라 늘어날 수 있음)
  - 모든 스레드에 공유되는 메모리 영역
  - 포함되는 영역:
    - InnoDB 버퍼 풀
    - MyISAM 키 캐시
    - 바이너리 로그 버퍼
    - 리두 로그 버퍼
    - 테이블 캐시
- 로컬(세션/커넥션) 메모리 영역:
  - MySQL 서버에 존재하는 클라이언트 스레드가 쿼리를 처리하는데 사용하는 메모리 영역
  - 각 커넥션 별로 독립 할당되며 공유되지 않음.
  - 가능성은 희박하지만 최악의 경우 MySQL 서버가 메모리 부족으로 멈춰 버릴 수도 있기에 적절한 메모리 공간을 할당해야함
  - 포함되는 영역:
    - 조인 버퍼
    - 정렬 버퍼
    - 네트워크 버퍼
    - 리드 버퍼

### 4.1.4 플러그인 스토리지 엔진 모델
- MySQL의 대표적인 독특한 구조
  - 그러나 8.0 부터는 기존의 플러그인을 대체하는 컴포넌트가 나옴
- 스토리지 엔진의 기능을 플러그인화하여 다양한 기능을 구현할 수 있게 만들어준 구조.
  - 이 세상 수많은 사용자의 니즈를 다 맞추기 위해 기본 제공되는 스토리지 엔진 외에 부가기능이 달린 엔진이 필요할 수 있고, 그러한 요건을 맞춰 스스로 개발할 수 있게 열려있는 구조라 생각하면 될 듯 하다
- MySQL 서버의 경우 대부분의 작업은 MySQL 엔진 영역에서 일어나고, 마지막의 `데이터 읽기/쓰기` 작업만 스토리지 엔진에서 일어닌다.
  - InnoDB, MyISAM 같이 다른 엔진으로 만들어진 테이블의 데이터를 처리하더라도 대부분의 작업은 비슷하며 마지막에 데이터의 읽기 쓰기 영역에서만 차이가 난다.
    - 복잡한 GROUP BY 나 ORDER BY 같은 로직들은 MySQL 엔진의 `쿼리실행기`에서 일어난다.
  - **이 때문에 새로운 용도의 스토리지 엔진을 만든다고 쳐도 DBMS 전체가 아니라 일부분의 기능을 수행할 수 있는 엔진을 만들면 된다.**
- Handler 변수:
  - `Handler_` 로 시작하는 상태 변수
  - MySQL 엔진이 스토리지 엔진에 요청을 보낸 횟수를 의미
- 서버에 설치된 스토리지 엔진 목록을 보는 명령어:
```
SHOW ENGINES
```
  - `Support` 컬럼의 값의 의미:
    - YES: 서버(mysqld)에 스토리지 엔진이 포함되어있고 사용 가능한 상태임
    - DEFAULT: YES 와 동일한 상태 + 필수 스토리지 엔진이라 없으면 MySQL 서버가 시작하지 못할 수도 있음
    - NO: 현재 MySQL 서버에 포함되지 않았음
      - 사용하기 위해선 MySQL 서버를 다시 빌드/컴파일 해야함
    - DISABLED: 포함되어 있기는 한데 파라미터에 의해 비활성화된 상태
- 다운로드한 플러그인은 끼워 넣기만하면 사용이 가능하고 손쉽게 업그레이드도 가능
- 스토리지 엔진 외에도 다양한 기능이 플러그인의 형태로 제공됨
  - ex: 인증, 전문 검색 파서, 쿼리 재작성 등
- MySQL 서버의 기능을 커스텀하게 확장할 수 있게 플러그인 API가 매뉴얼에 공개되어 있어 구현에 참조 가능

### 4.1.5 컴포넌트 
- MySQL 8.0 부터 나온 플러그인을 대체하기 위한 컴포넌트 아키텍처로 아래 플러그인의 단점들을 보안한 구조이다.
- 플러그인의 단점:
  - 플러그인은 MySQL 서버와 상호작용하고 플러그인끼리는 통신이 불가함
  - 플러그인은 MySQL 서버의 변수나 함수를 직접 호출하기 때문에 안전하지 않음 (캡슐화의 부재)
  - 플러그인은 상호 의존 관계를 설정할 수 없어서 초기화가 어려움
- 컴포넌트 설치시 새로운 시스템 변수를 설정해야 할 수도 있기에 매뉴얼을 잘 참조해야한다.

### 4.1.6 쿼리 실행 구조 
흐름 (전체 흐름중 1번을 제외한 모든 내용은 MySQL 엔진 영역에서 일어남):
1. 사용자가 SQL 요청을 보냄
2. 쿼리 파서
   - 쿼리 파서는 쿼리 문장을 MySQL이 인식할 수 있는 최소 단위의 어휘나 기호 (토큰)으로 분리 -> 트리 형태의 구조로 만들어냄
   - 쿼리 문법 오류는 이 단계에서 발견되고 오류 메세지로 응답됨
   - 위 내용을 처리 후 전처리기로 전달 
3. 전처리기
   - 쿼리 파서가 만들어준 트리 구조를 기반으로 쿼리 문장에 문제점이 있는지 파악함
     - 테이블 이름이나 컬럼명 또는 내장 함수등과 같은 객체를 매핑해 존재 여부와 객체의 접근 권한 등을 확인.
     - 존재하지 않거나 권한이 없는 객체의 토큰이 이 단계에서 걸러지고 에러로 응답됨
4. 옵티마이저
   - 요청된 쿼리 문장을 저렴한 비용으로 가장 빠르게 처리할지를 담당.
     - 쿼리 변환
     - 비용 최적화
     - 실행 계획 수립
5. 쿼리 실행기 (실행 엔진)
   - 실행할 쿼리를 만들고 스토리지 엔진으로 전달한 후 종합해 응답하는 역할
     - 만들어진 계획을 가지고 핸들러에게 요청해 받은 결과를 또 다른 핸들러에 요청에 사용하고 최종응답을 만들어 넘기는 역할
   - ex: 옵티마이저가 GROUP BY의 처리를 위해 임시 테이블을 사용하기로 했다면 아래와 같은 일을 쿼리 실행기 (실행 엔진)이 실행함. (핸들러와 스토리지 엔진의 작업은 생략되어있음)
     1. 실행 엔진이 핸들러에게 임시 테이블을 만들라 요청
     2. 실행 엔진이 WHERE 절에 일치하는 레코드를 읽어오라고 핸들러에게 요청
     3. 읽어온 레코드들을 a에서 준비한 임시 테이블에 저장하라고 핸들러에 요청
     4. 데이터가 준비된 임시 테이블에서 필요한 방식으로 데이터를 읽어오라고 핸들러에 요청
     5. 결과물을 클라이언트로 전달
- Handler (스토리지 엔진)
  - 핸들러는 가장 밑단에서 MySQL 실행 엔진의 요구에 따라 데이터를 디스크로 저장하고 디스크로부터 읽어오는 역할을 한다
  - 즉 핸들러 == 스토리지 엔진을 의미함
  - 그렇기에 MyISAM로 생성된 테이블의 경우 핸들러가 MyISAM 스토리지 엔진이고, InnoDB로 생성된 테이블의 핸들러는 InnoDB 스토리지 엔진이 된다.

### 4.1.8 쿼리 캐시
- SQL 실행 결과를 메모리에 캐시하고, 동일 SQL 쿼리가 실행되면 테이블을 읽지 않고 즉시 결과를 반환하여 읽기 성능을 올리는 캐시 기능.
- 그러나 테이블의 데이터가 변경되면 캐시에 저장된 내용중 변경된 테이블과 관련된 데이터를 invalidate 해야하기에 심각한 동시처리 성능 저하를 유발함
  - 이 때문에 MySQL 서버가 발전하는 과정중 계속된 동시 처리 성능 저하와 버그의 원인이 되기도 했다.
    - 테이블의 데이터 변경이 거의 없는 환경에서는 좋은 성능을 보여주기는 하나, 이러한 환경은 흔지 않다.
      - 데이터 변경은 거의 없고 읽기만 하는 서비스
- MySQL 8.0 으로 올라오면서 쿼리 캐시는 MySQL 서버 기능에서 완전히 제거됨.

### 4.1.9 스레드 풀
- MySQL 엔터프라이즈 에디션에서만 제공되는 기능
- 스레드 풀은 내부적으로 사용자의 요청을 처리하는 스레드의 개수를 줄여서 동시에 처리되는 요청이 많더라도 서버의 CPU가 제한된 (적은) 수의 스레드 처리에만 집중할 수 있게 해 서버 리소스 소모를 줄이기 위한 목적으로 사용됨.
  - 적절히 CPU에게 요청을 보내 processor Affinity 를 높이고 컨텍스트 스위치를 줄여서 오버헤드를 낮출 수 있도록 하는 전략.
  - 그러나 스레드 풀이 눈에 띄는 성능 향상을 보여준 경우는 드물었다고 함
    - 오히려 스케쥴링 과정에서 CPU의 시간을 제대로 확보하지 못하는 경우 처리가 더 느려지는 사례도 있었다고 함.
- Percona Server 의 스레드 그룹 개수를 조절하는 시스템 변수: `thread_pool_size`
  - 일반적으로는 CPU 코어의 개수와 맞추는 것이 CPU 프로세서 친화도를 높이는데 좋다.
- 일반적인 상황에서 처리량을 올려주는 성능 향상 기능이라기보다, 과도한 동시성이 발생했을 때 성능이 붕괴하는 것을 막아주는 overload-control 기능에 가깝다는 듯 하다.

### 4.1.10 트랜잭션 지원 메타데이터
- 데이터베이스 서버에서 메타데이터(데이터 딕셔너리):
  - 테이블의 구조 정보와 스토어드 프로그램등의 정보.
- 5.7 버전까지는 테이블 구조를 FRM 파일에 저장하고 일부 스토어드 프로그램 또한 파일 (.TRN, .TRG, .PAR, etc) 기반으로 관리했음
  - 그러나 파일 기반의 경우 생성 및 변경 작업이 트랜잭션을 지원하지 않는 문제가 있음
    - 그로인해 테이블의 생성/변경 중에 MySQL 서버가 비정상적으로 종료되면 일관되지 않는 문제가 있었음.
      - 이 같은 현상을 `데이터베이스나 테이블이 깨졌다` 고 표현함
- 8.0 부터 위의 문제를 해결하기 위해 메타데이터를 InnoDB 테이블에 저장하도록 개선됨
- MySQL 서버가 동작하기 위해 필요한 테이블 = 시스템 테이블
  - 사용자 인증에 관련한 테이블 등이 있다.
  - 8.0 부터는 시스템 테이블들을 전부 InnoDB 가 관리하도록 개선됨

## 4.2 InnoDB 스토리지 엔진 아키텍처
- InnoDB는 MySQL에서 사용할 수 있는 스토리지 엔진중 거의 유일하게 레코드 기반의 락을 제공
  - 이로인해 동시성 처리량이 높다 -> 성능이 높고 안정적이다.

### 4.2.1 프라이머리 키에 의한 클러스터링
- InnoDB의 모든 테이블은 기본적으로 프라이머리 키를 기준으로 클러스터링되어 저장됨
  - 디스크에 PK 순서대로 저장된다.
  - 클러스터 키에 대해선 [8장](08.md)에서 다룰 예정.
- 세컨더리 인덱스들은 레코드 주소대신 PK 값을 논리 주소로 활용
- MyISAM 에서는 PK와 세컨더리 인덱스 간의 차이가 없다.

### 4.2.2 외래키 지원
- FK에 대한 지원은 InnoDB 스토리지 엔진 레벨에서 지원하는 기능으로 MyISAM이나 MEMORY 테이블에서는 사용할 수 없다.
- 운영에서는 잘 쓰이지 않는다.
  - 부모 자식 테이블 양쪽에 인덱스 생성이 필요하고, 양쪽에 데이터가 있는지 체크하는 작업이 필요해지기 때문에 락이 여러 테이블로 전파되며 데드락이 발생할 때가 많다.
    - 개발 환경에서도 위 상황은 주의해야한다 함

### 4.2.3 MVCC (Multi Version Concurrency Control)
- 레코드 레벨의 트랜잭션을 지원하기 위해 제공하는 기능
- 목적: 락을 사용하지 않는 일관된 읽기를 제공
  - InnoDB에선 Undo log를 이용해 이 기능을 구현.
- 하나의 레코드에 대해 여러 버전이 버퍼풀, 메모리, 디스크에 동시에 관리되고 격리 수준에 따라 어느 영역에 있는 데이터를 읽을지 결정해 리턴한다.
  - READ_UNCOMMITED: DB 버퍼풀에 있는 변경되었지만 커밋은 안된 데이터도 리턴
  - READ_COMMITTED 이상 (REPEATABLE_READ, SERIALIZABLE): 버퍼풀이 아닌 아직 언두 영역의 값을 리턴.

### 4.2.4 잠금 없는 일관된 읽기 (Non-Locking Consistent Read)
- MVCC를 이용해 격리 수준에 따라 잠금의 영향 없이 읽기를 수행.
  - ex: 수정된 row 을 읽을 때 
    - uncommited 는 버퍼에 있는 값을 그대로 읽음
    - commited 는 언두 로그를 이용해 수정 전 상태를 읽음

### 4.2.5 자동 데드락 감지
- 잠금 대기 그래프 (Wait-for-list): 교착 상태에 빠지지 않았는지 체크하는 그래프
- 데드락 감지 스레드에서 잠금 대기 그래프를 검사해 교착상태에 빠진 트랜잭션들을 찾아서 강제 종료.
  - 언두 로그의 양을 통해 어느 트랜잭션을 종료시킬지 판단함
    - 일반적으로는 더 적은 양의 트랜잭션을 종료 대상으로 취급
      - 롤백 대상이 적고, 강제 롤백으로 인한 서버 부담도 덜하기 때문
- InnoDB 스토리지 엔진에서는 상위의 MySQL 엔진의 락 (LOCK TABLE)은 감지할 수 없음
  - 이를 해결하려면 `innodb_table_locks` 시스템 변수를 활성화하면 감지가 가능해짐
    - 특별한 사유가 없다면 활성화하는 것이 좋다
- 동시 처리 스레드가 매우 많거나, 각 트랜잭션이 가진 락의 개수가 많아지면 데드락 감지 스레드의 작업이 느려지게 됨
  - 데드락 감지 스레드는 잠금 그래프에 대한 검사를 위해 잠금 테이블에 새로운 락을 걸고 데드락 스레드를 찾음 -> 느림을 해결하기 위해 새로운 느림이 만들어짐.
    - 이로인해 데드락 스레드가 느려지면 서비스 쿼리를 처리중인 스레드도 작업을 진행하지 못하게 되면서 대기하게 됨
    - 데이터베이스 서버의 CPU 사용량이 늘어남
  - 이런 악순환 문제를 해결하기 위해 제공하는 환경 변수: `innodb_deadlock_detect`
    - 이 값을 비활성화하면 데드락 감지 스레드가 없어짐 -> 두개 트랜잭션에서 동시에 하나의 레코드에 대한 락을 요구하게 되면 무한정 대기하게 되는 문제가 있음
      - `innodb_lock_wait_timeout` 설정을 걸면 일정 시간이 지나면 자동으로 요청이 실패하게 만들 수 있음
        - 초단위로 설정 가능. 기본값은 50초

### 4.2.6 자동화된 장애 복구
- InnoDB는 MySQL 서버가 기동할 때 자동으로 복구를 수행하고, 문제가 있다면 MySQL 서버를 강제 종료시킴
  - InnoDB는 짱짱 튼튼해서 앵간해서는 MySQL 서버가 못 뜨는 경우는 없으나, MySQL 서버와 무관하게 디스크나 서버 하드웨어 이슈 등 외부 요인으로 자동 복구가 불가한 경우는 존재함
- 이렇게 다시 MySQL 서버가 기동을 했다면, 덤프를 이용해 최대한 백업하고, 신규 인스턴스를 생성해 DB와 테이블을 재생성하는 것이 더 좋다.
- MySQL 서버가 기동하지 않는다면 `innodb_force_recovery` 설정을 이용해 데이터 파일이나 로그 파일의 손상 여부 검사를 선별적으로 진행하게해서 서버가 기동하게 만들 수 있다.
  - 디폴트인 0 이외의 값으로 떴다면, INSERT, UPDATE, DELETE 명령어는 사용이 불가능하다.
  - 데이터 파일의 손상 (에러로그에 `Database page corruption on disk..` 같은 메세지 출력) -> 1로 설정해 데이터 파일 복구만 우회
  - 로그 파일의 손상 -> 6으로 설정해 로그파일 복구만 우회
  - 뭐가 문젠지 모름 -> 1~6까지 바꿔보면서 테스트. 
    - 숫자가 커지면 커질수록 문제가 심각하다는 의미이고, 복구 가능성은 작아짐..
- 위 복구 방안을 다 해봤는데도 안된다면 백업을 이용해 그냥 다시 구축하는 것이 더 좋다.. 

### 4.2.7 InnoDB 버퍼 풀
- 디스크의 데이터 파일이나 인덱스 정보를 메모리에 캐시해 두는 공간.
- 쓰기를 지연시켜 일괄 작업으로 처리할 수 있게 해주는 버퍼 역할도 같이 함
  - 데이터 변경 작업은 랜덤 쓰기 작업인데, 이를 최소화 하기 위해 모아서 한번에 처리하게 만들어서 랜덤 디스크 작업 횟수를 줄이는 목적.

#### 4.2.7.1 버퍼 풀 크기 설정
- 5.7 전까지는 버퍼 풀 크기를 조절할 수 없었다.
- 이 크기는 운영체제와 각 클라 스레드가 사용할 메모리를 고려해 설정되어야 한다. 
  - 일반적으로 가능하면 적절히 작은 값으로 설정해 조금씩 상황을 봐가며 증가시키는게 최적.
- 처음으로 서비스 준비를 하는 단계라면, 운영체제 전체 메모리 공간이 8GB 미만이라면 50% 정도를 버퍼 풀로 설정
  - 8기가 이상이라면 전체의 50%에서 시작해 조금씩 올려가면서 최적점을 찾는 것을 권장.
- 5.7 이후부터는 `innodb_buffer_pool_size` 로 설정할 수 있고, 동적으로 변경이 가능함
  - 크리티컬한 변경이기에 되도록이면 MySQL 서버가 한가한 시점에 변경해야함
  - 늘리는 것은 영향도가 적으나 줄이는 것은 영향이 매우 큼
- 버퍼 풀은 128MB의 청크 단위로 관리됨
  - 128MB단위로 늘이고 줄이고가 처리된다.
- 버퍼 풀에 대한 접근을 관리하는 락 (세마포어) 때문에 내부 락 경합이 유발되었으나 개선되어 버퍼풀을 여러개로 쪼개어 관리할 수 있게 되었고, 버퍼풀에 대한 경합도 여러개로 분산되는 효과가 있었음
  - 버퍼 풀의 갯수는 `innodb_buffer_pool_instances` 로 조절 가능

#### 4.2.7.2 버퍼 풀의 구조
- 버퍼 풀을 관리하기 위해 페이지 크기(`innodb_page_size`)로 나눈 조각들에 데이터를 넣어두고, 아래 리스트들을 이용해 필요한 데이터를 사용함
- LRU (Least Recently Used) 리스트: 한번 읽어온 데이터를 메모리에 유지해 디스크 읽기를 최소화하기 위해 들고 있는 리스트
  - MRU (Most Recently Used) 리스트와 합친 개념으로 설명함
  - InnoDB 에서 데이터를 찾는 과정:
    - 버퍼 풀에 데이테가 이미 있는지 검사
      - 어댑티브 해시 인덱스를 이용해 데이터의 페이지 검색
      - 풀에 있던 데이터가 읽어지면 MRU리스트 최상단으로 올라가고, 점점 더 내려가다 LRU 리스트로 감
    - 버퍼 풀에 없으면 디스크에서 버퍼 풀로 데이터를 적재
      - LRU 헤더 부분에 가져온 데이터 추가
    - LRU의 데이터가 실제로 읽히게되면 MRU 헤더부분으로 이동
    - 사용자 쿼리가 얼마나 해당 데이터에 접근했느냐를 기준으로 AGE가 부여되고, 이 Age가 지나면 버퍼 풀에서 삭제
    - 필요 데이터가 자주 접근되었다면 메모리의 해당 페이지의 인덱스 키를 어댑티브 해시 인덱스에 추가해서 더 빨리 찾을 수 있게 수정
- 플러시(Flush) 리스트: 디스크에 동기화되지 않은 데이터를 가진 페이지(더티페이지)의 변경 시점 기준의 페이지 목록 
  - 디스크에서 읽힌 후 버퍼에서 변경되면 이 리스트에 포함되게되고, 시간이 지나면 디스크로 플러시됨
  - 리두 로그와 동일하게 반영되지만, 리두 로그가 디스크로 기록되었다고해서 데이터 페이지가 디스크로 기록됐다는게 보장되지는 않는다.
- 프리(Free) 리스트: 사용자 데이터로 대춰지지 않은 비어있는 페이지 목록

#### 4.2.7.3 버퍼 풀과 리두 로그
- 버퍼 풀은 DB 성능을 위해 데이터 캐시와 쓰기 버퍼링의 용도가 있다
  - 버퍼 풀의 메모리 공간 증설은 데이터 캐시 기능만 향상 시킴
  - 쓰기 성능은 어케 늘릴 수 있는가? -> 리두 로그와 버퍼풀의 관계를 이해해야함
- 버퍼 풀에는 디스크에서 읽은 깨끗한 데이터 (클린 페이지) 와 수정된 데이터 (더티 페이지)가 공존
- 더티 페이지는 디스크에 기록되어야 하고 버퍼 풀에서는 없어져야함
- 리두 로그는 변경 내역을 기록하는 고정 크기의 파일 묶음으로 공간 자체는 계속 순환되어 재사용된다
  - 일정 시간이 지나면 예전 로그는 덮어써짐
    - 당연히 아직 더티 페이지가 디스크에 작성되지 않은 경우에만 덮어쓰기가 가능
    - **더티 페이지가 있어 덮어 쓸 수 없는 공간을 활성 리두 로그 (Active Redo Log) 라고함**
  - 로그 포지션은 계속 증가된 값을 갖게 되고, 이게 LSN(Log Sequence Number)이다.
- InnoDB 엔진은 주기적으로 체크포인트를 발생시켜서 동기화하려함 
  - 이 떄 가장 최근 체크포인트 지점의 LSN이 기준점이 되어 안전하게 덮어 쓸 수 있는 기준점이 됨
- 체크포인트 에이지 = 마지막 로그 LSN - 최신 체크포인트 LSN
  - 아직 디스크에 기록되지 않은 변경 내역의 수
- 일반적으로 리두 로그는 변경분만 가지고 있고 버퍼 풀은 데이터 페이지를 통째로 가지고 있기 때문에 리두 로그는 그에 비해 훨씬 작은 공간만 있어도 된다.

#### 4.2.7.4 버퍼 풀 플러시 (Buffer Pool Flush)
- 5.6 버전까지는 더티 페이지 플러시 기능이 잘 안동작해서 문제가 많았다
  - 디스크 기록이 폭증해 MySQL 서버의 쿼리 처리 기능이 저하되는 등의 문제가 있었다.
  - 8.0 에서는 많이 개선되었음
- 위의 개선 떄문에 운영시 성능 문제가 발생하지 않는다면 굳이 아래 시스템 변수들에 대한 조정은 불필요하다
- 성능 향상을 이유로 백그라운드에서 2가지 플러시 기능이 수행됨:
  1. 플러시 리스트 플러시 (Flush_list flush)
     - 클리너 스레드라고 하는 더티 페이지를 동기화 시키는 스레드가 존재
       - `innodb_page_cleaners`로 스레드 수 조절 가능. `innodb_buffer_poos_instnaces`보다 클 수 없음 (자동으로 동일하게 변경함)
     - 이노디비는 기본적으로 버퍼 풀이 가진 페이지의 90%까지 더티 페이지를 가질 수 있다.
       - 상황에 따라 90%은 너무 과할 수 있다 -> `innodb_max_dirty_pages_pct` 로 변경 가능
       - 그러나 일반적으로는 쓰기 성능을 올리기 위해 기본값을 유지하는게 좋다고 함
     - 버퍼 풀에 더티 페이지가 많으면 많을 수록 디스크 쓰기 버스트가 발생할 확률이 높아짐.
       - `innodb_max_dirty_pages_lwm` 으로 버퍼 풀에 쓰여지는 비율을 더 높이거나 줄일 수 있다.
         - 기본값은 10%. 만약 더티 페이지의 비율이 얼마 안되는데 디스크 쓰기는 과한 상태라면 이 비율을 늘리는 것으로 디스크 쓰기 횟수를 줄이는 효과가 있다.
     - 그러나 어댑티브 플러시를 사용하면 버퍼 풀의 더티 비율이나 설정 값이 아니라 리두 로그의 증가 속도를 분석해 적절한 수의 더티페이지가 버퍼 풀에 유지되도록 디스크 쓰기를 실행함
       - 기본으로 켜져있고, `innodb_adaptive_flushing` 으로 끌 수 있음
       - `innodb_adaptive_flushing_lwm` 를 통해 비율 조정 가능. 기본은 10%.
  2. LRU 리스트 플러시 (LRU_list flush)
     - LRU 리스트에 있는 사용 빈도가 낮은 데이터 페이지들을 제거하고 새로운 페이지를 추가할 공간을 만드는 작업
     - `innodb_lru_scan_depth` 로 버퍼 풀 인스턴스별 스캔 횟수를 조절할 수 있음

#### 4.2.7.5 버퍼 풀 상태 백업 및 복구
- 버퍼 풀은 쿼리 성능과 아주 밀접하게 연관되어 있고, 잘 돌아가던 MySQL 서버를 셧다운하고 다시 시작하면 이전 성능의 1/10도 안나올 수도 있다고 한다.
  - 디스크 I/O 없이 버퍼풀의 데이터를 활용하기에 당연히 성능이 좋다 -> 재시작하면 버퍼 풀의 데이터는 다 날아갔을터
  - 이렇게 버퍼 풀에 데이터가 적재되어 있는 상태를 워밍업이라고 표현함
  - 5.5 버전까지는 강제 워밍업을 위해 주요 테이블과 인덱스에 풀 스캔을 진행하고 서비스를 오픈했었다고 함
- 5.6 버전부터 버퍼 풀 덤프 및 적재가 도입되며 재시작전에 시스템 변수 `innodb_buffer_pool_dump_now`를 명령어에 추가하면 현재 버퍼 풀을 백업해 뒀다가 재시동시 사용이 가능
  - 데이터의 페이지 메타 정보만 저장하기 때문에 저장된 파일의 용량은 작다. -> 백업도 빠르게 끝난다.
    - 다만 그 메타 정보만 가지고 다시 백업을 로드하는 시간은 오래걸릴 수도 있다. (디스크에서 다시 읽어야하기 때문에)
- 버퍼 풀 적재가 너무 오래 걸리면 `innodb_buffer_pool_load_abort` 로 중단시키기도 가능
- `innodb_buffer_pool_dump_at_shutdown` 을 적용하면 셧다운 시 자동으로 버퍼풀을 저장
- `innodb_buffer_pool_load_at_startup` 을 적용하면 뜰 때 자동으로 버퍼풀을 적재
  - 위 둘을 MySQL 설정 파일에 넣거나 실행 명령에 추가해도 된다.

#### 4.2.7.6 버퍼 풀에 적재 내용 확인
- 5.6 버전 부터 인포메이션 스키마의 innodb_buffer_pool 테이블을 이용해 버퍼 풀의 메모리에 어떤 테이블의 페이지들이 적재되어 있는지 확인이 가능했다.
  - 하지만 버퍼 풀이 큰 경우 이 테이블 조회가 상당히 큰 부하를 일으키면서 서비스 쿼리가 많이 느려지는 문제가 발생.
- 위 문제를 해결하기 위해 8.0에서는 인포메이션 스키마에 innodb_cached_indexes 라는 테이블이 추가됨
  - 인덱스별로 버퍼풀에 얼마나 적재돼 있는지 확인이 가능

#### 4.2.8 Double Write Buffer
- InnoDB 리두 로그는 공간 낭비를 위해 변경된 내용만 기록한다 
  - 하드웨어 오작동이나 시스템의 비정상 종료 등의 이유로 더티 페이지에서 디스크로 플러시할 때 일부만 저장되는 경우가 있을 수 있다.
- 위 문제를 해결하기 위해 Double Write 기법을 활용함.
- InnoDB 에서의 동작방식
  1. 변경된 더티 페이지를 묶어서 한번의 디스크 쓰기로 시스템 테이블 스페이스의 Double Write 버퍼에 기록
  2. 그리고 이노디비 스토리지 엔진은 더티 페이지를 파일의 적당한 위치에 랜덤쓰기를 실행.
- `innodb_doublewrite` 로 사용 여부를 제어
- 일반적으로 SSD를 쓰는 환경에서는 자주 사용되지 않을 수 있음.
  - 순차/랜덤 I/O의 비용차이가 크지 않아 한번의 순차 디스크로 쓰는게 오히려 부담
  - 그러나 무결성이 매우 중요한 서비스라면 DoubleWrite을 고려할 수 있다.

### 4.2.9 언두 로그
- 트랜잭션과 격리수준의 보장을 위해 DML 변경 이전 버전의 데이터를 별도로 백업하는데 이렇게 백업된 데이터를 언두 로그라고 부른다. 
- 사용 사례:
  - 트랜잭션 보장: 롤백될 때 언두 로그에 백업해둔 이전 데이터를 이용해 복구
  - 격리 수준 보장: 특정 커넥션에서 데이터를 변경하는 도중에 다른 커넥션에서 데이터를 조회하면 트랜잭션 격리 수준에 맞게 변경중인 레코드를 읽는게 아니라 언두로드에 백업된 데이터를 읽어서 반환
- 매우 중요한 피처에 사용되기에 중요하지만, 그렇기에 관리 비용도 크다

#### 4.2.9.1 언두 로그 모니터링
- 5.5 버전까지는 늘어나 버린 언두 로그 사용공간이 다시는 돌아가지 않았는데, 5.7 -> 8.0로 업그레이드되며 완전히 해소되었다 한다.
- 하지만 여전히 장기간 활성 상태로 남아있는 트랜잭션은 성능에 좋지 않다.
- 이를 확인하기 위해 인포메이션 스키마의 `innodb_metrics` 테이블을 활용해 모니터링이 가능하다.

#### 4.2.9.2 언두 테이블스페이스 관리
- 언두 테이블 스페이스 = 언두 로그가 저장되는 공간.
- 8.0 이상부터는 `innodb_undo_tablespaces` 명령어는 효력을 잃게되어 언두 로그는 항상 시스템 테이블 스페이스 외부의 별도 로그 파일에 저장되도록 변경됨.
- 하나의 언두 테이블 스페이스에는 1~128개의 롤백 세그먼트들이 존재하며, 각각 세그먼트는 1개 이상의 언두 슬롯을 가진다.
  - 롤백 세그먼트는 페이지 크기를 16 바이트로 나눈 값의 개수만큼의 언두 슬롯을 가진다. 
- 하나의 트랜잭션이 필요로하는 언두 슬롯은 그 트랜잭션에서 실행하는 INSERT, UPDATE, DELETE 문장의 특성에 따라 최대 4개 까지 언두 슬롯을 사용.
- 최대 동시 트랜잭션 수: innodb 페이지 크기 / 16 * (롤백 세그먼트 개수) * (언두 테이블 스페이스 개수)
- 일반적으로는 기본값을 유지해서 사용한다고 함
- `Undo tablespace truncate`: 이 언두로그의 필요 없어진 부분을 다시 운영체제로 반납 하는 것
  - 자동모드: InnoDB의 퍼지 스레드 (purge thread) 에서 주기적으로 불필요한 언두 테이블 스페이스에서 제거. (undo purge)
  - 수동 모드: `innodb_undo_log_truncate` 을 OFF로 설정하면 언두 로그의 잘라내기가 자동 실행되지 않음.
    - 주로 자동 모드로 실행했을 때 언두 테이블 스페이스 공간의 반납이 부진할 때 설정
    - 이게 꺼지면 퍼지 스레드에서 비활성 상태가 된 언두 테이블 스페이스의 불필요한 공간을 잘라내 운영체제로 반납
    - 반납이 완료되면 언두 테이블 스페이스를 다시 활성화 (자동 아님 유저가 명령어를 실행해야함)

### 4.2.10 체인지 버퍼
- INSERT/UPDATE 에는 데이터 파일의 변경뿐만 아니라 해당 테이블에 포함된 인덱스를 업데이트하는 작업도 필요함
  - 그런데 인덱스 업데이트도 랜덤 디스크 I/O라 테이블에 인덱스가 많으면 이 작업도 상당한 자원이 소모하게 됨
  - 그래서 버퍼 풀에 해당 인덱스가 있으면 바로 실행하지만, 없으면 write back 전략을 취함 -> 이 때 사용되는 공간이 체인지 버퍼
- 유니크 인덱스는 체인지 버퍼를 사용할 수 없다
  - 사용자에게 쿼리 결과를 전달하기 전에 반드시 중복 여부를 체크해야하기 때문.
- 이 또한 마찬가지로 체인지 버퍼 스레드에서 백그라운드에서 동작함
- 설정을 통해 어느 영역까지 체인지 버퍼에 둘지 설정할 수 있음
- 체인지 버퍼는 기본적으로 버퍼 풀로 설정된 메모리의 25%까지 사용이 가능함
  - 필요시 최대 50%까지 쓰도록 설정이 가능

### 4.2.11 리두 로그 및 로그 버퍼
- 리두 로그는 ACID의 D에 해당하는 영속성과 가장 밀접하게 연관됨.
- 하드웨어/소프트웨어 등 여러 가지 문제점으로 인해 MySQL 서버가 비정상 종료되었을 시 기록되지 못한 데이터를 잃지 않게 해주는 안전장치
- 데이터 변경은 읽기 성능을 고려한 데이터베이스의 자료 구조 특성상 보통 랜덤 액세스가 필요함
  - 변경 데이터를 바로 디스크에 기록하는 대신, 변경 내용을 리두 로그에 먼저 기록한 뒤 데이터 파일에 반영함
- MySQL 서버가 비정상 종료됐을 때 발생할 수 있는 경우:
  1. 커밋됐지만 데이터 파일에 기록되지 않은 데이터:
     - 리두 로그에 기록된 변경 내용을 데이터 파일에 다시 적용해 복구
  2. 롤백됐지만 데이터 파일에 이미 기록된 데이터:
     - 언두 로그를 이용해 변경 이전 상태로 되돌려야 함
     - 리두 로그는 해당 변경이 커밋, 롤백 또는 트랜잭션 실행 중 어느 상태였는지 확인하는 용도로 사용

- 리두 로그 크기 설정:
  - 리두 로그 전체 크기 = `innodb_log_file_size`(파일 크기) × `innodb_log_files_in_group`(파일 개수)
  - 리두 로그 크기는 버퍼 풀에서 더티 페이지를 얼마나 오래 유지하며 쓰기를 버퍼링할 수 있는지 결정하므로 중요함
    - 너무 작으면 체크포인트와 더티 페이지의 디스크 기록이 자주 발생해 쓰기 성능이 저하됨
    - 너무 크면 장애 발생 시 처리해야 할 로그가 많아져 복구 시간이 길어질 수 있음
    - 버퍼 풀 크기와 DBMS의 쓰기량, 장애 복구 목표 시간을 함께 고려해 적절한 크기로 설정
- 로그 버퍼(Log Buffer):
  - 트랜잭션의 변경 내용을 리두 로그 파일에 기록하기 전에 일시적으로 모아두는 메모리 공간
  - 변경 작업이 많은 서버에서 매번 리두 로그 파일에 기록하는 비용을 줄이면서도 ACID를 보장할 수 있는 수준으로 버퍼링함
  - `innodb_log_buffer_size`로 크기를 설정하며 기본값은 16MB
  - BLOB이나 TEXT처럼 큰 데이터를 자주 변경하거나 하나의 트랜잭션에서 많은 데이터를 처리한다면 더 크게 설정하는 것을 고려

#### 4.2.11.1 리두 로그 아카이빙
- MySQL 8.0부터 리두 로그를 별도 파일로 아카이빙할 수 있음
- MySQL Enterprise Backup이나 Xtrabackup 같은 백업 도구가 데이터 파일을 복사하는 동안 필요한 리두 로그가 덮어쓰이지 않도록 보호하는 기능
- 관련 설정 및 함수:
  - `innodb_redo_log_archive_dirs`: 리두 로그를 보관할 아카이빙 디렉터리 지정
  - `innodb_redo_log_archive_start(label, subdir)`: 지정한 디렉터리에서 리두 로그 아카이빙 시작
  - `innodb_redo_log_archive_stop()`: 진행 중인 리두 로그 아카이빙 종료
- 아카이빙을 시작한 세션의 연결이 끊기면 작업이 자동으로 중지되고 생성 중이던 아카이브 파일도 삭제됨

#### 4.2.11.2 리두 로그 활성화 및 비활성화
- 리두 로그는 장애 복구를 위해 기본적으로 항상 활성화되어 있음
- MySQL 8.0부터 리두 로그를 수동으로 활성화하거나 비활성화할 수 있음
  - 새 인스턴스에 백업 데이터를 복원하거나 대량 데이터를 적재할 때 일시적으로 비활성화하면 작업 시간을 단축할 수 있음

```sql
ALTER INSTANCE DISABLE INNODB REDO_LOG;

-- 대량 데이터 적재

ALTER INSTANCE ENABLE INNODB REDO_LOG;

-- 활성화 여부 확인
SHOW GLOBAL STATUS LIKE 'Innodb_redo_log_enabled';
```

- 주의점:
  - 리두 로그가 비활성화된 상태에서 서버가 비정상 종료되면 장애 복구가 불가능함
  - 데이터가 손상돼 서버가 기동되지 않을 수 있으며, 이 경우 `innodb_force_recovery=6` 설정이 필요할 수도 있음
  - 따라서 서비스 운영 중에는 리두 로그를 항상 활성화된 상태로 유지해야 함
  - 일부 데이터 손실을 감수하고 쓰기 성능을 높이려는 목적이라면 리두 로그를 비활성화하기보다 `innodb_flush_log_at_trx_commit`을 0이나 2로 설정하는 것이 더 안전함

### 4.2.12 어댑티브 해시 인덱스(Adaptive Hash Index)
- 일반 인덱스는 사용자가 생성한 B-Tree 인덱스를 의미하지만, 어댑티브 해시 인덱스(AHI)는 InnoDB가 자주 조회되는 키를 자동으로 해시 형태로 관리하는 기능
- `innodb_adaptive_hash_index` 시스템 변수로 활성화하거나 비활성화할 수 있음
- 동작 방식:
  1. InnoDB가 B-Tree 인덱스에서 자주 조회되는 키를 관찰
  2. 인덱스 ID와 실제 키를 조합한 값을 버퍼 풀에 있는 데이터 페이지의 메모리 주소와 매핑해 해시 테이블에 저장
  3. 같은 키가 다시 조회되면 B-Tree의 루트, 브랜치, 리프 노드를 탐색하지 않고 해당 페이지에 바로 접근
- AHI 엔트리는 대상 페이지가 버퍼 풀에 있을 때만 유지됨
  - 페이지가 버퍼 풀에서 제거되면 관련 AHI 엔트리도 함께 제거됨
- 장점:
  - B-Tree 탐색을 생략해 CPU 사용량을 줄일 수 있음
  - B-Tree 내부 잠금(세마포어) 경합을 줄일 수 있음
  - 동등 비교나 IN 조건으로 같은 키를 반복 조회하는 워크로드에서 TPS와 QPS가 향상될 수 있음
- 효과적인 경우:
  - 데이터 대부분이 버퍼 풀에 있어 디스크 읽기가 많지 않은 경우
  - 동등 비교나 IN 조건이 많은 경우
  - 데이터 접근이 일부 핫 세트에 집중되는 경우
- 효과가 크지 않은 경우:
  - 버퍼 풀 미스가 잦아 디스크 읽기 비중이 큰 경우
  - 조인이나 LIKE 패턴 검색처럼 키 탐색 패턴이 다양한 경우
  - 매우 큰 테이블을 넓은 범위로 스캔하는 경우
- **AHI는 메모리에 적재된 페이지에 더 빠르게 접근하기 위한 가속기이며, 디스크 I/O 자체를 줄여주는 기능은 아님**
- 비용 및 주의점:
  - AHI 엔트리를 관리하기 위한 메모리가 추가로 필요함
  - AHI가 활성화되어 있으면 조회할 때 해시 인덱스도 확인하므로 히트율이 낮다면 불필요한 오버헤드가 발생할 수 있음
  - DROP이나 ALTER를 실행하면 해당 테이블의 AHI 엔트리를 제거해야 하므로 CPU 사용량이 증가하고 DDL 실행이 지연될 수 있음
    - INSTANT DDL도 영향을 받을 수 있음
- 설정 및 튜닝:
  - `innodb_adaptive_hash_index`: AHI 활성화 및 비활성화
    - 효과가 없거나 DDL 지연이 문제가 된다면 비활성화를 고려
  - `innodb_adaptive_hash_index_parts`: AHI 파티션 수 설정
    - 기본값은 8이며, AHI 내부 잠금 경합이 심하다면 파티션 수를 늘려 경합을 분산할 수 있음
- 상태 확인:
  ```sql
  SHOW ENGINE INNODB STATUS
  ```
  - `X.xx hash searches/s`: 초당 AHI를 이용한 검색 수
  - `Y.yy non-hash searches/s`: 초당 AHI를 이용하지 못하고 B-Tree를 탐색한 검색 수
  - `hash / (hash + non-hash)` 비율과 CPU 및 메모리 사용량을 함께 확인해 활성화 여부를 판단
- 메모리 사용량 확인:
  ```sql
  SELECT EVENT_NAME, CURRENT_NUMBER_OF_BYTES_USED
  FROM performance_schema.memory_summary_global_by_event_name
  WHERE EVENT_NAME = 'memory/innodb/adaptive hash index';
  ```
- 판단 기준:
  - AHI 사용 비율이 의미 있게 높고 CPU 사용량 절감 효과가 있다면 활성화 상태를 유지
  - AHI 내부 잠금 경합이 관찰된다면 `innodb_adaptive_hash_index_parts` 값을 늘리는 것을 고려
  - 사용 비율은 낮은데 CPU나 메모리 사용량이 크다면 비활성화하고 해당 메모리를 버퍼 풀에 할당하는 것을 고려
  - 대형 DDL이나 DROP을 자주 실행한다면 비활성화해 작업 시간의 변동을 줄이는 것을 고려

### 4.2.13 InnoDB와 MyISAM, MEMORY 스토리지 엔진 비교
- MySQL의 기본 스토리지 엔진은 시대에 따라 달라졌지만, 현재는 InnoDB가 사실상 대부분의 역할을 담당함

- InnoDB:
  - MySQL 5.5부터 기본 스토리지 엔진으로 사용됨
  - MySQL 8.0부터 시스템 테이블도 모두 InnoDB로 변경됨
  - 트랜잭션, MVCC, 외래 키를 지원해 안정성과 동시성 처리에 강점이 있음
  - 읽기와 쓰기 모두 안정적이며 대규모 트랜잭션 처리에 적합함
  - 과거 MyISAM에서만 지원하던 전문 검색과 공간 좌표 검색도 지원함
  - 따라서 특별한 이유가 없다면 MySQL에서는 InnoDB를 기본 선택지로 사용
- MyISAM:
  - MySQL 5.1 이하 버전에서 기본 스토리지 엔진으로 사용됨
  - 단순한 구조와 빠른 읽기 성능이 장점이었음
  - 트랜잭션을 지원하지 않으며 테이블 단위 잠금을 사용해 동시성 처리에 취약함
  - MySQL 8.0 이후 신규 시스템에서 선택할 이유가 거의 없으며 주로 레거시 호환 목적으로 사용됨
- MEMORY:
  - 데이터를 모두 메모리에 저장하므로 단일 스레드 처리 성능이 빠름
  - 테이블 단위 잠금을 사용해 동시성 처리 성능이 낮음
  - MySQL 5.7까지 내부 임시 테이블 용도로 사용됐지만, MySQL 8.0부터는 TempTable 엔진이 기본 역할을 대신함
  - 따라서 현재는 레거시 호환이나 제한적인 특수 용도를 제외하면 선택할 이유가 거의 없음

## 4.3 MyISAM 스토리지 엔진 아키텍처

### 4.3.1 키 캐시
- InnoDB의 버퍼 풀과 비슷하게 인덱스를 메모리에 캐시하는 역할을 함
  - 버퍼 풀과 달리 **인덱스만 캐시**하며, 데이터는 캐시하지 않음
  - 디스크 쓰기에 대해서도 부분적인 버퍼링 역할만 수행함
- 키 캐시의 효율은 다음 히트율로 간단히 확인할 수 있음
  - `Key_reads`: 디스크에서 인덱스를 직접 읽은 횟수
  - `Key_read_requests`: 키 캐시에서 인덱스를 읽도록 요청한 횟수 
  - 키 캐시 히트율(%) = 100 - (Key_reads / Key_read_requests * 100)

- 일반적으로 키 캐시 히트율은 99% 이상을 유지하도록 권장함
  - 99% 미만이라면 `key_buffer_size`를 늘리는 것을 고려할 수 있음
  - 단, MyISAM은 데이터 캐시를 운영체제에 의존하므로 키 캐시에 메모리를 과도하게 할당하면 안 됨
- 운영체제별 키 캐시 크기 제한:
  - 32비트 운영체제: 하나의 키 캐시는 최대 4GB까지 설정 가능
  - 64비트 운영체제: `OS_PER_PROCESS_LIMIT` 값까지 설정 가능
- 하나의 키 캐시 제한보다 더 큰 공간이 필요하다면 기본 키 캐시 외에 **명명된 키 캐시(Named Key Cache)**를 추가할 수 있음
  - `key_buffer_size`: 모든 MyISAM 테이블이 기본으로 사용하는 키 캐시
  - `kbuf_board`, `kbuf_comment`: 각각 2GB를 할당받은 별도의 키 캐시
  - 명명된 키 캐시는 생성만 해서는 사용되지 않으며, 캐시할 테이블의 인덱스를 명시적으로 지정해야 함
  - `board` 테이블의 인덱스는 `kbuf_board`를 사용
  - `comment` 테이블의 인덱스는 `kbuf_comment`를 사용

### 4.3.2 운영체제의 캐시 및 버퍼
- MyISAM의 키 캐시는 인덱스만 캐시하므로 데이터 읽기와 쓰기는 운영체제의 디스크 I/O에 의존함
- 대부분의 운영체제는 남는 메모리를 파일 캐시와 쓰기 버퍼로 활용함
  - 한 번 읽은 파일을 다시 읽을 때 디스크가 아니라 메모리에서 데이터를 반환할 수 있음
  - 쓰기 작업도 운영체제의 버퍼를 거쳐 처리될 수 있음
- 운영체제 캐시는 InnoDB 버퍼 풀처럼 데이터베이스의 데이터 특성을 고려해 동작하는 지능적인 캐시는 아님
- 운영체제 캐시의 기본 원칙은 **애플리케이션이 사용하지 않는 남는 메모리를 활용하는 것**임
  - 전체 메모리를 MySQL이나 다른 애플리케이션이 모두 사용하면 운영체제가 파일 캐시를 확보할 수 없음
  - 이 경우 MyISAM 데이터 파일을 매번 디스크에서 읽게 되어 성능이 저하될 수 있음
- MyISAM을 주로 사용하는 서버에서는 키 캐시를 전체 메모리의 40% 이하로 설정하는 것을 권장함
  - 남은 메모리를 운영체제의 데이터 파일 캐시로 사용할 수 있도록 적절히 비워둬야 함

### 4.3.3 데이터 파일과 프라이머리 키(인덱스) 구조
- InnoDB와 MyISAM의 데이터 저장 방식:
  - InnoDB: 프라이머리 키를 기준으로 클러스터링되어 레코드가 PK 순서대로 저장됨
  - MyISAM: 클러스터링 없이 레코드가 INSERT된 순서대로 힙(Heap)처럼 저장됨
- MyISAM 테이블의 모든 레코드는 물리적인 위치를 나타내는 `ROWID`를 가짐
  - 데이터 파일(`.MYD`): 실제 레코드를 저장
  - 인덱스 파일(`.MYI`): 인덱스 키와 해당 레코드의 `ROWID`를 저장
  - `ROWID`는 데이터 파일 안에서 레코드가 저장된 위치(offset)를 의미함
- 프라이머리 키와 세컨더리 인덱스의 구조에 차이가 없음
  - 두 인덱스 모두 실제 데이터 대신 데이터 파일에 저장된 레코드의 `ROWID`를 포인터로 가짐

- MyISAM의 `ROWID` 저장 방식은 다음 두 가지로 나뉨
  1. 고정 길이 `ROWID`
     - 테이블을 생성할 때 `MAX_ROWS` 옵션을 지정하면 사용됨
     - 테이블이 가질 수 있는 최대 레코드 수가 정해짐
     - `ROWID`로 INSERT된 순번에 해당하는 4바이트 정수를 사용함
  2. 가변 길이 `ROWID` (기본값)
     - `MAX_ROWS` 옵션을 지정하지 않으면 `myisam_data_pointer_size` 시스템 변수의 값을 사용함
     - 기본값은 7바이트이며 `ROWID`는 2~7바이트의 가변 길이로 저장됨
       - 첫 1바이트에는 길이 정보, 나머지 바이트에는 실제 주소가 저장됨
     - 기본 설정에서 MyISAM 테이블의 최대 크기는 256TB
     - 256TB보다 큰 데이터 파일이 필요하다면 `myisam_data_pointer_size=8`로 설정해 최대 64PB까지 확장할 수 있음

## 4.4 MySQL 로그 파일
- MySQL 서버의 상태나 부하 원인을 진단할 때 로그 파일은 가장 기본적인 점검 대상임
- 서버 내부 구조를 모두 알지 못하더라도 로그를 통해 문제의 원인을 상당 부분 파악할 수 있으므로 문제가 발생하면 습관적으로 확인하는 것이 좋음

### 4.4.1 에러 로그 파일
- MySQL 서버가 실행되는 동안 발생한 정보, 경고, 에러 메시지를 기록함
- 에러 로그 파일의 위치:
  - `my.cnf`의 `log_error` 파라미터에 지정된 경로
  - 별도로 지정하지 않으면 데이터 디렉터리(`datadir`)에 `.err` 확장자의 파일로 생성됨

#### 4.4.1.1 MySQL 시작 과정의 정보 및 에러 메시지
- 설정을 변경했거나 서버가 비정상 종료된 뒤 재기동했다면 에러 로그에서 정상 기동과 설정 적용 여부를 확인해야 함
- 정상적으로 기동되면 일반적으로 다음 메시지가 기록됨

```
mysqld: ready for connections
```

- 새로 추가하거나 변경한 파라미터와 관련된 오류 및 경고가 없는지 확인해야 함
  - `ignored`: 서버는 기동됐지만 해당 설정은 적용되지 않은 상태
  - 알 수 없는 변수나 잘못된 값: 에러를 출력하고 서버 기동이 실패할 수 있음

#### 4.4.1.2 비정상 종료 후 InnoDB 트랜잭션 복구 메시지
- MySQL 서버가 비정상 또는 강제 종료된 뒤 재시작되면 InnoDB가 자동 복구를 수행함
  - 완료되지 않은 트랜잭션을 정리
  - 데이터 파일에 기록되지 않은 변경 내용을 재처리
- 자동 복구에 실패하면 관련 메시지가 에러 로그에 기록되고 MySQL 서버가 다시 종료될 수 있음
- 데이터 파일이 심각하게 손상되어 정상 기동할 수 없다면 `innodb_force_recovery`를 일시적으로 사용할 수 있음

```
innodb_force_recovery = 1
```

  - 1부터 6까지 단계별로 설정할 수 있으며, 필요한 최소 단계부터 적용해야 함
  - 값이 커질수록 기능 제한과 데이터 손실 위험이 증가함
  - 서버를 기동한 뒤 데이터를 백업하거나 덤프하고 정상 서버로 복구하기 위한 최후의 수단임

#### 4.4.1.3 쿼리 처리 중 발생한 문제 메시지
- 쿼리 실행 중 발생하는 오류는 사전에 발견하기 어려워 에러 로그를 주기적으로 점검해야 알 수 있는 경우가 많음
- 주로 다음 내용이 기록됨
  - 쿼리 실행 중 발생한 에러
  - 복제(Replication)에서 문제를 일으킬 수 있는 쿼리에 대한 경고
- 정기적으로 확인하면 잠재적인 성능 문제나 데이터 문제를 조기에 발견할 수 있음

#### 4.4.1.4 비정상적으로 종료된 커넥션 메시지(Aborted connection)
- 클라이언트 애플리케이션이 연결을 정상적으로 종료하지 못하고 종료된 경우 주로 기록됨
- 네트워크 문제로 의도하지 않게 연결이 끊어진 경우에도 발생함
- 메시지가 지나치게 많이 기록된다면 다음 사항을 확인해야 함
  - 애플리케이션의 커넥션 종료 로직
  - 클라이언트와 MySQL 서버 사이의 네트워크 상태
- `max_connect_errors` 값이 너무 작으면 특정 클라이언트가 서버에 접속하지 못할 수 있음

```
Host 'hostname' is blocked
```

  - 클라이언트 호스트에서 발생한 접속 실패나 강제 연결 종료 횟수가 `max_connect_errors`를 넘으면 해당 호스트의 접속이 차단됨
  - 필요하다면 값을 늘릴 수 있지만, 먼저 접속 오류가 반복된 원인을 확인해야 함

#### 4.4.1.5 InnoDB 모니터링 및 상태 조회 결과 메시지
- InnoDB 테이블 모니터링, 락 모니터링, `SHOW ENGINE INNODB STATUS`와 같은 상태 조회 결과는 비교적 큰 메시지를 에러 로그에 기록할 수 있음
- 모니터링을 계속 활성화해두면 에러 로그가 매우 커져 파일 시스템의 공간을 소진할 수 있음
  - 필요한 진단이 끝나면 반드시 모니터링을 비활성화해야 함

#### 4.4.1.6 MySQL 종료 메시지
- MySQL 서버가 예기치 않게 종료되거나 재시작됐다면 에러 로그의 마지막 종료 메시지를 확인해야 함
- 사용자가 정상적으로 종료한 경우 `Received SHUTDOWN from user '...'` 와 같은 메시지가 기록됨
- 종료 메시지가 없거나 16진수 주소가 포함된 스택 트레이스가 출력됐다면 세그멘테이션 폴트(Segmentation fault)로 비정상 종료됐을 가능성이 높음
  - 스택 트레이스를 기준으로 알려진 MySQL 버그인지 확인
  - 관련 버그라면 버전 업그레이드 또는 회피책(Workaround)을 검토

### 4.4.2 제너럴 쿼리 로그 파일(General Log)
- MySQL 서버가 받은 모든 쿼리의 전체 목록을 시간 순서대로 검토할 때 사용함
- 슬로우 쿼리 로그와 달리 쿼리 실행이 끝난 뒤가 아니라 **서버가 요청을 받는 즉시 기록**함
  - 쿼리 실행 중 에러가 발생해도 요청 자체는 로그에 남음
- 로그 파일 상단에는 다음과 같은 서버 정보가 출력될 수 있음
  - `mysqld` 실행 경로와 버전, TCP 포트, Unix 소켓 경로
- `general_log_file` 파라미터로 로그 파일 경로를 설정할 수 있음
- `log_output` 파라미터로 로그 저장 대상을 결정함
  - `FILE`: 디스크의 로그 파일에 저장
  - `TABLE`: MySQL 시스템 테이블에 저장하며 SQL로 조회해 검토

### 4.4.3 슬로우 쿼리 로그
- 쿼리 튜닝 시 운영 환경에서 성능 저하를 일으키는 쿼리를 찾는 데 사용함
  - 서비스 적용 전에는 전체 쿼리를 대상으로 튜닝할 수 있음
  - 운영 중에는 문제 쿼리를 바로 식별하기 어려우므로 슬로우 쿼리 로그가 중요한 단서가 됨
- `long_query_time` 이상 실행된 쿼리를 기록함
  - 쿼리가 종료된 뒤 실제 실행 시간을 기준으로 기록 여부를 판단함
  - 정상적으로 실행이 완료된 쿼리만 기록됨
- `log_output`으로 저장 대상을 선택할 수 있음
  - `FILE`: 디스크의 로그 파일에 저장
  - `TABLE`: `mysql.general_log`, `mysql.slow_log` 테이블에 저장
    - 두 테이블은 CSV 스토리지 엔진을 사용하므로 실질적으로 CSV 파일에 저장하는 것과 비슷하게 동작함
- 슬로우 쿼리 로그의 주요 항목:
  - `Time`: 쿼리가 종료된 시각. 시작 시각은 `Time - Query_time`으로 계산 가능
  - `Query_time`: 쿼리 전체 실행 시간
  - `Lock_time`: MySQL 엔진 레벨의 테이블 잠금 대기 시간
    - 잠금 확인 등의 오버헤드가 포함될 수 있어 매우 작은 값은 무시해도 됨
  - `Rows_examined`: 쿼리 처리를 위해 접근한 레코드 수
  - `Rows_sent`: 클라이언트에 결과로 보낸 레코드 수
- MySQL의 잠금은 MySQL 엔진과 스토리지 엔진의 두 레이어에서 처리됨
  - MyISAM/MEMORY: 테이블 단위 잠금을 사용하고 MVCC를 지원하지 않아 `SELECT`의 `Lock_time`도 1초 이상일 수 있음
  - InnoDB: 레코드 단위 잠금을 사용하지만 MySQL 엔진 레벨의 테이블 잠금 영향으로 `Lock_time`이 크게 나타날 수 있음
  - 슬로우 로그의 `Lock_time`은 InnoDB 스토리지 엔진 내부의 레코드 잠금 대기 시간을 보여주지 않으므로 InnoDB 쿼리 분석에는 유용성이 낮을 수 있음
- 로그의 양이 많으면 사람이 직접 분석하기 어려우므로 Percona Toolkit의 `pt-query-digest`를 사용할 수 있음

#### 4.4.3.1 슬로우 쿼리 통계
- 보고서의 최상단에서 전체 쿼리에 대한 요약 통계를 보여줌
  - 실행 시간(`Exec time`)과 잠금 대기 시간(`Lock time`)의 평균, 최소, 최대
  - 로그 수집 기간(`Time range`)
  - 유니크 쿼리 수
  - QPS와 동시성

#### 4.4.3.2 실행 빈도 및 누적 시간 랭킹
- 쿼리별 응답 시간 합계 또는 실행 횟수를 기준으로 랭킹을 보여줌
  - `--order-by` 옵션으로 정렬 기준을 변경할 수 있음
- `Query ID`는 쿼리에서 리터럴 값을 제거해 정규화한 뒤 생성한 해시값임
  - 값만 다르고 형태가 같은 쿼리는 같은 `Query ID`로 묶임

#### 4.4.3.3 쿼리별 실행 횟수 및 누적 실행 시간 상세 정보
- 랭킹 순서대로 각 `Query ID`의 상세 분석 결과를 보여줌
- 주요 정보:
  - 쿼리 실행 횟수와 누적 응답 시간
  - 응답 시간 분포 히스토그램
  - `Rows sent`, `Rows examined`
  - 표본 쿼리의 `EXPLAIN`
  - 관련 테이블의 메타데이터
- 랭킹 영역에서는 어떤 테이블을 대상으로 한 쿼리인지 빠르게 파악하고, 상세 영역에서는 실제 쿼리와 실행 특성을 확인할 수 있음
