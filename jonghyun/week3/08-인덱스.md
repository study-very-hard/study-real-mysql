# **Ch.8 인덱스**

- 인덱스는 쿼리 성능 얘기에서 빼놓을 수 없는 부분
  - 쿼리 개발/튜닝을 보기 전에, MySQL에서 쓸 수 있는 인덱스의 종류와 특성을 먼저 살펴보는 챕터
  - 각 인덱스의 특성과 차이는 물리적으로 모델링할 때도 중요한 요소
- MySQL 8.0까지 오면서 상용 RDBMS의 기능을 많이 지원하게 됨
  - MyISAM에서만 되던 전문 검색, 위치 기반 검색도 이제 InnoDB에서 사용 가능

## **8.1 디스크 읽기 방식**

- 인덱스 전용 용어는 아니지만, 이 장에서 계속 나오는 "랜덤 I/O", "순차 I/O"부터 정리
- CPU, 메모리 같은 전기적 장치는 엄청 빨라졌지만 디스크 같은 기계식 장치는 발전이 제한적이었음
  - SSD가 많이 쓰여도 여전히 저장 매체는 컴퓨터에서 가장 느린 부분
  - 결국 DB 성능 튜닝은 **디스크 I/O를 얼마나 줄이느냐**가 관건인 경우가 많음

### **8.1.1 하드 디스크 드라이브(HDD)와 솔리드 스테이트 드라이브(SSD)**

- HDD는 기계식 장치라 DB 서버에서는 항상 디스크가 병목이 됨
- SSD(Solid State Drive): 플래터(원판) 대신 플래시 메모리를 장착한 저장 매체
  - 원판을 회전시킬 필요가 없어서 아주 빠름. D-RAM보다는 느리지만 HDD보다는 훨씬 빠름
  - 기존 HDD와 같은 인터페이스(SATA, SAS)라 그대로 쓸 수 있음
- 메모리와 디스크는 10만 배 이상, 메모리와 SSD는 1000배 가량 차이 (그림 8.1)
- 순차 I/O에서는 SSD가 HDD보다 조금 빠르거나 비슷한 수준
  - **SSD의 진짜 장점은 랜덤 I/O가 훨씬 빠르다는 것**
  - DB 서버는 순차 I/O보다 작은 데이터를 랜덤 I/O로 읽고 쓰는 작업이 대부분이라 SSD가 DBMS용 스토리지로 최적

### **8.1.2 랜덤 I/O와 순차 I/O**

- 랜덤 I/O: 하드 디스크 드라이브 플래터를 돌려 읽을 데이터가 있는 위치로 디스크 헤더를 옮긴 다음 데이터를 읽는 것
  - 사실 순차 I/O도 이 과정 자체는 같음. 차이는 헤더를 몇 번 움직이느냐
- 3개의 페이지(3 x 16KB)를 기록할 때 순차 I/O는 시스템 콜 1번(헤드 1번 이동), 랜덤 I/O는 3번(헤드 3번 이동)
  - 시간은 헤더를 움직이는 단계에서 결정되므로 이 경우 순차 I/O가 약 3배 빠름
- 결국 디스크 성능은 **헤더 이동 없이 한 번에 얼마나 많은 데이터를 기록하느냐**로 결정됨
  - 그래서 MySQL에는 그룹 커밋, 바이너리 로그 버퍼, InnoDB 로그 버퍼 같은 기능이 내장돼 있음
- SSD에서도 랜덤 I/O는 순차 I/O보다 처리량이 떨어짐.
  - SSD 스펙에도 둘을 구분해서 적어둠
- 순차 I/O도 파일 동기화(fsync)가 잦으면 랜덤 I/O처럼 비효율적으로 처리됨
  - 캐시 메모리가 달린 RAID 컨트롤러가 이걸 효율적으로 바꿔줌.
  - SSD를 써도 RAID 컨트롤러 캐시 성능은 중요하다.
- 쿼리 튜닝으로 랜덤 I/O를 순차 I/O로 바꿀 방법은 많지 않음
  - 튜닝의 목적은 **랜덤 I/O 자체를 줄이는 것** = 꼭 필요한 데이터만 읽도록 쿼리를 개선하는 것
- 인덱스 레인지 스캔은 주로 랜덤 I/O, 풀 테이블 스캔은 순차 I/O
  - 큰 테이블의 대부분을 읽어야 하면 일부러 풀 테이블 스캔을 유도하기도 함 (DW, 통계 작업에서 자주)

## **8.2 인덱스란?**

- 비유: 책 맨 끝의 찾아보기(색인)
  - 찾아보기 = 인덱스, 책의 내용 = 데이터 파일, 페이지 번호 = 레코드 주소
  - 칼럼 값과 레코드 주소를 key-value 쌍으로 묶어 인덱스를 만들어 두는 것
  - **즉 정렬**. 찾아보기가 ㄱ, ㄴ, ㄷ 순서로 정렬된 것처럼 인덱스도 칼럼 값을 미리 정렬해서 보관
- 인덱스는 SortedList(항상 정렬 유지)와 같고 데이터 파일은 ArrayList(저장 순서 그대로)와 같다
- SortedList의 장단점이 곧 인덱스의 장단점
  - 저장할 때마다 정렬해야 하니 저장은 복잡하고 느림 → 인덱스가 많으면 INSERT/UPDATE/DELETE가 느려짐
  - 이미 정렬돼 있으니 찾는 건 아주 빠름 → SELECT가 빨라짐
- **인덱스는 저장(INSERT, UPDATE, DELETE) 성능을 희생하고 읽기 속도를 높이는 기능**
  - WHERE 절에 나온 칼럼이라고 전부 인덱스를 만들면 저장 성능이 떨어지고 인덱스만 비대해져 역효과가 날 수 있다.
- 이 책에서는 키(Key)와 인덱스(Index)를 같은 의미로 사용
- 역할별 분류:
  - 프라이머리 키(Primary Key): 레코드를 대표하는 칼럼(조합) 값으로 만든 인덱스. 식별자라고도 함.
  - 세컨더리 인덱스(Secondary Index): PK를 제외한 나머지 모든 인덱스
    - 유니크 인덱스는 PK를 대체할 수 있어 대체 키라고도 함
- 대표적인 데이터 저장 방식(알고리즘)별 분류:
  - B-Tree 인덱스: 가장 일반적이고 오래된, 그만큼 성숙한 알고리즘
    - 칼럼 값을 변형하지 않고 원래 값으로 인덱싱
    - R-Tree(위치 기반 검색용)도 결국 B-Tree의 응용
  - Hash 인덱스: 칼럼 값으로 해시값을 계산해 인덱싱, 매우 빠른 검색
    - 값을 변형하므로 전방(Prefix) 일치나 범위 검색에는 못 씀
    - 주로 메모리 기반 DB에서 사용
  - 외에도 최근에는 Fractal-Tree 인덱스나 로그 기반 Merge-Tree 인덱스와 같은 알고리즘을 사용하는 DB도 개발이 되고있다.
- 중복 허용 여부 분류: 유니크 인덱스(Unique) / 유니크하지 않은 인덱스(Non-Unique)
  - 옵티마이저에게는 중요한 차이. 유니크 인덱스에 동등 조건(Equal, =)이면 1건만 찾으면 끝이라는 걸 옵티마이저가 알 수 있음
- 기능별 분류: 전문 검색용, 공간 검색용 인덱스 등
  - 더 분류할 수 있지만 MySQL을 사용할 때는 이 두가지로 충분하다 함.
  - 뒤에서 더 파볼 예정.

## **8.3 B-Tree 인덱스**

- 가장 먼저 도입됐고 여전히 가장 범용적으로 쓰이는 인덱스 알고리즘
  - 보통 DBMS에서는 변형인 B+-Tree나 B*-Tree를 사용
- B-Tree의 "B"는 Binary(이진)가 아니라 Balanced의 약자
  - 인터넷 그림 때문에 이진 트리로 오해하는 사람이 많다고 함
- 칼럼의 원래 값을 변형하지 않고(앞부분만 잘라서 관리하긴 함) 항상 정렬된 상태로 유지
  - 전문 검색 같은 특수 요건이 아니면 대부분 B-Tree를 씀

### **8.3.1 구조 및 특성**

- 노드 구성: 루트 노드(최상위), 브랜치 노드(중간), 리프 노드(최하위)
  - 리프 노드는 **실제 데이터 레코드를 찾아가기 위한 주솟값**을 가짐 (인덱스엔 키 칼럼만 있으니까)
- 인덱스 키 값은 정렬돼 있지만 데이터 파일의 레코드는 정렬돼 있지 않음
  - INSERT 순서대로도 아님. 삭제로 생긴 빈 공간을 다음 INSERT가 재활용하기 때문
- 단, InnoDB는 레코드가 클러스터되어 기본적으로 **PK 순서로 정렬되어 저장됨**
  - 오라클의 IOT, MS-SQL의 클러스터 테이블과 같은 구조. InnoDB는 디폴트로 클러스터링 테이블
- MyISAM과 InnoDB의 차이 (세컨더리 인덱스로 레코드를 찾아가는 방법):
  - MyISAM: 세컨더리 인덱스가 **물리적인 주소**를 가짐
    - 레코드 주소 = 테이블 생성 옵션에 따라 INSERT된 순번이거나 데이터 파일 내 위치(Offset)
  - InnoDB: PK가 ROWID 역할을 함. 세컨더리 인덱스가 PK 값을 가짐 ⇒ 논리적인 주소를 가지는 샘
    - 세컨더리 인덱스로 PK를 찾고 → PK 인덱스를 한 번 더 검색해서 레코드를 읽음
    - InnoDB가 느려 보이지만 각자 장단점이 있음 → 8.8에서 다룰 예정.

### **8.3.2 B-Tree 인덱스 키 추가 및 삭제**

#### **8.3.2.1 인덱스 키 추가**

- 적절한 위치를 검색해 리프 노드에 키 값과 레코드 주소를 저장
  - 리프가 꽉 차면 분리(Split)가 필요하고 상위 브랜치까지 영향.
    - 그래서 B-Tree는 쓰기 비용이 크다고 알려짐
- 대략적인 비용 예측: 레코드 추가 비용을 1이라 하면 인덱스 하나당 1.5 정도
  - 인덱스가 3개면 1.5 * 3 + 1 = 5.5 정도
  - 대부분은 CPU/메모리가 아니라 **디스크에서 인덱스 페이지를 읽고 쓰는 시간**
- MyISAM, MEMORY는 즉시 반영. InnoDB는 필요하면 지연시켜 나중에 처리
  - 단, PK와 유니크 인덱스는 중복 체크가 필요해서 InnoDB도 즉시 추가/삭제

#### **8.3.2.2 인덱스 키 삭제**

- 리프 노드를 찾아서 삭제 마크만 하면 끝. 마킹된 공간은 방치하거나 재활용
  - 마킹도 디스크 쓰기라 I/O가 필요
- 5.5 이상 InnoDB에서는 이것도 버퍼링되어 지연 처리될 수 있음. MyISAM, MEMORY는 삭제가 끝나야 쿼리 완료

#### **8.3.2.3 인덱스 키 변경**

- 키 값에 따라 리프 노드 위치가 정해지므로 키 값만 쓱 바꾸는 건 불가능
- **기존 키 삭제 → 새 키 추가**로 처리됨
  - InnoDB에서는 이 작업 모두 체인지 버퍼로 지연 처리 가능

#### **8.3.2.4 인덱스 키 검색**

- 트리 탐색: 루트 → 브랜치 → 리프까지 이동하면서 비교하는 과정. UPDATE, DELETE에서 대상을 찾을 때도 사용
- 100% 일치나 값의 앞부분(Left-most part) 일치, 부등호(<, >) 비교는 가능. 뒷부분만 검색하는 건 불가
- **인덱스 키 값에 변형이 가해진 후 비교되면 B-Tree의 빠른 검색을 절대 못 씀**
  - 변형된 값은 B-Tree에 존재하는 값이 아니니까
- InnoDB에서 인덱스의 특징:
  - 레코드 락, 넥스트 키 락(갭 락)이 **검색한 인덱스를 잠근 후 레코드를 잠그는 방식**
  - UPDATE/DELETE 때 적절한 인덱스가 없으면 불필요하게 많은 레코드, 심하면 테이블 전체 레코드를 잠금
  - **InnoDB에선 인덱스 설계가 락 범위까지 좌우할 수 있다.**

### **8.3.3 B-Tree 인덱스 사용에 영향을 미치는 요소**

- 인덱스를 구성하는 칼럼의 크기, 레코드 건수, 유니크한 키 값의 개수 등이 성능에 영향을 줌

#### **8.3.3.1 인덱스 키 값의 크기**

- 페이지(Page) 또는 블록(Block): InnoDB가 디스크에 데이터를 저장하는 기본 단위. 디스크 I/O와 버퍼 풀 버퍼링의 최소 단위
  - 인덱스도 페이지 단위로 관리됨
- 이진 트리처럼 자식이 2개뿐이면 검색이 비효율적. DBMS의 B-Tree는 자식 노드 개수가 가변적
  - 몇 개를 가질지는 **페이지 크기와 키 값의 크기**로 결정됨
  - `innodb_page_size`: 5.7부터 4KB ~ 64KB 중 선택 가능, 기본값 16KB
- 계산 예시 (자식 노드 주소 영역은 6~12바이트인데 편의상 12바이트로 가정):
  - 키 16바이트: 16 × 1024 / (16 + 12) = **585개**
  - 키 32바이트: 16 × 1024 / (32 + 12) = **372개**
  - 레코드 500개를 읽어야 한다면 전자는 페이지 한 번, 후자는 최소 2번 디스크에서 읽어야 함
- 키 값이 커지면:
  - 디스크에서 읽어야 하는 횟수가 늘어나 느려짐
  - 인덱스 전체 크기가 커지는데, 버퍼 풀이나 MyISAM 키 캐시는 크기가 제한적이라 **메모리에 캐시할 수 있는 레코드 수가 줄어듦 → 메모리 효율 저하**

#### **8.3.3.2 B-Tree 깊이**

- 깊이(Depth)는 중요하지만 직접 제어할 방법은 없음
- 깊이 3일 때 담을 수 있는 키 개수:
  - 키 16바이트: 585  *585*  585 = 약 2억 개
  - 키 32바이트: 372  *372*  372 = 약 5천만 개
- 깊이 = 값을 찾을 때 랜덤하게 디스크를 몇 번 읽어야 하는지와 직결됨
  - 키가 커지면 한 페이지에 담는 키 수가 줄고 → 같은 건수라도 깊이가 깊어지고 → 디스크 읽기가 늘어남
- 결국 **인덱스 키는 가능하면 작게** 만들라는 얘기
  - 실제로는 대용량 DB라도 깊이가 5단계 이상 되는 경우는 흔치 않다고 함

#### **8.3.3.3 선택도(기수성)**

- 선택도(Selectivity) / 기수성(Cardinality): 거의 같은 의미로, 전체 인덱스 키 값 중 **유니크한 값의 수**
  - 키 값 100개 중 유니크한 값이 10개면 기수성은 10
  - 중복 값이 많을수록 기수성과 선택도가 낮아짐
  - 선택도가 높을수록 검색 대상이 줄어서 빠름
- 선택도가 나빠도 정렬이나 그루핑을 위해 인덱스를 만드는 게 나은 경우도 많음
  - 인덱스는 검색에만 쓰는 게 아니니 용도를 다 고려해서 설계해야 함
  - 예를들면 선택도가 떨어지는 (종류가 몇개 없는) 상태값을 기준으로 정렬을 해야하는 케이스
- 예시: `tb_city` 테이블 1만 건, country 칼럼에만 인덱스, 국가+도시 중복 없음

```sql
CREATE TABLE tb_city (
	country VARCHAR(10),
	city VARCHAR(10),
	INDEX ix_country (country)
);

SELECT * FROM tb_city WHERE country='KOREA' AND city='SEOUL';
```

- MySQL은 인덱스된 칼럼의 통계(전체 건수, 유니크 값 개수)를 관리하므로 전체 건수 / 유니크 값 개수로 키 하나당 몇 건이 일치할지 예측 가능
  - 인덱스가 없으니 city의 카디날리티는 작업 범위에 아무 영향을 주지 못함

| 케이스 | country 유니크 값 | country='KOREA'로 읽는 건수 | 불필요하게 읽은 건수 |
| --- | --- | --- | --- |
| A | 10개 | 약 1,000건 (10,000/10) | 999건 |
| B | 1,000개 | 약 10건 (10,000/1,000) | 9건 |
- 결과는 똑같이 1건이지만 MySQL 서버가 한 일의 양은 완전히 다름
  - A의 country 인덱스는 비효율적
  - 모든 조건을 만족하는 인덱스를 만드는 건 현실적으로 불가능하니 B 정도의 낭비는 무시할 수 있음

#### **8.3.3.4 읽어야 하는 레코드의 건수**

- 인덱스를 거쳐 레코드를 읽는 건 테이블에서 바로 읽는 것보다 비용이 높음
- 일반적인 옵티마이저는 인덱스를 통해 1건 읽는 것이 테이블에서 직접 1건 읽는 것보다 **4~5배** 비싸다고 예측
  - RDBMS마다 다르고, MySQL은 코스트 모델 설정에 따라 바뀔 수 있다 (10장에서 다시 다룰 예정)
- 그래서 인덱스로 읽을 레코드가 전체의 **20~25%** 를 넘으면 테이블을 직접 다 읽고 필터링하는 게 효율적
  - 100만 건 중 50만 건을 읽는 쿼리라면 옵티마이저는 인덱스를 안 쓰고 풀 스캔
  - 이 정도면 힌트로 인덱스를 강제해도 이득이 없음 (옵티마이저가 힌트를 무시하고 테이블을 읽기도 함)

### **8.3.4 B-Tree 인덱스를 통한 데이터 읽기**

- 인덱스를 쓰게 유도할지 말지 판단하려면 스토리지 엔진이 인덱스를 어떻게 경유해서 레코드를 읽는지 알아야 함

#### **8.3.4.1 인덱스 레인지 스캔**

- 가장 대표적인 접근 방식, 다른 방식보다 빠름
  - 1건만 읽는 경우와 여러 건 읽는 경우는 원래 이름이 다른데 여기선 묶어서 레인지 스캔이라 부름 (10장에서 구분)

```sql
SELECT * FROM employees WHERE first_name BETWEEN 'Ebbe' AND 'Gad';
```

- 검색할 범위가 결정됐을 때 사용
  - 루트 → 브랜치 → 리프까지 내려가 시작 지점을 찾고, 거기서부터 리프 노드를 순서대로 쭉 읽음 = 스캔
  - 리프 끝에 닿으면 리프 노드 간 링크로 다음 리프로 넘어가고, 멈출 위치에 다다르면 결과 반환
- 정순이든 역순이든 **인덱스 칼럼 순서로 정렬된 상태로** 레코드를 가져옴 (별도 정렬 없이)
- 리프 노드에서 조건에 맞는 건들은 데이터 파일에서 레코드를 읽어와야 함
  - **레코드 한 건마다 랜덤 I/O가 한 번씩** 일어남. 3건 일치하면 랜덤 I/O 최대 3번
  - 그래서 인덱스를 통한 레코드 읽기는 비싼 작업이고, 20~25% 기준이 여기서 나옴
- 레인지 스캔의 3단계:
  1. 인덱스 탐색(Index seek): 조건을 만족하는 값이 저장된 위치를 찾음
  2. 인덱스 스캔(Index scan): 1번 위치부터 필요한 만큼 인덱스를 쭉 읽음 (1, 2번을 합쳐 인덱스 스캔이라고도 함)
  3. 읽어 들인 키와 레코드 주소로 레코드가 저장된 페이지를 가져와 최종 레코드를 읽음
- 커버링 인덱스: 3번 과정이 필요 없는 경우
  - 인덱스가 이미 모든 데이터를 가지고 있기에 레코드를 않읽어도 되는 케이스
  - 디스크의 레코드를 안 읽어도 되니 랜덤 읽기가 확 줄고 그만큼 빨라짐
- 1, 2번 단계가 얼마나 수행됐는지는 상태 값으로 확인 가능

```sql
SHOW STATUS LIKE 'Handler_%';
```

- `Handler_read_key`: 1번 단계 실행 횟수, `Handler_read_next`/`Handler_read_prev`: 2번 단계로 정순/역순으로 읽은 건수
- `Handler_read_first`/`Handler_read_last`: 첫/마지막 레코드를 읽은 횟수 (MIN(), MAX())
- 인덱스만 읽었는지 3번 단계까지 갔는지는 구분하지 않음

#### **8.3.4.2 인덱스 풀 스캔**

- 인덱스를 처음부터 끝까지 모두 읽는 방식
  - 대표적으로 인덱스는 (A, B, C)인데 조건은 B나 C로 검색하는 경우
- 리프 노드의 제일 앞이나 뒤로 가서 리프를 잇는 링크드 리스트를 따라 쭉 스캔
- 쿼리가 인덱스 칼럼만으로 처리 가능할 때 사용. **레코드까지 읽어야 한다면 절대 이 방식으로 처리되지 않음**
  - 레인지 스캔보다는 느리지만, 인덱스가 테이블보다 작으니 테이블 풀 스캔보다는 효율적
- 책에서 그냥 *"인덱스를 사용한다"*고 하면 레인지 스캔이나 루스 인덱스 스캔을 말하는 것
  - 인덱스 풀 스캔은 인덱스를 만드는 목적이 아니라서, 테이블 풀 스캔이나 인덱스 풀 스캔은 *"인덱스를 사용하지 못한다", "효율적으로 사용하지 못한다"*고 표현했다 함

#### **8.3.4.3 루스 인덱스 스캔**

- 루스(Loose) 인덱스 스캔: 말 그대로 느슨하게, 듬성듬성 인덱스를 읽는 것
  - 오라클의 인덱스 스킵 스캔과 비슷.
  - 레인지 스캔, 풀 스캔은 반대 개념으로 "타이트(Tight) 인덱스 스캔"이라고 불림.
- 레인지 스캔처럼 동작하지만 필요 없는 키 값은 SKIP하고 다음으로 넘어감
  - **주로 GROUP BY, 집합 함수 MAX()/MIN() 최적화에 사용**

```sql
-- dept_emp 테이블에 (dept_no, emp_no) 인덱스가 있음
SELECT dept_no, MIN(emp_no)
FROM dept_emp
WHERE dept_no BETWEEN 'd002' AND 'd004'
GROUP BY dept_no;
```

- dept_no 그룹별 첫 번째 레코드의 emp_no만 읽으면 되니, 옵티마이저가 나머지는 무시하고 넘어감 (사용 조건은 10장)

#### **8.3.4.4 인덱스 스킵 스캔**

- 인덱스의 핵심은 정렬. 그래서 칼럼 순서가 매우 중요함

```sql
ALTER TABLE employees ADD INDEX ix_gender_birthdate (gender, birth_date);

-- 인덱스를 사용하지 못하는 쿼리 (gender 조건 없음)
SELECT * FROM employees WHERE birth_date >= '1965-02-01';

-- 인덱스를 사용할 수 있는 쿼리
SELECT * FROM employees WHERE gender='M' AND birth_date >= '1965-02-01';
```

- 예전엔 birth_date로 시작하는 인덱스를 새로 만들어야 했음
- 8.0부터 **인덱스 스킵 스캔(Index skip scan)**: gender를 건너뛰고 birth_date만으로 인덱스 검색 가능
  - **루스 인덱스 스캔은 GROUP BY 전용이었지만 스킵 스캔은 WHERE 검색에도 쓸 수 있음**

```sql
SET optimizer_switch='skip_scan=off';  -- 8.0 이전 방식
EXPLAIN SELECT gender, birth_date FROM employees WHERE birth_date >= '1965-02-01';
-- type: index, key: ix_gender_birthdate, Extra: Using where; Using index

SET optimizer_switch='skip_scan=on';
EXPLAIN SELECT gender, birth_date FROM employees WHERE birth_date >= '1965-02-01';
-- type: range, key: ix_gender_birthdate, Extra: Using where; Using index for skip scan
```

- off: type이 index = 인덱스를 처음부터 끝까지 읽음(풀 인덱스 스캔). 모든 칼럼이 필요했다면 테이블 풀 스캔이었을 것
- on: type이 range = 꼭 필요한 부분만 읽음
- 동작: gender의 유니크한 값('M', 'F')을 모두 구해서 `gender='M' AND ...`, `gender='F' AND ...` 두 쿼리를 실행하는 것처럼 처리
  - ENUM이라 가능한 건 아님. 어떤 타입이든 루스 인덱스 스캔 방식으로 값을 먼저 뽑아냄
- 아직 신기능이라 단점이 있음:
  - 조건이 없는 선행 칼럼의 **유니크한 값의 개수가 적어야** 함(선택도가 낮아야함)
    - 많으면 스캔 시작 지점을 찾는 작업이 많아져 오히려 느려짐
    - 예: (emp_no, dept_no) 인덱스에 스킵 스캔을 하면 사원 수만큼 시작 지점을 검색해야 함
  - 쿼리가 **인덱스에 있는 칼럼만으로 처리 가능**해야 함 (커버링 인덱스)
    - `SELECT *`로 바꾸면 풀 테이블 스캔이 됨
    - 옵티마이저가 개선되면 해결될 부분으로 봄

### **8.3.5 다중 칼럼(Multi-column) 인덱스**

- 다중 칼럼 인덱스(복합 칼럼 인덱스, Concatenated Index): 2개 이상의 칼럼으로 구성된 인덱스
  - 실서비스에선 이게 더 많이 쓰임
- 데이터가 적으면 브랜치 노드가 없을 수도 있지만 루트와 리프는 항상 존재
- 핵심: **두 번째 칼럼은 첫 번째 칼럼에 의존해서 정렬됨**
  - 두 번째 칼럼의 정렬은 첫 번째 칼럼 값이 같은 레코드 안에서만 의미가 있음
  - 칼럼이 4개면 세 번째는 두 번째에, 네 번째는 세 번째에 의존
  - (dept_no, emp_no) 인덱스에서 emp_no가 10003처럼 작아도 dept_no가 뒤쪽이면 인덱스 뒤쪽에 위치
- 그래서 다중 칼럼 인덱스에서는 칼럼 순서를 아주 신중하게 정해야 함

### **8.3.6 B-Tree 인덱스의 정렬 및 스캔 방향**

- 키 값은 오름차순이나 내림차순으로 저장되지만, 거꾸로 읽으면 반대 정렬로도 쓸 수 있음. 방향은 옵티마이저가 결정

#### **8.3.6.1 인덱스의 정렬**

- MySQL 5.7까지는 칼럼 단위로 ASC/DESC를 섞을 수 없었음 (숫자에 -1을 곱해 저장하는 꼼수를 씀)
  - 5.7에서 섞어서 만들면 에러는 없지만 실제로는 다 오름차순. 키워드는 문법상으로만 지원
- MySQL 8.0부터 정렬 순서를 섞은 인덱스 생성 가능

```sql
CREATE INDEX ix_teamname_userscore ON employees (team_name ASC, user_score DESC);
```

#### **8.3.6.1.1 인덱스 스캔 방향**

```sql
SELECT * FROM employees ORDER BY first_name DESC LIMIT 1;
```

- 인덱스를 끝까지 읽는 게 아니라, 역순으로 접근해서 첫 레코드만 읽으면 끝
  - 옵티마이저는 최댓값부터 거꾸로 읽으면 내림차순이 된다는 걸 이미 알고 있음
  - ORDER BY, MIN()/MAX() 최적화에서도 읽기 방향을 바꿔 실행 계획을 만듦

#### **8.3.6.1.2 내림차순 인덱스**

- 단일 칼럼 ASC/DESC 정렬은 읽는 방향만 바꾸면 해결됨
- 복합 인덱스에서 칼럼마다 방향이 섞인 경우(team_name ASC, user_score DESC)는 8.0의 내림차순 인덱스로만 해결 가능
- 그럼 first_name 역순 정렬만 필요하다면 ASC 인덱스와 DESC 인덱스 중 뭐가 나을까?

```sql
CREATE INDEX ix_firstname_asc ON employees (first_name ASC);
CREATE INDEX ix_firstname_desc ON employees (first_name DESC);
```

- 용어 정리:
  - 오름차순 인덱스(Ascending index): 작은 값의 인덱스 키가 B-Tree의 왼쪽으로 정렬된 인덱스
  - 내림차순 인덱스(Descending index): 큰 값의 인덱스 키가 B-Tree의 왼쪽으로 정렬된 인덱스
  - 인덱스 정순 스캔(Forward index scan): 키 크기와 관계없이 리프 노드의 왼쪽 페이지부터 오른쪽으로 스캔
  - 인덱스 역순 스캔(Backward index scan): 키 크기와 관계없이 리프 노드의 오른쪽 페이지부터 왼쪽으로 스캔
- 테스트: 약 1,260만 건 테이블 t1(PK: tid)을 정순/역순으로 풀 스캔

```sql
-- LIMIT ... OFFSET 때문에 결국 전체를 스캔
SELECT * FROM t1 ORDER BY tid ASC  LIMIT 12619775,1;  -- 4.15 sec
SELECT * FROM t1 ORDER BY tid DESC LIMIT 12619775,1;  -- 5.35 sec
```

- 1.2초 차이쯤이야 싶지만 비율로 보면 **역순이 28.9% 더 걸림**
- 정순/역순은 페이지 간 양방향 연결(Double linked list)에서 앞으로 가느냐 뒤로 가느냐 차이뿐인데, 역순이 느린 이유:
  - 페이지 잠금이 정순 스캔(Forward index scan)에 적합한 구조
  - 페이지 내에서 인덱스 레코드가 **단방향으로만** 연결된 구조
  - 참고로 InnoDB 페이지는 힙(Heap)처럼 쓰여서 레코드가 물리적으로 순서대로 배치되진 않음
- 어떻게 선택할까:
  - `WHERE userid=? ORDER BY score DESC LIMIT 10` 같은 쿼리엔 (userid ASC, score ASC)도 (userid DESC, score DESC)도 적절함
  - 소량 레코드에 드물게 실행되면 굳이 내림차순 인덱스를 고려할 필요 없음
  - 많은 레코드를 조회하면서 빈번하게 실행된다면 내림차순 인덱스가 더 효율적
- 많은 쿼리가 인덱스 앞쪽이나 뒤쪽만 집중적으로 읽어서 특정 페이지 잠금이 병목이 될 것 같으면, 자주 쓰는 정렬 순서대로 인덱스를 만드는 게 잠금 병목 완화에 도움이 됨

### **8.3.7 B-Tree 인덱스의 가용성과 효율성**

- WHERE, GROUP BY, ORDER BY가 언제 인덱스를 쓸 수 있고 어떤 방식으로 쓰는지 알아야 쿼리나 인덱스를 최적화할 수 있음

#### **8.3.7.1 비교 조건의 종류와 효율성**

- 다중 칼럼 인덱스에서는 칼럼 순서, 그리고 조건이 동등(=)인지 범위(>, <)인지에 따라 활용 형태와 효율이 달라짐

```sql
SELECT * FROM dept_emp
WHERE dept_no='d002' AND emp_no >= 10144;
-- 케이스 A: INDEX (dept_no, emp_no)
-- 케이스 B: INDEX (emp_no, dept_no)
```

- 케이스 A:
  - dept_no='d002' AND emp_no>=10144인 레코드를 찾고, dept_no가 d002가 아닐 때까지 쭉 읽기만 하면 됨
  - 읽은 레코드가 전부 원하는 결과. 5건 찾는데 5번 비교. 효율적
- 케이스 B:
  - emp_no>=10144 AND dept_no='d002'인 레코드를 찾고, 이후 모든 레코드에 대해 dept_no가 d002인지 비교해야 함
  - 5건 찾는데 7번 비교
  - 다중 칼럼 인덱스는 N번째 키가 N-1번째 키에 대해 다시 정렬되기 때문
- 필터링: 인덱스로 읽은 레코드가 나머지 조건에 맞는지 비교하면서 취사선택하는 작업
- 작업 범위 결정 조건: 작업의 범위를 결정하는 조건 (공식 명칭은 아님)
  - 많을수록 쿼리 성능을 높임
- 필터링 조건(체크 조건): 비교 범위를 못 줄이고 단순히 거름종이 역할만 하는 조건
  - 많다고 성능이 좋아지지 않고, 오히려 느리게 만들 때가 많음
- 케이스 A는 dept_no, emp_no 둘 다 작업 범위 결정 조건
- 케이스 B는 emp_no만 작업 범위 결정 조건, dept_no는 필터링 조건

#### **8.3.7.2 인덱스의 가용성**

- B-Tree 인덱스는 **왼쪽 값을 기준(Left-most)으로 오른쪽 값이 정렬**돼 있음
  - 하나의 칼럼 안에서도, 다중 칼럼 인덱스의 칼럼끼리도 적용됨
  - 케이스 A: INDEX (first_name)
  - 케이스 B: INDEX (dept_no, emp_no)
- 이 정렬 특성이 빠른 검색의 전제 조건
  - 하나의 칼럼이라도 값의 왼쪽 부분이 없으면 레인지 스캔 불가
  - 다중 칼럼 인덱스에서도 왼쪽 칼럼 값을 모르면 레인지 스캔 불가

```sql
-- 케이스 A: 왼쪽이 고정되지 않아서 레인지 스캔 불가
SELECT * FROM employees WHERE first_name LIKE '%mer';

-- 케이스 B: 선행 칼럼 dept_no 조건 없이 emp_no만으로는 효율적으로 사용 불가
SELECT * FROM dept_emp WHERE emp_no >= 10144;
```

- 왼쪽 값 기준 규칙은 GROUP BY, ORDER BY에도 똑같이 적용됨

#### **8.3.7.3 가용성과 효율성 판단**

- 아래 조건에서는 B-Tree 인덱스를 **작업 범위 결정 조건으로** 쓸 수 없음 (체크 조건으로는 쓸 수 있음)
  - NOT-EQUAL 비교: `<>`, `NOT IN`, `NOT BETWEEN`, `IS NOT NULL`
  - `LIKE '%??'`(앞부분이 아닌 뒷부분 일치) 형태
    - `WHERE column LIKE '%승환'`, `LIKE '_승환'`, `LIKE '%승%'`
  - 스토어드 함수나 연산자로 인덱스 칼럼이 변형된 후 비교
    - `WHERE SUBSTRING(column,1,1) = 'X'`, `WHERE DAYOFMONTH(column) = 1`
  - NOT-DETERMINISTIC 속성의 스토어드 함수가 비교 조건에 사용된 경우
    - `WHERE column = deterministic_function()`
  - 데이터 타입이 서로 달라서 인덱스 칼럼 타입을 변환해야 비교 가능한 경우
    - `WHERE char_column = 10`
  - 문자열 콜레이션이 다른 경우
    - `WHERE utf8_bin_char_column = euckr_bin_char_column`
- MySQL은 NULL도 인덱스에 저장하므로 `WHERE column IS NULL`도 작업 범위 결정 조건으로 사용 가능
- 다중 칼럼 인덱스 `INDEX ix_test (column_1, column_2, column_3, ..., column_n)` 기준 (i는 2보다 크고 n보다 작은 임의의 값):
  - 작업 범위 결정 조건으로 못 쓰는 경우
    - column_1에 대한 조건이 없는 경우
    - column_1의 비교 조건이 위 사용 불가 조건 중 하나인 경우
  - 작업 범위 결정 조건으로 쓰는 경우
    - column_1 ~ column_(i-1)까지 동등 비교(= 또는 IN)
    - column_i는 동등 비교(= 또는 IN), 크다/작다(>, <), LIKE 좌측 일치 패턴 중 하나
  - 이러면 column_1 ~ column_i까지 작업 범위 결정 조건, column_(i+1) ~ column_n은 체크 조건

```sql
-- 인덱스를 사용할 수 없음
... WHERE column_1 <> 2

-- column_1, column_2까지 범위 결정 조건
... WHERE column_1 = 1 AND column_2 > 10

-- column_1 ~ column_3까지 범위 결정 조건, column_4는 체크 조건
... WHERE column_1 = 1 AND column_2 = 2 AND column_3 IN (10,20,30) AND column_4 <> 100

-- column_1 ~ column_4까지 범위 결정 조건
-- 좌측 일치 LIKE는 크다/작다 비교와 동급으로 생각하면 됨
... WHERE column_1 = 1 AND column_2 IN (2,4) AND column_3 = 30 AND column_4 LIKE '김승%'
```

- 이건 B-Tree의 특징이라 MySQL뿐 아니라 대부분의 RDBMS에 똑같이 적용됨

## **8.4 R-Tree 인덱스**

- 공간 인덱스(Spatial Index): R-Tree 알고리즘으로 2차원 데이터를 인덱싱하고 검색하는 인덱스
  - 내부 메커니즘은 B-Tree와 흡사
  - B-Tree는 1차원 스칼라 값, R-Tree는 2차원 공간 개념 값을 다룸
- MySQL의 공간 확장(Spatial Extension) = 공간 데이터 타입 + 공간 인덱스(R-Tree) + 공간 연산 함수(거리, 포함 관계). 자세한 건 12.2절

### **8.4.1 구조 및 특성**

- 기하학적 도형(Geometry)을 저장하는 데이터 타입 제공
  - POINT, LINE, POLYGON, GEOMETRY
  - GEOMETRY는 나머지 3개의 슈퍼 타입이라 셋 다 저장 가능
- MBR(Minimum Bounding Rectangle): 도형을 감싸는 최소 크기의 사각형
  - **이 사각형들의 포함 관계를 B-Tree 형태로 구현한 게 R-Tree 인덱스**
  - x, y 좌표만 있는 포인트도 하나의 도형 객체
- 도형들의 MBR을 3개 레벨로 나누면:
  - 최상위(R1, R2) = 루트 노드, 차상위(R3 ~ R6, 도형 그룹) = 브랜치 노드, 최하위(R7 ~ R14, 각 도형) = 리프 노드

### **8.4.2 R-Tree 인덱스의 용도**

- Rectangle의 R + B-Tree의 Tree = R-Tree
- 주로 WGS84(GPS) 기준 위도/경도 좌표 저장에 사용
  - CAD/CAM, 회로 디자인 같은 좌표 기반 정보에도 적용 가능
- 도형(MBR)의 포함 관계로 만든 인덱스라서 **ST_Contains(), ST_Within() 같은 포함 관계 함수로 검색할 때만** 인덱스 사용 가능
  - 예: 현재 위치에서 반경 5km 이내 음식점 검색
  - ST_Distance(), ST_Distance_Sphere()는 공간 인덱스를 효율적으로 못 씀
  - 그래서 거리 기반 검색도 ST_Contains()나 ST_Within()으로 해야 함
- 반경 5km 검색: 원을 감싸는 최소 사각형(MBR)에 포함되는 점을 검색 (포함 함수는 다각형으로만 연산 가능)
  - 사각형 모서리의 점(P6)은 5km 밖인데도 결과에 포함됨
- P6이 포함돼도 괜찮다면 포함 관계 비교만 하는 게 좋음

```sql
-- "사각 상자"에 포함된 좌표 px만 검색
SELECT * FROM tb_location
WHERE ST_Contains(사각상자, px);

SELECT * FROM tb_location
WHERE ST_Within(px, 사각상자);
```

- 두 함수는 비교는 거의 같지만 파라미터 순서가 반대
  - ST_Contains(포함 경계를 가진 도형, 포함되는 도형)
  - ST_Within(포함되는 도형, 포함 경계를 가진 도형)
- P6을 꼭 빼야 하면 ST_Distance_Sphere()로 한 번 더 필터링

```sql
SELECT * FROM tb_location
WHERE ST_Contains(사각상자, px)            -- 공간 좌표 px가 사각 상자에 포함되는지
  AND ST_Distance_Sphere(p, px) <= 5*1000  /* 5km */;
```

## **8.5 전문 검색 인덱스**

- 지금까지의 인덱스는 크지 않은 데이터나 이미 키워드화된 작은 값을 위한 것
  - B-Tree는 값이 1MB여도 MyISAM 1,000바이트, InnoDB 3072바이트까지만 잘라서 키로 씀 (InnoDB는 로우 포맷이 REDUNDANT/COMPACT면 767바이트)
  - 전체 일치나 좌측 일부 일치 검색만 가능
- 전문(Full Text) 검색: 문서 내용 전체를 인덱스화해서 특정 키워드가 포함된 문서를 찾는 것. B-Tree로는 불가
  - 전문 검색 인덱스는 기능의 명칭이지 특정 알고리즘 이름이 아님

### **8.5.1 인덱스 알고리즘**

- 본문에서 검색할 키워드를 분석해 내고 그 키워드로 인덱스를 구축. 크게 어근 분석과 n-gram 분석으로 나뉨
  - 구분자(공백, 문장 기호) 방식은 8.0부터 두 알고리즘에 포함됨

#### **8.5.1.1 어근 분석 알고리즘**

- 색인 과정의 두 단계:
  - 불용어(Stop Word) 처리: 검색에서 별 가치가 없는 단어를 걸러서 제거
    - MySQL은 소스코드에 정의돼 있지만 사용자가 별도로 정의할 수 있음
  - 어근 분석(Stemming): 검색어로 선정된 단어의 뿌리인 원형을 찾는 작업
- MySQL은 오픈소스 형태소 분석 라이브러리 MeCab을 플러그인으로 지원
  - 한글, 일본어는 영어처럼 단어 변형이 거의 없어서 어근 분석보다 형태소 분석으로 명사와 조사를 구분하는 게 더 중요
  - MeCab은 원래 일본어용이지만 한국어가 일본어와 비슷해서 한글 분석도 가능 (서구권 언어용으론 Snowball)
  - 단어 사전과 언어 샘플 학습이 필요해서, 적용은 쉬워도 한글에 맞게 완성도를 높이는 데는 많은 시간과 노력이 듦

#### **8.5.1.2 n-gram 알고리즘**

- 형태소 분석은 범용으로 쓰기 어려워서 보완책으로 도입된 게 n-gram
  - 형태소 분석이 문장을 이해하는 알고리즘이라면, n-gram은 단순히 키워드를 찾기 위한 인덱싱 알고리즘
- n-gram: 본문을 무조건 몇 글자씩 잘라서 인덱싱하는 방법
  - 단순하고 언어별 준비 작업이 필요 없지만, 인덱스 크기가 상당히 큼
  - n은 인덱싱할 키워드의 최소 글자 수. 보통 2글자 단위인 2-gram(Bi-gram)을 많이 씀
- 예: `To be or not to be. That is the question`
  - 공백과 마침표로 10개 단어로 나누고, 각 단어를 **2글자씩 중첩해서** 토큰으로 분리 (10글자 단어면 9개 토큰)
  - 예: question → qu, ue, es, st, ti, io, on. 중복 토큰은 하나로 병합
- 토큰이 불용어와 **같거나 불용어를 포함하면** 버리고, 남은 토큰만 인덱스에 등록
  - 내장 불용어(36개)는 `information_schema.INNODB_FT_DEFAULT_STOPWORD`에서 확인 (a, about, an, are, as, at, be, i, in, is ...)
- MySQL은 이렇게 구분된 토큰을 **단순한 B-Tree 인덱스에 저장**함

#### **8.5.1.3 불용어 변경 및 삭제**

- 위 예시에서 "ti", "at", "ha" 같은 토큰은 "a"와 "i" 철자가 불용어로 등록돼 있어서 전부 버려짐
  - 도움보다 혼란을 줄 수 있어서, 불용어 처리를 무시하거나 직접 등록하는 걸 권장
- 불용어 처리 무시:
  - 모든 엔진: my.cnf의 `ft_stopword_file=''` (서버 시작 시에만 읽어서 재시작 필요)
  - InnoDB만: `SET GLOBAL innodb_ft_enable_stopword=OFF;` (동적 변수)
- 사용자 정의 불용어:
  - 파일: `ft_stopword_file='/data/my_custom_stopword.txt'`
  - 테이블(InnoDB만): 불용어 테이블을 `innodb_ft_server_stopword_table`에 설정. **설정 이후에 전문 검색 인덱스가 생성돼야** 적용됨

```sql
CREATE TABLE my_stopword(value VARCHAR(30)) ENGINE=INNODB;
INSERT INTO my_stopword(value) VALUES ('MySQL');

SET GLOBAL innodb_ft_server_stopword_table='mydb/my_stopword';
ALTER TABLE tb_bi_gram
	ADD FULLTEXT INDEX fx_title_body(title, body) WITH PARSER ngram;
```

- `innodb_ft_user_stopword_table`도 사용법은 같고, 인덱스마다 다른 불용어를 써야 할 때 사용

### **8.5.2 전문 검색 인덱스의 가용성**

- 전문 검색 인덱스를 쓰려면 두 조건이 필수:
  - 쿼리에서 전문 검색 문법(MATCH ... AGAINST ...) 사용
  - 테이블이 전문 검색 대상 칼럼에 전문 인덱스를 보유

```sql
CREATE TABLE tb_test (
	doc_id INT,
	doc_body TEXT,
	PRIMARY KEY (doc_id),
	FULLTEXT KEY fx_docbody (doc_body) WITH PARSER ngram
) ENGINE=InnoDB;

-- 결과는 나오지만 풀 테이블 스캔
SELECT * FROM tb_test WHERE doc_body LIKE '%애플%';

-- 전문 검색 인덱스 사용
SELECT * FROM tb_test
WHERE MATCH(doc_body) AGAINST('애플' IN BOOLEAN MODE);
```

- 전문 검색 인덱스를 구성하는 칼럼은 MATCH 절 괄호 안에 **모두** 명시해야 함

## **8.6 함수 기반 인덱스**

- 일반 인덱스는 칼럼 값의 앞부분 또는 전체에 대해서만 생성 가능
- 칼럼 값을 변형한 값으로 인덱스를 만들어야 할 때 함수 기반 인덱스를 씀 (8.0부터)
- 구현 방법: 가상 칼럼을 이용한 인덱스, 함수를 이용한 인덱스
  - 계산 과정만 다르고 내부 구조와 유지관리는 B-Tree와 동일

### **8.6.1 가상 칼럼을 이용한 인덱스**

- user(user_id, first_name, last_name) 테이블에서 first_name + last_name을 합쳐서 검색해야 한다면
  - 예전: full_name 칼럼을 추가하고 모든 레코드를 업데이트한 다음 인덱스 생성
  - 8.0: 가상 칼럼을 추가하고 거기에 인덱스 생성

```sql
ALTER TABLE user
	ADD full_name VARCHAR(30) AS (CONCAT(first_name,' ',last_name)) VIRTUAL,
	ADD INDEX ix_fullname (full_name);

EXPLAIN SELECT * FROM user WHERE full_name='Matt Lee';
-- type: ref, key: ix_fullname, key_len: 123
```

- VIRTUAL이든 STORED든 가상 칼럼에 인덱스 생성 가능
- 단점: 테이블에 칼럼을 추가하는 것과 같은 효과라 **실제 테이블 구조가 변경됨**
  - VIRTUAL과 STORED 차이는 15.8절

### **8.6.2 함수를 이용한 인덱스**

- 가상 칼럼은 5.7에서도 가능했지만, 함수를 직접 인덱스 생성 구문에 쓰는 건 8.0부터
  - 테이블 구조를 바꾸지 않고 계산된 결괏값 검색을 빠르게 만들어 줌

```sql
CREATE TABLE user (
	user_id BIGINT,
	first_name VARCHAR(10),
	last_name VARCHAR(10),
	PRIMARY KEY (user_id),
	INDEX ix_fullname ((CONCAT(first_name,' ',last_name)))
);

EXPLAIN SELECT * FROM user WHERE CONCAT(first_name,' ',last_name)='Matt Lee';
-- type: ref, key: ix_fullname, key_len: 87, ref: const
```

- **조건절에 인덱스에 명시된 표현식이 그대로 사용돼야** 함
  - 결과가 같아도 표현식이 다르면 옵티마이저는 다른 표현식으로 보고 인덱스를 못 씀
- 실행 계획에서 인덱스를 안 쓴다면 CONCAT에 쓴 공백 문자 리터럴 때문일 가능성이 높음
  - 아래 3개 시스템 변수의 콜레이션을 같게 맞추고 다시 테스트 (책에서는 utf8mb4_0900_ai_ci로 통일)
  - collation_connection, collation_database, collation_server
- 가상 칼럼 방식과 함수 직접 사용 방식은 사용법과 SQL 문법만 다를 뿐, 내부적으로는 동일한 구현을 사용
  - 즉 둘 사이에 성능 차이는 없음

## **8.7 멀티 밸류 인덱스**

- 전문 검색 인덱스를 제외한 모든 인덱스는 레코드 1건이 키 값 1개를 가짐 (1:1)
- 멀티 밸류(Multi-Value) 인덱스: 하나의 레코드가 여러 개의 키 값을 가질 수 있는 인덱스
  - RDBMS 기준으로는 정규화에 위배되는 형태
  - JSON 배열 필드의 원소(Element)들을 인덱싱해야 하는 요건 때문에 생김
  - 배열 인덱스가 안 돼서 MongoDB와 많이 비교당했는데, 8.0부터는 부족함이 없는 상태라고 함

```sql
CREATE TABLE user (
	user_id BIGINT AUTO_INCREMENT PRIMARY KEY,
	first_name VARCHAR(10),
	last_name VARCHAR(10),
	credit_info JSON,
	INDEX mx_creditscores ( (CAST(credit_info->'$.credit_scores' AS UNSIGNED ARRAY)) )
);

INSERT INTO user VALUES (1, 'Matt', 'Lee', '{"credit_scores":[360, 353, 351]}');
```

- 일반적인 조건 방식이 아니라 **아래 함수로 검색해야** 옵티마이저가 인덱스를 씀
  - MEMBER OF(), JSON_CONTAINS(), JSON_OVERLAPS()

```sql
EXPLAIN SELECT * FROM user WHERE 360 MEMBER OF(credit_info->'$.credit_scores');
-- type: ref, key: mx_creditscores, key_len: 9, ref: const, Extra: Using where
```

- Worklog에는 DECIMAL, INTEGER, DATETIME, VARCHAR/CHAR 지원이라고 돼 있지만 8.0.21에서는 CHAR/VARCHAR 배열은 미지원
  - `CAST(contacts->'$.phone_no' AS CHAR ARRAY)`로 인덱스를 만들면 ERROR 1235 (아직 지원 안 함)

## **8.8 클러스터링 인덱스**

- 클러스터링: 여러 개를 하나로 묶는다는 의미. MySQL에서는 레코드를 PK 기준으로 비슷한 것끼리 묶어서 저장
  - 비슷한 값을 동시에 조회하는 경우가 많다는 점에 착안. **InnoDB만** 지원

### **8.8.1 클러스터링 인덱스**

- 클러스터링 인덱스: PK 값이 비슷한 레코드끼리 묶어서 저장하는 것. **PK에만** 적용되는 내용
  - PK 값에 의해 레코드의 저장 위치가 결정되고, PK가 바뀌면 물리적인 위치도 바뀌어야 함. 그래서 PK를 신중하게 결정해야 함
- 인덱스 알고리즘이라기보다 **테이블 레코드의 저장 방식**
  - "클러스터링 인덱스" = "클러스터링 테이블", 기준이 되는 PK = 클러스터링 키
- PK 기반 검색이 매우 빠르고, 대신 레코드 저장이나 PK 변경은 상대적으로 느림
- 일반 B-Tree도 키 값으로 정렬돼 있지만 그렇게 부르진 않음. 레코드가 PK로 정렬되어 저장된 경우만 클러스터링이라 함
- 구조는 일반 B-Tree와 비슷하지만 **리프 노드에 레코드의 모든 칼럼이 같이 저장**돼 있음
  - 클러스터링 테이블은 그 자체가 하나의 거대한 인덱스 구조
- PK를 바꾸면 레코드가 이동함

```sql
UPDATE tb_test SET emp_no=100002 WHERE emp_no=100007;
```

- 3번 페이지에 있던 레코드가 2번 페이지로 이동. 실제로 PK를 바꾸는 일은 거의 없지만 PK의 중요성을 보여주는 예
- MyISAM 등은 PK가 바뀌어도 레코드 위치가 안 바뀜. 한번 저장된 주소 = 로우 아이디(ROW-ID), MySQL에선 사용자에게 노출 안 됨
- PK가 없는 InnoDB 테이블의 클러스터링 키 선택 우선순위:
  1. PK가 있으면 PK
  2. NOT NULL 옵션의 유니크 인덱스 중 첫 번째
  3. 자동으로 유니크한 값을 가지도록 증가하는 칼럼을 내부적으로 추가해서 사용
- 3번의 자동 추가 칼럼은 사용자에게 안 보이고 쿼리에서 쓸 수도 없음. 의미 없는 숫자로 클러스터링되니 혜택이 없음
  - 클러스터링 인덱스는 테이블당 하나뿐인 엄청난 혜택이니 가능하면 PK를 명시적으로 만들자

### **8.8.2 세컨더리 인덱스에 미치는 영향**

- MyISAM, MEMORY: 레코드가 처음 저장된 곳에서 안 움직이고, PK와 세컨더리 인덱스 모두 ROWID로 레코드를 찾음 → 구조적으로 차이 없음
- InnoDB의 세컨더리 인덱스가 레코드 주소를 가진다면 클러스터링 키가 바뀔 때마다 모든 인덱스의 주솟값을 바꿔야 함
  - 그래서 InnoDB의 모든 세컨더리 인덱스는 **레코드 주소가 아니라 PK 값을 저장**
- 예: PK(emp_no), INDEX ix_firstname(first_name)인 테이블에서 `WHERE first_name='Aamer'`
- MyISAM: ix_firstname 검색 → 레코드 주소 확인 → 주소로 최종 레코드를 가져옴
- InnoDB: ix_firstname 검색 → PK 값 확인 → PK 인덱스를 검색해서 최종 레코드를 가져옴
- InnoDB가 조금 더 복잡하지만 클러스터링 인덱스의 장점이 더 크니 성능 저하는 너무 걱정 안 해도 된다고 함

### **8.8.3 클러스터링 인덱스의 장점과 단점**

- MyISAM 같은 클러스터링되지 않은 일반 PK와 비교한 상대적인 장단점

| 구분 | 내용 |
| --- | --- |
| 장점 | PK(클러스터링 키)로 검색할 때 처리 성능이 매우 빠름. 특히 PK 범위 검색이 매우 빠름 |
| 장점 | 모든 세컨더리 인덱스가 PK를 가지고 있어서 인덱스만으로 처리되는 경우가 많음 (커버링 인덱스) |
| 단점 | 모든 세컨더리 인덱스가 클러스터링 키를 가지므로 키 값이 크면 전체 인덱스 크기가 커짐 |
| 단점 | 세컨더리 인덱스로 검색할 때 PK로 한 번 더 검색해야 해서 느림 |
| 단점 | INSERT 시 PK로 저장 위치가 결정되므로 느림 |
| 단점 | PK를 변경하면 레코드를 DELETE하고 INSERT해야 해서 느림 |
- 정리하면 장점은 빠른 읽기(SELECT), 단점은 느린 쓰기(INSERT, UPDATE, DELETE)
- OLTP 환경은 쓰기:읽기 비율이 2:8이나 1:9 정도라서, 쓰기가 조금 느려도 읽기를 빠르게 유지하는 게 매우 중요

### **8.8.4 클러스터링 테이블 사용 시 주의사항**

#### **8.8.4.1 클러스터링 인덱스 키의 크기**

- 모든 세컨더리 인덱스가 PK 값을 포함하므로 PK가 커지면 세컨더리 인덱스도 자동으로 커짐
  - 보통 세컨더리 인덱스가 4~5개 정도라 급격히 증가함
- 세컨더리 인덱스 5개인 테이블에서 PK 크기 비교:

| PK 크기 | 레코드당 증가하는 인덱스 크기 | 100만 건 저장 시 증가하는 인덱스 크기 |
| --- | --- | --- |
| 10바이트 | 10바이트 * 5 = 50바이트 | 50바이트 * 1,000,000 = 47MB |
| 50바이트 | 50바이트 * 5 = 250바이트 | 250바이트 * 1,000,000 = 238MB |
- 레코드 한 건으로 보면 별것 아니지만 100만 건이면 거의 190MB, 1,000만 건이면 1.9GB가 늘어남
- 인덱스가 커지면 같은 성능을 내기 위해 메모리도 더 필요하니 PK는 신중하게 선택

#### **8.8.4.2 프라이머리 키는 AUTO-INCREMENT보다는 업무적인 칼럼으로 생성(가능한 경우)**

- InnoDB의 PK는 클러스터링 키라 PK로 검색(특히 범위 검색)하면 매우 빠름
  - MyISAM은 PK로 뭘 고르든 성능 차이가 별로 없지만 InnoDB는 엄청난 차이가 남
- PK는 대부분의 검색에서 자주 쓰이므로, 칼럼 크기가 크더라도 업무적으로 레코드를 대표할 수 있다면 그 칼럼을 PK로 설정하는 게 좋음

#### **8.8.4.3 프라이머리 키는 반드시 명시할 것**

- PK 없는 테이블을 가끔 보는데, AUTO_INCREMENT 칼럼을 써서라도 PK를 만드는 걸 권장
- PK를 정의하지 않으면 InnoDB가 내부적으로 일련번호 칼럼을 추가하는데, 사용자는 접근할 수 없음
  - 결국 PK를 안 만드는 것과 AUTO_INCREMENT 칼럼을 PK로 만드는 건 똑같음
  - 그럴 바엔 사용자가 쓸 수 있는 AUTO_INCREMENT 값을 PK로 쓰는 게 낫다
- ROW 기반 복제나 InnoDB Cluster에서는 모든 테이블에 PK가 있어야 정상적인 복제 성능을 보장받음
  - PK는 꼭 만들자

#### **8.8.4.4 AUTO-INCREMENT 칼럼을 인조 식별자로 사용할 경우**

- 여러 칼럼으로 복합 PK를 만들면 PK가 길어질 때가 있음
  - PK가 길어도 세컨더리 인덱스가 필요 없다면 그대로 써도 좋음
  - 세컨더리 인덱스도 필요하고 PK도 길다면 AUTO_INCREMENT 칼럼을 추가해서 PK로 설정
- 인조 식별자(Surrogate key): PK를 대체하려고 인위적으로 추가한 PK
- 로그 테이블처럼 조회보다 INSERT 위주인 테이블은 AUTO_INCREMENT 인조 식별자를 PK로 쓰는 게 성능에 도움

## **8.9 유니크 인덱스**

- 유니크는 인덱스라기보다 **제약 조건**에 가까움
  - 테이블이나 인덱스에 같은 값이 2개 이상 저장될 수 없음
  - MySQL에서는 인덱스 없이 유니크 제약만 걸 방법이 없음
- 유니크 인덱스에 NULL도 저장 가능하고, NULL은 특정 값이 아니라서 2개 이상 저장될 수 있음
- PK는 기본적으로 NULL을 허용하지 않는 유니크 속성이 자동 부여됨
  - MyISAM, MEMORY의 PK는 사실상 NOT NULL 유니크 인덱스와 같음
  - InnoDB의 PK는 클러스터링 키 역할도 하므로 유니크 인덱스와 근본적으로 다름

### **8.9.1 유니크 인덱스와 일반 세컨더리 인덱스의 비교**

- 구조상으로는 아무 차이 없음. 읽기/쓰기 성능 관점에서 비교

#### **8.9.1.1 인덱스 읽기**

- 많은 사람이 유니크 인덱스가 빠르다고 생각하는데 **사실이 아님**
  - 일반 인덱스가 한 건 더 읽는 작업은 디스크 읽기가 아니라 CPU의 값 비교라 영향이 거의 없음
- 일반 세컨더리 인덱스가 느린 건 중복이 허용돼 읽을 레코드가 많아서지, 인덱스 특성 때문이 아님
  - 1건에 0.1초, 2건에 0.2초 걸렸다고 후자가 느리다고 할 수 없는 것과 같은 이치
- 실행 계획은 다르지만, 읽어야 할 레코드 건수가 같다면 성능 차이는 미미

#### **8.9.1.2 인덱스 쓰기**

- 유니크 인덱스는 키를 쓸 때 **중복 체크 과정이 한 단계 더** 필요해서 일반 세컨더리 인덱스보다 느림
- MySQL은 중복 체크 때 읽기 잠금, 쓰기 때 쓰기 잠금을 사용하는데 이 과정에서 **데드락이 아주 빈번히** 발생
- InnoDB는 인덱스 키 저장을 체인지 버퍼로 버퍼링해서 빨리 처리하는데, 유니크 인덱스는 반드시 중복 체크를 해야 해서 **버퍼링을 못 함**
  - 그래서 유니크 인덱스는 변경 작업이 더 느림

### **8.9.2 유니크 인덱스 사용 시 주의사항**

- 꼭 필요하면 당연히 만들어야 하지만, 성능이 좋아질 거라 생각하고 불필요하게 만들지는 말 것
- 같은 칼럼에 유니크 인덱스와 일반 인덱스를 중복으로 만드는 경우가 있는데 불필요
  - 유니크 인덱스도 일반 세컨더리 인덱스와 같은 역할을 그대로 할 수 있음

```sql
CREATE TABLE tb_unique (
	id INTEGER NOT NULL,
	nick_name VARCHAR(100),
	PRIMARY KEY (id),
	UNIQUE INDEX ux_nickname (nick_name),
	INDEX ix_nickname (nick_name)  -- 불필요한 중복
);
```

- 같은 칼럼에 PK와 유니크 인덱스를 동시에 만드는 것도 불필요한 중복
- 유니크 인덱스가 실행 계획이나 파티션에 미치는 영향은 10장, 13장에서
- 결론: 유일성이 꼭 보장돼야 하는 칼럼만 유니크 인덱스로, 아니면 일반 세컨더리 인덱스도 고려해 보자

## **8.10 외래키**

- MySQL에서 외래키는 InnoDB에서만 생성 가능
  - 외래키 제약을 설정하면 연관 테이블의 칼럼에 **인덱스까지 자동 생성**
  - 외래키를 제거하기 전에는 자동 생성된 인덱스를 삭제할 수 없음
- InnoDB 외래키 관리의 두 가지 특징:
  - 테이블의 변경(쓰기 잠금)이 발생하는 경우에만 잠금 경합(잠금 대기)이 발생
  - 외래키와 연관되지 않은 칼럼의 변경은 최대한 잠금 경합을 발생시키지 않음

```sql
CREATE TABLE tb_parent (id INT NOT NULL, fd VARCHAR(100) NOT NULL, PRIMARY KEY (id)) ENGINE=InnoDB;

CREATE TABLE tb_child (
	id INT NOT NULL,
	pid INT DEFAULT NULL,  -- parent.id 칼럼 참조
	fd VARCHAR(100) DEFAULT NULL,
	PRIMARY KEY (id),
	KEY ix_parentid (pid),
	CONSTRAINT child_ibfk_1 FOREIGN KEY (pid) REFERENCES tb_parent (id) ON DELETE CASCADE
) ENGINE=InnoDB;
-- tb_parent: (1, 'parent-1'), (2, 'parent-2') / tb_child: (100, 1, 'child-100')
```

### **8.10.1 자식 테이블의 변경이 대기하는 경우**

```sql
-- 커넥션-1
BEGIN; UPDATE tb_parent SET fd='changed-2' WHERE id=2;
-- 커넥션-2
BEGIN; UPDATE tb_child SET pid=2 WHERE id=100;  -- 대기
-- 커넥션-1
ROLLBACK;  -- 커넥션-2: Query OK, 1 row affected (3.04 sec)
```

- 커넥션-1이 부모 id=2에 쓰기 잠금 → 커넥션-2가 자식의 외래키 칼럼 pid를 2로 바꾸려다 대기 → 커넥션-1 종료 후 바로 처리
- 자식 테이블의 외래키 칼럼 변경(INSERT, UPDATE)은 부모 테이블 확인이 필요한데, 부모 레코드에 쓰기 잠금이 있으면 해제될 때까지 기다림 → 첫 번째 특징
- 자식 테이블의 외래키가 아닌 칼럼(tb_child.fd 같은)의 변경은 외래키로 인한 잠금 확장이 없음 → 두 번째 특징

### **8.10.2 부모 테이블의 변경 작업이 대기하는 경우**

```sql
-- 커넥션-1
BEGIN; UPDATE tb_child SET fd='changed-100' WHERE id=100;
-- 커넥션-2
BEGIN; DELETE FROM tb_parent WHERE id=1;  -- 대기
-- 커넥션-1
ROLLBACK;  -- 커넥션-2: Query OK, 1 row affected (6.09 sec)
```

- 커넥션-1이 부모 키 1을 참조하는 자식 레코드에 쓰기 잠금 → 커넥션-2의 부모 id=1 DELETE가 대기
  - ON DELETE CASCADE라 부모가 삭제되면 자식도 같이 삭제돼야 하므로
- 물리적인 외래키를 만들 땐 이런 잠금 경합까지 고려해서 모델링해야 함
  - 진짜 고려할 점은 참조 체크 자체가 아니라 **체크를 위해 연관 테이블에 읽기 잠금을 걸어야 한다는 것**
  - 잠금이 다른 테이블로 확장되면 그만큼 전체 동시 처리에 영향을 줌
  - 실무에서 물리 FK를 안 거는 팀이 많은 이유 중 하나가 이거겠다 싶음
