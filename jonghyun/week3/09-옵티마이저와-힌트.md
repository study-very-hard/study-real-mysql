# **Ch.9 옵티마이저와 힌트**

- 옵티마이저: 쿼리를 어떤 방법으로 실행해야 최소 비용으로 결과를 만들 수 있을지 결정하는 MySQL의 두뇌
    - 결과는 같아도 만드는 방법은 다양함. 통계 정보를 참조해 최적의 실행 계획을 세움
- `EXPLAIN` 결과를 제대로 읽으려면 옵티마이저가 어떤 최적화를 하는지 알아야 함
- 이번 장: 기본 데이터 처리(정렬, 그루핑, DISTINCT, 임시 테이블) → 고급 최적화(옵티마이저 스위치, 조인 최적화) → 쿼리 힌트

---

## **9.1 개요**

### **9.1.1 쿼리 실행 절차**

1. SQL 파싱: SQL을 MySQL이 이해할 수 있는 SQL 파스 트리로 분리. "SQL 파서"가 처리하고 문법 오류는 여기서 걸러짐
2. 최적화 및 실행 계획 수립: 파스 트리를 보고 "옵티마이저"가 처리. 끝나면 "실행 계획"이 나옴
    - 불필요한 조건 제거, 복잡한 연산 단순화
    - 조인 시 테이블 읽는 순서 결정
    - 조건과 인덱스 통계 정보로 사용할 인덱스 결정
    - 가져온 레코드를 임시 테이블에 넣고 다시 가공할지 결정
3. 실행: 실행 계획대로 스토리지 엔진에서 레코드를 읽고, MySQL 엔진이 조인/정렬
- 1, 2단계는 거의 MySQL 엔진이, 3단계는 MySQL 엔진과 스토리지 엔진이 같이 처리

### **9.1.2 옵티마이저의 종류**

- 규칙 기반 최적화(RBO): 통계 정보 없이 옵티마이저에 내장된 우선순위로 실행 계획을 세움
    - 같은 쿼리면 거의 항상 같은 계획. 데이터 분포가 다양해서 이제는 거의 안 씀
    - 통계 정보가 부족하고 CPU가 느려 비용 계산이 부담스럽던 시절의 방식
- 비용 기반 최적화(CBO): 가능한 방법들을 만들고 작업 비용과 통계 정보로 비용을 산출해 최소 비용을 선택
    - 대부분의 RDBMS와 MySQL이 이 방식

## **9.2 기본 데이터 처리**

### **9.2.1 풀 테이블 스캔과 풀 인덱스 스캔**

- 풀 테이블 스캔: 인덱스 없이 테이블을 처음부터 끝까지 읽는 것. 주로 선택되는 경우:
    - 레코드가 너무 적어 인덱스보다 빠를 때 (보통 페이지 1개)
    - WHERE/ON에 인덱스를 쓸 적절한 조건이 없을 때
    - 레인지 스캔이 가능해도 일치 건수가 너무 많다고 판단될 때
- MySQL에는 한 번에 몇 페이지를 읽을지 정하는 변수가 없지만, InnoDB는 리드 어헤드를 함
    - 리드 어헤드(Read ahead): 앞으로 필요할 데이터를 예측해 미리 디스크에서 읽어 버퍼 풀에 두는 것
    - 처음 몇 페이지는 포그라운드 스레드가 읽다가, 이후 백그라운드 스레드가 4~8개씩 시작해 최대 64개 페이지까지 한 번에 읽음
    - `innodb_read_ahead_threshold`: 리드 어헤드 시작 임계값. DW 용도면 낮춰서 더 빨리 시작하게 하는 것도 방법
- 풀 인덱스 스캔에도 리드 어헤드가 똑같이 쓰임
    - `SELECT COUNT(*) FROM employees;`는 풀 테이블 스캔 같지만, 용량이 작은 인덱스를 읽는 풀 인덱스 스캔일 가능성이 높음
    - `SELECT *`처럼 레코드에만 있는 칼럼이 필요하면 풀 테이블 스캔

### **9.2.2 병렬 처리**

- 8.0부터 처음으로 하나의 쿼리를 여러 스레드가 나눠 처리할 수 있게 됨 (여러 쿼리 동시 처리는 원래 됐음)
- `innodb_parallel_read_threads`로 스레드 수를 정함. 아직 힌트나 옵션은 없고, 조건 없이 전체 건수를 세는 쿼리 정도만 가능
    - `SELECT COUNT(*) FROM salaries;`가 스레드 1개일 때 0.32초 → 2개 0.20초 → 4개 0.18초 → 8개 0.13초
- CPU 코어 수를 넘으면 오히려 느려질 수 있음

### **9.2.3 ORDER BY 처리(Using filesort)**

- 정렬은 인덱스를 이용하거나, 쿼리 실행 시 "Filesort"로 처리

| **방법** | **장점** | **단점** |
| --- | --- | --- |
| 인덱스 이용 | 이미 정렬돼 있어 순서대로 읽기만 하면 돼서 매우 빠름 | 쓰기 때 인덱스 작업으로 느려지고, 디스크와 버퍼 풀 메모리가 더 필요 |
| Filesort 이용 | 인덱스가 필요 없음. 대상이 적으면 메모리에서 처리돼 충분히 빠름 | 쿼리 실행 시 정렬하므로 건수가 많을수록 느림 |
- 모든 정렬을 인덱스로 튜닝하긴 거의 불가능함
    - 정렬 기준이 너무 많거나, GROUP BY/DISTINCT/UNION 결과를 정렬하거나, 랜덤하게 가져와야 하는 경우
- Extra에 "Using filesort"가 보이면 인덱스 없이 별도 정렬을 한 것

#### **9.2.3.1 소트 버퍼**

- 소트 버퍼(Sort buffer): 정렬용으로 할당받는 메모리. 최대 크기는 `sort_buffer_size`, 쿼리가 끝나면 즉시 반납
- 정렬할 레코드가 버퍼보다 크면 조각마다 정렬해서 디스크에 임시 기록한 뒤 다시 병합함
    - 멀티 머지(Multi-merge): 이 병합 작업. 횟수는 `Sort_merge_passes` 상태 변수에 누적
- 벤치마크에선 256KB~8MB에서 최적이고 그 밖에선 크기 효과가 없었음
    - 리눅스에선 너무 크면 메모리 할당 때문에 오히려 느려질 수도 있음
    - 저자 경험상 OLTP 서버는 56KB~1MB 미만이 적절
- 소트 버퍼는 세션 메모리라 커넥션과 정렬이 많을수록 메모리 사용이 늘어남
    - 10MB 이상이면 동시 대량 정렬로 OOM-Killer가 MySQL을 죽일 수 있음 (메모리를 제일 많이 쓰니 1순위)
    - 대량 정렬이 필요하면 해당 세션만 잠깐 늘렸다 줄이는 게 좋음

#### **9.2.3.2 정렬 알고리즘**

- 레코드 전체를 담는 "싱글 패스", 정렬 기준 칼럼만 담는 "투 패스"로 나뉨 (공식 명칭은 아님)
- `SET OPTIMIZER_TRACE="enabled=on"` 후 `INFORMATION_SCHEMA.OPTIMIZER_TRACE`의 `filesort_summary`에서 `sort_algorithm`, `sort_mode`로 확인 가능
- sort_mode 3가지:
    - `<sort_key, rowid>`: 정렬 키 + 로우 아이디만 → 투 패스
    - `<sort_key, additional_fields>`: 정렬 키 + 레코드 전체, 칼럼은 고정 사이즈 → 싱글 패스
    - `<sort_key, packed_additional_fields>`: 정렬 키 + 레코드 전체, 칼럼은 가변 사이즈 → 싱글 패스 (5.7부터, 메모리 효율용)
- `std::stable_sort`는 C++ STL 함수 이름. 리눅스 GNU STL은 퀵 소트와 힙 소트를 섞어 씀
- 싱글 패스: SELECT 대상 칼럼 전부를 소트 버퍼에 담아 정렬하고 그대로 클라이언트에 넘김
- 투 패스: 정렬 칼럼과 PK만 담아 정렬한 뒤, 그 순서대로 테이블을 다시 읽어 나머지 칼럼을 가져옴
    - 테이블을 두 번 읽어야 해서 불합리하지만, 싱글 패스는 소트 버퍼가 더 많이 필요함 (128KB면 투 패스 약 7,000건, 싱글 패스는 그 절반)
- 최신 버전은 주로 싱글 패스지만, 다음 경우엔 투 패스:
    - 레코드 크기가 `max_length_for_sort_data`보다 클 때
    - BLOB/TEXT 칼럼이 SELECT 대상에 있을 때
- 싱글 패스는 레코드가 작고 적을 때, 투 패스는 크고 많을 때 효율적
- `SELECT *`는 소트 버퍼를 몇 배~몇십 배 낭비할 수 있음. 특히 정렬이 필요하면 필요한 칼럼만 조회하자

#### **9.2.3.3 정렬 처리 방법**

| **정렬 처리 방법 (아래로 갈수록 느림)** | **Extra 칼럼** |
| --- | --- |
| 인덱스를 사용한 정렬 | 별도 표기 없음 |
| 조인에서 드라이빙 테이블만 정렬 | Using filesort |
| 조인 결과를 임시 테이블로 저장 후 정렬 | Using temporary; Using filesort |
- 인덱스 정렬:
    - ORDER BY 칼럼이 드라이빙 테이블에 속하고, 그 순서대로 된 인덱스가 있어야 함. WHERE 조건도 같은 인덱스를 쓸 수 있어야 함
    - B-Tree 계열만 가능 (해시, 전문 검색, R-Tree 불가). 조인이면 네스티드 루프 조인에서만
    - 조인 버퍼가 쓰이면 순서가 흐트러질 수 있으니 주의

```sql
SELECT *
FROM employees e, salaries s
WHERE s.emp_no=e.emp_no
  AND e.emp_no BETWEEN 100002 AND 100020
ORDER BY e.emp_no;
-- 인덱스 덕에 자동 정렬된다고 ORDER BY e.emp_no를 지우는 건 좋지 않은 선택
```

- ORDER BY를 지우지 말아야 하는 이유: 인덱스 정렬이면 추가 작업이 없어서 손해가 없고, 실행 계획이 바뀌면 순서가 깨져 버그가 됨
- 드라이빙 테이블만 정렬: 조인하면 건수와 크기가 불어나니, 첫 번째 테이블만 먼저 정렬하고 조인하는 차선책
    - 드라이빙 테이블 칼럼만으로 ORDER BY를 써야 함

```sql
SELECT *
FROM employees e, salaries s
WHERE s.emp_no=e.emp_no
  AND e.emp_no BETWEEN 100002 AND 100010
ORDER BY e.last_name;
-- 1) PK로 9건 검색 → 2) last_name으로 Filesort → 3) 정렬된 순서로 salaries와 조인해 86건
```

- 임시 테이블 사용 후 정렬: 위 쿼리를 `ORDER BY s.salary`로 바꾸면 드리븐 테이블 칼럼이라 조인 결과를 임시 테이블에 담아 정렬해야 함
    - 정렬할 레코드가 가장 많아 가장 느림. Extra: "Using where; Using temporary; Using filesort"
- 스트리밍 vs 버퍼링:
    - 스트리밍: 조건에 맞는 레코드를 찾는 대로 바로 클라이언트에 보냄. 첫 레코드 응답이 빠르고 LIMIT이 전체 시간을 크게 줄여줌
    - 버퍼링: ORDER BY, GROUP BY는 전부 모아 가공해야 보낼 수 있음. LIMIT이 있어도 서버 작업량은 별로 안 줄어듦
    - 인덱스 정렬만 스트리밍이고, 나머지 두 방법은 버퍼링
    - JDBC는 서버가 스트리밍으로 보내도 내부 버퍼에 다 모았다가 반환함 (통신 횟수가 줄어 처리량이 좋아서). 대량 데이터면 스트리밍 방식으로 바꿀 수 있음
- tb_test1(100건) : tb_test2(1,000건) = 1:10, `ORDER BY t1.col2 LIMIT 10`, tb_test1이 드라이빙일 때:

| **정렬 방법** | **읽어야 할 건수** | **조인 횟수** | **정렬 대상 건수** |
| --- | --- | --- | --- |
| 인덱스 사용 | t1: 1건, t2: 10건 | 1번 | 0건 |
| 드라이빙 테이블만 정렬 | t1: 100건, t2: 10건 | 1번 | 100건 |
| 임시 테이블 후 정렬 | t1: 100건, t2: 1,000건 | 100번 | 1,000건 |
- tb_test2가 드라이빙이면 드라이빙만 정렬해도 1,000건, 임시 테이블이면 조인 1,000번에 1,000건 정렬
- 드라이빙 순서보다 정렬 방식이 더 큰 성능 차이를 만듦. 가능하면 인덱스 정렬, 안 되면 최소한 드라이빙 테이블만 정렬하도록 유도
- Filesort에서도 LIMIT이 아예 무의미하진 않음 (상위 N건이 채워지면 정렬을 멈춤). 하지만 퀵/힙 소트 특성상 기대만큼 빨라지진 않음

#### **9.2.3.4 정렬 관련 상태 변수**

```sql
FLUSH STATUS;
SHOW STATUS LIKE 'Sort%';
-- Sort_merge_passes 13 / Sort_range 0 / Sort_rows 300024 / Sort_scan 1
```

- `Sort_merge_passes`: 멀티 머지 횟수 / `Sort_range`: 레인지 스캔 결과의 정렬 횟수 / `Sort_scan`: 풀 테이블 스캔 결과의 정렬 횟수 / `Sort_rows`: 정렬한 전체 레코드 수
- 해석: 풀 테이블 스캔 결과를 1번 정렬, 13번 병합, 30만 건 정렬

### **9.2.4 GROUP BY 처리**

- GROUP BY도 스트리밍을 불가능하게 함
- HAVING: GROUP BY 결과를 필터링하는 절. 인덱스로 처리되지 않으니 HAVING 튜닝용 인덱스는 필요 없음

#### **9.2.4.1 인덱스 스캔을 이용하는 GROUP BY(타이트 인덱스 스캔)**

- 드라이빙 테이블 칼럼으로 그루핑하고 그 칼럼에 인덱스가 있으면, 인덱스를 차례로 읽으며 그루핑한 뒤 조인
- 추가 정렬이나 임시 테이블이 필요 없음 (집계 함수 때문에 임시 테이블이 필요할 때는 있음)
- Extra에 GROUP BY 관련 문구나 "Using temporary/filesort"가 없음

#### **9.2.4.2 루스 인덱스 스캔을 이용하는 GROUP BY**

- 루스 인덱스 스캔: 인덱스를 건너뛰면서 필요한 부분만 읽는 것. Extra에 "Using index for group-by"

```sql
EXPLAIN
SELECT emp_no
FROM salaries
WHERE from_date='1985-03-01'
GROUP BY emp_no;
-- salaries | range | PRIMARY | Using where; Using index for group-by
```

- 인덱스가 (emp_no, from_date)라 WHERE만으로는 레인지 스캔이 안 되는데 range로 처리됨
    1. 인덱스에서 첫 그룹 키 emp_no=10001을 찾음
    2. `emp_no=10001 AND from_date='1985-03-01'`로 검색하듯 가져옴
    3. 다음 유니크한 emp_no로 넘어가 반복
- 특징:
    - 단일 테이블 GROUP BY에만, 프리픽스 인덱스는 불가
    - 레인지 스캔과 반대로 유니크한 값이 적을수록(분포도가 나쁠수록) 빠름
    - 임시 테이블이 필요 없음
- (col1, col2, col3) 인덱스 기준:

```sql
-- 가능
SELECT col1, col2 FROM tb_test GROUP BY col1, col2;
SELECT DISTINCT col1, col2 FROM tb_test;
SELECT col1, MIN(col2) FROM tb_test GROUP BY col1;
SELECT col1, col2 FROM tb_test WHERE col1 < const GROUP BY col1, col2;
SELECT MAX(col3), MIN(col3), col1, col2 FROM tb_test WHERE col2 > const GROUP BY col1, col2;
SELECT col1, col2 FROM tb_test WHERE col3 = const GROUP BY col1, col2;

-- 불가: MIN/MAX 외 집합 함수
SELECT col1, SUM(col2) FROM tb_test GROUP BY col1;
-- 불가: GROUP BY가 인덱스 왼쪽부터 일치하지 않음
SELECT col1, col2 FROM tb_test GROUP BY col2, col3;
-- 불가: SELECT 칼럼이 GROUP BY와 불일치
SELECT col1, col3 FROM tb_test GROUP BY col1, col2;
```

- 8.0의 인덱스 스킵 스캔도 같은 방식. 이제 GROUP BY뿐 아니라 레코드 검색에도 루스 인덱스 스캔 방식을 쓸 수 있음
    - 마찬가지로 선행 칼럼의 유니크한 값이 많으면 사용하지 않음

#### **9.2.4.3 임시 테이블을 사용하는 GROUP BY**

- 인덱스를 전혀 쓸 수 없는 GROUP BY는 임시 테이블로 처리

```sql
EXPLAIN
SELECT e.last_name, AVG(s.salary)
FROM employees e, salaries s
WHERE s.emp_no=e.emp_no
GROUP BY e.last_name;
-- e | ALL | NULL    | Using temporary
-- s | ref | PRIMARY | NULL
```

- "Using filesort" 없이 "Using temporary"만 나옴
    - 8.0 이전엔 GROUP BY가 그루핑 칼럼 기준 묵시적 정렬까지 했지만, 8.0부터는 안 함
    - GROUP BY 칼럼으로 유니크 인덱스를 가진 임시 테이블을 만들고, 조인 결과를 넣으면서 중복 체크로 INSERT/UPDATE
- ORDER BY를 같이 쓰면 명시적으로 정렬함 → "Using temporary; Using filesort"
- 5.7까지는 정렬이 필요 없으면 `ORDER BY NULL`을 권장했지만 8.0에선 필요 없음

### **9.2.5 DISTINCT 처리**

- 집합 함수와 같이 쓸 때와 아닐 때 영향 범위가 다름
- `SELECT DISTINCT`는 GROUP BY와 같은 방식으로 처리됨. 8.0에선 아래 두 쿼리가 내부적으로 같음

```sql
SELECT DISTINCT emp_no FROM salaries;
SELECT emp_no FROM salaries GROUP BY emp_no;
```

- DISTINCT는 레코드(튜플) 전체를 유니크하게 함. 특정 칼럼만이 아님
    - `SELECT DISTINCT(first_name), last_name ...`처럼 함수처럼 써도 괄호는 무시되고 (first_name, last_name) 조합이 유니크해짐
    - 에러 없이 그럴듯하게 실행되니 실수하기 쉬움
- 집합 함수 안의 DISTINCT는 인자로 준 칼럼값만 유니크하게 함

```sql
EXPLAIN SELECT COUNT(DISTINCT s.salary)
FROM employees e, salaries s
WHERE e.emp_no=s.emp_no
  AND e.emp_no BETWEEN 100001 AND 100100;
-- e | range | PRIMARY | Using where; Using index
-- s | ref   | PRIMARY | NULL
```

- salary 값을 담는 임시 테이블(유니크 인덱스)을 쓰지만 "Using temporary"는 안 나옴. 모든 버전이 그렇다고 함
    - 건수가 많으면 상당히 느려질 수 있음
    - `COUNT(DISTINCT e.last_name)`을 추가하면 실행 계획은 같은데 임시 테이블은 2개
- 인덱스된 칼럼이면 임시 테이블 없이 처리 가능: `SELECT COUNT(DISTINCT emp_no) FROM employees;`
- 아래 셋의 차이는 꼭 기억

```sql
SELECT DISTINCT first_name, last_name FROM employees WHERE emp_no BETWEEN 10001 AND 10200;
SELECT COUNT(DISTINCT first_name), COUNT(DISTINCT last_name) FROM employees WHERE emp_no BETWEEN 10001 AND 10200;
SELECT COUNT(DISTINCT first_name, last_name) FROM employees WHERE emp_no BETWEEN 10001 AND 10200;
```

### **9.2.6 내부 임시 테이블 활용**

- 내부 임시 테이블: MySQL 엔진이 정렬/그루핑할 때 내부적으로 쓰는 임시 테이블
    - `CREATE TEMPORARY TABLE`과는 다름. 다른 세션에서 볼 수 없고 쿼리가 끝나면 자동 삭제
    - 처음엔 메모리에 만들어지고 커지면 디스크로 옮겨짐

#### **9.2.6.1 메모리 임시 테이블과 디스크 임시 테이블**

- 8.0 이전: 메모리는 MEMORY 엔진(가변 길이 미지원이라 최대 길이만큼 할당해서 낭비), 디스크는 MyISAM(트랜잭션 미지원)
- 8.0부터: 메모리는 TempTable(가변 길이 지원), 디스크는 InnoDB 또는 TempTable의 MMAP 파일
- 관련 변수:
    - `internal_tmp_mem_storage_engine`: MEMORY/TempTable 선택. 기본 TempTable
    - `temptable_max_ram`: TempTable 최대 메모리. 기본 1GB
    - `temptable_use_mmap`: 1GB를 넘으면 MMAP 파일(ON)로, 아니면 InnoDB 테이블로 전환. 기본 ON (오버헤드가 더 적어서)
    - `internal_tmp_disk_storage_engine`: 처음부터 디스크에 만들 때의 엔진. 기본 InnoDB
    - MEMORY 엔진이라면 `tmp_table_size`, `max_heap_table_size`도 같이 조절
- 디스크 임시 테이블은 `tmpdir`에 생성되는데, 파일을 열자마자 삭제함
    - OS는 참조하는 프로세스가 없어질 때 실제로 지우므로, 쿼리가 끝나면 확실히 사라지고 다른 누구도 파일을 볼 수 없음
    - 그래서 `ls -al`로는 안 보이고 `lsof`로 보면 "deleted"로 나옴. deleted라도 아직 사용 중일 수 있음

#### **9.2.6.2 임시 테이블이 필요한 쿼리**

- ORDER BY와 GROUP BY 칼럼이 다른 쿼리
- ORDER BY나 GROUP BY 칼럼이 조인 순서상 첫 번째 테이블이 아닌 쿼리
- DISTINCT와 ORDER BY가 같이 있거나, DISTINCT가 인덱스로 처리되지 못하는 쿼리
- UNION이나 UNION DISTINCT가 사용된 쿼리 (select_type이 UNION RESULT)
- select_type이 DERIVED인 쿼리
- 위 마지막 3개는 "Using temporary"가 안 나와도 임시 테이블을 씀
- 1~4번은 유니크 인덱스가 있는 임시 테이블이라 더 느리고, 마지막은 유니크 인덱스가 없음
- 8.0부터 UNION ALL은 임시 테이블을 안 쓰지만, UNION(= UNION DISTINCT)은 중복 제거 때문에 여전히 씀

#### **9.2.6.3 임시 테이블이 디스크에 생성되는 경우**

- UNION/UNION ALL에서 SELECT되는 칼럼 중 512바이트 이상인 칼럼이 있을 때
- GROUP BY나 DISTINCT 칼럼 중 512바이트 이상인 칼럼이 있을 때
- 메모리 임시 테이블이 `tmp_table_size`/`max_heap_table_size`(MEMORY) 또는 `temptable_max_ram`(TempTable)보다 커질 때

#### **9.2.6.4 임시 테이블 관련 상태 변수**

- "Using temporary"만으로는 메모리/디스크 여부도, 개수도 알 수 없음

```sql
FLUSH STATUS;
SELECT first_name, last_name FROM employees GROUP BY first_name, last_name;
SHOW SESSION STATUS LIKE 'Created_tmp%';
-- Created_tmp_disk_tables 1 / Created_tmp_tables 1
```

- `Created_tmp_tables`: 만들어진 내부 임시 테이블 수 (메모리/디스크 구분 없음)
- `Created_tmp_disk_tables`: 디스크에 만들어진 것만

## **9.3 고급 최적화**

- 옵티마이저 옵션은 크게 두 가지
    - 조인 관련 옵티마이저 옵션: 예전부터 있었지만 다들 신경 안 씀. 조인이 많으면 알아야 함
    - 옵티마이저 스위치: 5.5부터. 고급 최적화 기능을 켤지 끌지 제어

### **9.3.1 옵티마이저 스위치 옵션**

- `optimizer_switch` 변수에 여러 옵션을 묶어서 설정. 각 옵션은 on/off/default
- 기본값 off는 `batched_key_access`뿐이고, 나머지(`block_nested_loop`, `index_condition_pushdown`, `use_index_extensions`, `index_merge*`, `mrr`, `mrr_cost_based`, `semijoin`, `firstmatch`, `loosescan`, `materialization`, `subquery_materialization_cost_based` 등)는 on
- `SET GLOBAL`(서버 전체), `SET SESSION`(현재 커넥션), `/*+ SET_VAR(optimizer_switch='...') */` 힌트(현재 쿼리만)로 설정

#### **9.3.1.1 MRR과 배치 키 액세스(mrr & batched_key_access)**

- 네스티드 루프 조인(Nested Loop Join): 드라이빙 테이블 레코드를 한 건 읽을 때마다 드리븐 테이블에서 일치하는 레코드를 찾는 방식
    - 조인은 MySQL 엔진, 레코드 읽기는 스토리지 엔진 담당이라 건별로 요청하면 스토리지 엔진이 최적화할 여지가 없음
- MRR(Multi-Range Read): 드라이빙 레코드를 조인 버퍼에 모았다가 한 번에 스토리지 엔진에 요청하는 방식
    - 스토리지 엔진이 데이터 페이지 순서대로 정렬해 접근하므로 디스크 읽기(버퍼 풀 접근)를 최소화
- BKA(Batched Key Access) 조인: MRR을 응용한 조인. 부가 정렬 때문에 오히려 느려질 수 있어서 기본 비활성화

#### **9.3.1.2 블록 네스티드 루프 조인(block_nested_loop)**

- 네스티드 루프 조인은 중첩 for문처럼 동작하고, 버퍼 없이 바로 드리븐 테이블을 찾아 반환함
- 블록 네스티드 루프 조인(BNL): 조인 버퍼(`join_buffer_size`)를 사용하는 조인. Extra에 "Using join buffer"
    - 드리븐 테이블을 인덱스로 검색할 수 없으면 드라이빙 건수만큼 풀 스캔을 해야 함
    - 이를 피할 수 없을 때 드라이빙 테이블 레코드를 조인 버퍼에 캐시하고, 드리븐 테이블을 읽으며 버퍼와 조인

```sql
SELECT *
FROM dept_emp de, employees e
WHERE de.from_date>'1995-01-01' AND e.emp_no<109004;
-- de | range | ix_fromdate | Using index condition
-- e  | range | PRIMARY     | Using join buffer (block nested loop)
```

- 처리: dept_emp를 ix_fromdate로 읽어 조인 버퍼에 저장 → employees를 PK로 검색 → 그 결과에 조인 버퍼 레코드를 결합
    - 실행 계획상 드라이빙은 dept_emp인데 실제로는 employees를 먼저 읽는 것처럼 동작 → 결과 순서가 흐트러질 수 있음
- 8.0.20부터는 BNL 대신 해시 조인이 쓰여서 이 문구가 안 나올 수 있음

#### **9.3.1.3 인덱스 컨디션 푸시다운(index_condition_pushdown)**

```sql
ALTER TABLE employees ADD INDEX ix_lastname_firstname (last_name, first_name);
SELECT * FROM employees WHERE last_name='Acton' AND first_name LIKE '%sal';
-- ICP off: Extra "Using where" / ICP on: Extra "Using index condition"
```

- `last_name='Acton'`은 범위를 좁히는 조건, `first_name LIKE '%sal'`은 읽은 후 비교만 하는 체크(필터링) 조건
- "Using where": 스토리지 엔진이 준 레코드를 MySQL 엔진이 인덱스로 못 거른 조건으로 검사하는 과정
- 5.5까지는 범위 제한에 못 쓰는 조건을 스토리지 엔진에 넘기지 않아서, 인덱스에 first_name이 있는데도 테이블을 다 읽은 뒤 비교했음
    - Acton이 10만 건인데 1건만 맞으면 99,999건 읽기가 낭비
- 5.6부터 인덱스에 포함된 칼럼 조건은 스토리지 엔진에 같이 넘기도록 핸들러 API가 개선됨 → 인덱스에서 걸러서 필요한 것만 테이블에서 읽음
- 기술적으로 대단한 건 아니지만 성능이 몇 배~몇십 배 좋아질 수 있음
- `engine_condition_pushdown`은 NDB(MySQL Cluster) 전용

#### **9.3.1.4 인덱스 확장(use_index_extensions)**

- InnoDB 세컨더리 인덱스에 자동 포함된 PK를 활용할지 결정하는 옵션
- PK가 (dept_no, emp_no)인 dept_emp의 `ix_fromdate(from_date)`는 사실상 (from_date, dept_no, emp_no) 인덱스처럼 동작

```sql
EXPLAIN SELECT COUNT(*) FROM dept_emp WHERE from_date='1987-07-25' AND dept_no='d001';
-- key: ix_fromdate, key_len: 19 (from_date 3바이트 + dept_no 16바이트)
EXPLAIN SELECT * FROM dept_emp WHERE from_date='1987-07-25' ORDER BY dept_no;
-- key: ix_fromdate, Extra: NULL → Using filesort 없이 정렬까지 인덱스로 처리
```

- key_len: 인덱스 칼럼 중 어디까지 썼는지를 바이트 수로 보여줌

#### **9.3.1.5 인덱스 머지(index_merge)**

- 보통 옵티마이저는 테이블당 인덱스 하나만 쓰고 나머지 조건은 체크용으로만 씀
- 인덱스 머지: 하나의 테이블에 2개 이상의 인덱스를 쓰는 것. 각 조건이 다른 인덱스를 쓸 수 있고 각각 건수가 많을 것 같을 때 선택됨
- 병합 방식에 따라 intersection, union, sort_union으로 나뉘고, `index_merge`로 셋을 한 번에 제어

#### **9.3.1.6 인덱스 머지 - 교집합(index_merge_intersection)**

```sql
EXPLAIN SELECT *
FROM employees
WHERE first_name='Georgi' AND emp_no BETWEEN 10000 AND 20000;
-- index_merge | ix_firstname,PRIMARY | Using intersect(ix_firstname,PRIMARY); Using where
```

- 각 조건 건수: first_name 253건, emp_no 범위 10,000건, 둘 다 만족은 14건
    - 하나만 쓰면 253건 중 14건만, 또는 10,000건 중 14건만 의미 있음 → 둘 다 비효율이라 교집합을 택함
- ix_firstname에 PK가 포함돼 있어서 ix_firstname만 쓰는 게 나을 수도 있음. 그럴 땐 끄면 됨

```sql
SELECT /*+ SET_VAR(optimizer_switch='index_merge_intersection=off') */ *
FROM employees
WHERE first_name='Georgi' AND emp_no BETWEEN 10000 AND 20000;
-- range | ix_firstname | Using index condition
```

#### **9.3.1.7 인덱스 머지 - 합집합(index_merge_union)**

- 각각 인덱스를 쓰는 조건이 OR로 연결된 경우

```sql
SELECT * FROM employees
WHERE first_name='Matt' OR hire_date='1987-03-31';
-- index_merge | ix_firstname,ix_hiredate | Using union(ix_firstname,ix_hiredate)
```

- 양쪽에 다 걸리는 레코드도 한 번만 나오는데 정렬 표시가 없음
    - 같은 값 안에서는 인덱스 결과가 PK 순으로 정렬돼 있어서, 두 집합을 하나씩 비교하며 정렬 없이 중복을 거름
    - 우선순위 큐(Priority Queue): 이렇게 정렬된 두 집합에서 하나씩 꺼내 중복을 제거하는 알고리즘
- AND는 둘 중 하나만 인덱스를 써도 되지만, OR는 하나라도 인덱스를 못 쓰면 항상 풀 테이블 스캔

#### **9.3.1.8 인덱스 머지 - 정렬 후 합집합(index_merge_sort_union)**

```sql
SELECT * FROM employees
WHERE first_name='Matt'
  OR hire_date BETWEEN '1987-03-01' AND '1987-03-31';
-- Using sort_union(ix_firstname,ix_hiredate)
```

- hire_date 범위 조건 결과는 emp_no로 정렬돼 있지 않아 우선순위 큐를 쓸 수 없음 → 각 집합을 emp_no로 정렬한 뒤 중복 제거

#### **9.3.1.9 세미 조인(semijoin)**

- 세미 조인: 실제 조인은 안 하고, 다른 테이블에 조건에 맞는 레코드가 있는지만 체크하는 쿼리

```sql
SELECT *
FROM employees e
WHERE e.emp_no IN
  (SELECT de.emp_no FROM dept_emp de WHERE de.from_date='1995-01-01');
-- 최적화가 없으면: e | PRIMARY | ALL | 300363건 / de | SUBQUERY | ref | 57건
```

- 서브쿼리를 먼저 실행할 것 같지만, 예전에는 employees를 풀 스캔하며 한 건씩 비교했음. 57건이면 될 걸 30만 건 넘게 읽음
- `semijoin=off`로 옛 방식을 볼 수 있지만, 테스트 후엔 꼭 `SET optimizer_switch='default';`로 되돌릴 것
    - 잊어버리면 다른 쿼리가 이상하게 느려져서 엉뚱한 데서 헤맴
- `= (subquery)`, `IN (subquery)`: 세미 조인 최적화, IN-to-EXISTS, MATERIALIZATION
- `<> (subquery)`, `NOT IN (subquery)`(안티 세미 조인): IN-to-EXISTS, MATERIALIZATION
- 8.0 세미 조인 최적화 전략: Table Pull-out, Duplicate Weed-out, First Match, Loose Scan, Materialization
    - Table pull-out은 항상 유리해서 제어 옵션이 없음
    - First Match → `firstmatch`, Loose Scan → `loosescan`, Duplicate Weed-out과 Materialization → `materialization`
    - `semijoin`은 셋을 한 번에 제어

#### **9.3.1.10 테이블 풀-아웃(Table Pull-out)**

- 서브쿼리 테이블을 아우터 쿼리로 끄집어내 조인으로 재작성하는 최적화

```sql
EXPLAIN
SELECT * FROM employees e
WHERE e.emp_no IN (SELECT de.emp_no FROM dept_emp de WHERE de.dept_no='d009');
-- 1 | SIMPLE | de | ref    | PRIMARY | Using index
-- 1 | SIMPLE | e  | eq_ref | PRIMARY | NULL
```

- id가 같으면 조인으로 처리된 것. Extra에 별도 문구가 없어서 id로 판단하거나, `SHOW WARNINGS`로 재작성된 쿼리(`FROM dept_emp de JOIN employees e WHERE ...`)를 확인
- 제한 사항과 특성:
    - 세미 조인 서브쿼리에서만, 서브쿼리 결과가 UNIQUE 인덱스나 PK 룩업으로 1건인 경우에만 사용 가능
    - 적용돼도 기존 최적화를 못 쓰는 게 아니라서 가능하면 최대한 적용함
    - 서브쿼리 테이블을 전부 끄집어낼 수 있으면 서브쿼리 자체가 없어짐
    - "서브쿼리를 조인으로 풀어 써라"는 튜닝 가이드를 대신 실행해주는 것. 이제 직접 풀 필요가 없다고 함

#### **9.3.1.11 퍼스트 매치(firstmatch)**

- IN(subquery)를 EXISTS(subquery)로 튜닝한 것과 비슷하게 동작

```sql
SELECT *
FROM employees e WHERE e.first_name='Matt'
  AND e.emp_no IN (
    SELECT t.emp_no FROM titles t
    WHERE t.from_date BETWEEN '1995-01-01' AND '1995-01-30');
-- 1 | e | ref | ix_firstname | NULL
-- 1 | t | ref | PRIMARY      | Using where; Using index; FirstMatch(e)
```

- "FirstMatch(e)": employees 레코드마다 titles에서 1건만 찾으면 더 이상 검색하지 않음. 서브쿼리가 아니라 조인으로 풀어서 실행
- 5.5의 IN-to-EXISTS 대비 장점:
    - 동등 조건 전파(Equality propagation, 옵티마이저가 없던 동등 조건을 자동 추가하는 것)가 아우터 쿼리 테이블까지 됨
    - 서브쿼리의 모든 테이블에 적용할지 일부에만 할지 취사선택 가능
- 제한 사항과 특성:
    - 단축 실행 경로(Short-cut path)라서 서브쿼리가 참조하는 아우터 테이블이 먼저 조회된 후 실행됨
    - 상관 서브쿼리(Correlated subquery)에서도 사용 가능
    - GROUP BY나 집합 함수가 쓰인 서브쿼리에는 불가

#### **9.3.1.12 루스 스캔(loosescan)**

- GROUP BY의 루스 인덱스 스캔과 비슷하게 읽는 방식

```sql
SELECT * FROM departments d WHERE d.dept_no IN (
  SELECT de.dept_no FROM dept_emp de);
-- 1 | de | index  | PRIMARY | Using index; LooseScan
-- 1 | d  | eq_ref | PRIMARY | NULL
```

- dept_emp는 33만 건이지만 PK(dept_no, emp_no)에서 dept_no는 9개뿐 → 유니크한 dept_no만 루스 인덱스 스캔으로 읽으면 중복 제거까지 하면서 효율적
- 서브쿼리 테이블을 루스 인덱스 스캔으로 읽고 아우터 테이블을 드리븐으로 조인. 서브쿼리가 루스 인덱스 스캔을 쓸 수 있는 형태여야 함
    - `expr IN (SELECT keypart1 FROM tab WHERE ...)`
    - `expr IN (SELECT keypart2 FROM tab WHERE keypart1='상수' ...)`
- 참고로 8.0은 이 쿼리를 Materialization으로 처리하려 해서, 책에서는 다른 전략을 꺼서 유도했다고 함

#### **9.3.1.13 구체화(Materialization)**

- 구체화(Materialization): 서브쿼리를 통째로 내부 임시 테이블로 만드는 것

```sql
SELECT * FROM employees e
WHERE e.emp_no IN
  (SELECT de.emp_no FROM dept_emp de WHERE de.from_date='1995-01-01');
-- 1 | SIMPLE       | <subquery2> | ALL    | NULL
-- 1 | SIMPLE       | e           | eq_ref | PRIMARY
-- 2 | MATERIALIZED | de          | ref    | ix_fromdate
```

- employees에 서브쿼리 외 조건이 없어서 FirstMatch로는 풀 스캔이 필요한 쿼리
- 테이블은 2개인데 실행 계획이 3줄 → 서브쿼리 결과로 임시 테이블 `<subquery2>`를 만들고 employees와 조인
- 제한 사항과 특성:
    - 상관 서브쿼리가 아니어야 함
    - 다른 전략과 달리 GROUP BY나 집합 함수가 있어도 사용 가능
    - 내부 임시 테이블이 사용됨
- `semijoin`, `materialization` 모두 ON이어야 함. materialization을 끄면 세미 조인이 아닌 서브쿼리의 구체화도 못 씀

#### **9.3.1.14 중복 제거(Duplicated Weed-out)**

- 세미 조인 서브쿼리를 INNER JOIN으로 바꿔 실행하고, 마지막에 중복을 제거하는 방식

```sql
SELECT * FROM employees e
WHERE e.emp_no IN (SELECT s.emp_no FROM salaries s WHERE s.salary>150000);

-- 실제로는 이렇게 처리하는 것과 같음
SELECT e.* FROM employees e, salaries s
WHERE e.emp_no=s.emp_no AND s.salary>150000
GROUP BY e.emp_no;
-- s | range  | ix_salary | Using where; Using index; Start temporary
-- e | eq_ref | PRIMARY   | End temporary
```

- 처리: ix_salary로 검색해 employees와 조인 → 임시 테이블에 저장 → emp_no로 중복 제거 → 반환
    - 조인과 임시 테이블 저장이 반복되는 구간의 시작에 "Start temporary", 끝에 "End temporary"가 붙음
- 상관 서브쿼리도 가능, GROUP BY나 집합 함수가 있으면 불가

#### **9.3.1.15 컨디션 팬아웃(condition_fanout_filter)**

- 조인은 일치 건수가 적은 테이블부터 하는 게 유리해서, 건수 예측이 정확할수록 좋은 계획이 나옴

```sql
SELECT *
FROM employees e
  INNER JOIN salaries s ON s.emp_no=e.emp_no
WHERE e.first_name='Matt'
  AND e.hire_date BETWEEN '1985-11-21' AND '1986-11-21';
-- off: e | ix_firstname | rows 233 | filtered 100.00
-- on : e | ix_firstname | rows 233 | filtered 23.20
```

- off면 인덱스 조건(first_name)만 보고 233건 모두 hire_date 조건도 만족한다고 예측
- on이면 나머지 조건(hire_date)의 충족 비율까지 계산해서 233 × 0.232 = 약 54건으로 예측
- 비율을 계산할 수 있는 조건: WHERE 칼럼에 인덱스가 있거나, 히스토그램이 있는 경우
- 옵티마이저의 건수 예측 우선순위: 레인지 옵티마이저 → 히스토그램 → 인덱스 통계 → 추측(Guesstimates)
    - 레인지 옵티마이저: 계획 수립 단계에서 실제 인덱스 데이터를 소량 읽어보고 예측. 그래서 실행 계획의 건수가 통계 정보와 다를 수 있음
- 계산이 정교해지는 만큼 계획 수립 비용이 늘어남. 쿼리가 간단하고 빈도가 높다면 업그레이드 전에 성능 테스트를 해보는 게 좋음

#### **9.3.1.16 파생 테이블 머지(derived_merge)**

- 파생 테이블(Derived Table): FROM 절에 사용된 서브쿼리
    - 예전엔 먼저 실행해서 임시 테이블로 만든 뒤 외부 쿼리를 처리 → 복사하고 다시 읽는 오버헤드, 커지면 디스크로

```sql
SELECT * FROM (
  SELECT * FROM employees WHERE first_name='Matt'
) derived_table
WHERE derived_table.hire_date='1986-04-03';
-- 병합 전: 1 | PRIMARY | <derived2> / 2 | DERIVED | employees
-- 병합 후: 1 | SIMPLE  | employees | index_merge | ix_hiredate,ix_firstname
```

- 5.7부터 파생 테이블을 외부 쿼리와 병합하는 최적화가 도입됨. `SHOW WARNINGS`로 보면 WHERE 하나로 합쳐진 쿼리로 재작성돼 있음
- 다음은 자동 병합이 안 되니 가능하면 수동으로 병합하는 게 좋음:
    - 집계 함수나 윈도우 함수, DISTINCT, GROUP BY/HAVING, LIMIT, UNION/UNION ALL이 쓰인 서브쿼리
    - SELECT 절에 사용된 서브쿼리, 값이 변경되는 사용자 변수가 쓰인 서브쿼리

#### **9.3.1.17 인비저블 인덱스(use_invisible_indexes)**

- 8.0부터 인덱스를 지우지 않고 옵티마이저가 못 쓰게 할 수 있음

```sql
ALTER TABLE employees ALTER INDEX ix_hiredate INVISIBLE;
ALTER TABLE employees ALTER INDEX ix_hiredate VISIBLE;
SET optimizer_switch='use_invisible_indexes=on';  -- 기본 off. on이면 INVISIBLE도 사용
```

#### **9.3.1.18 스킵 스캔(skip_scan)**

- (A, B, C) 인덱스에서 B, C 조건만 있으면 원래 인덱스를 못 씀. 스킵 스캔은 이 제약을 (제한적으로) 넘는 기법

```sql
ALTER TABLE employees ADD INDEX ix_gender_birthdate (gender, birth_date);
SELECT * FROM employees WHERE birth_date>='1965-02-01';  -- gender 조건이 없음
```

- 8.0은 gender의 모든 값을 가져와 `gender='M' AND ...`처럼 조건이 있는 것처럼 최적화함
- 선행 칼럼의 유니크한 값이 적을 때만 사용 (자세한 건 8.3.4.4절)
- `skip_scan` 스위치나 `SKIP_SCAN(employees ix_gender_birthdate)`, `NO_SKIP_SCAN(employees)` 힌트로 제어

#### **9.3.1.19 해시 조인(hash join)**

- 8.0.18부터 지원. 하지만 해시 조인이 항상 빠른 건 아님
    - 해시 조인: 첫 레코드는 늦지만 마지막 레코드까지는 빠름 → 최고 스루풋(Best Throughput)에 적합
    - 네스티드 루프 조인: 첫 레코드가 훨씬 빠름 → 최고 응답 속도(Best Response-time)에 적합
    - OLTP는 응답 속도, 분석은 스루풋이 중요
- MySQL은 OLTP용 범용 RDBMS라 조인 칼럼에 인덱스가 없거나 대상 테이블 건수가 매우 적을 때 등에만 해시 조인을 씀
    - 네스티드 루프 조인을 못 쓸 때의 차선책(Fallback strategy). 빠르다고 힌트로 강제하는 건 좋지 않음
    - 해시 조인이면 무조건 빠를 줄 알았는데, 응답 속도 기준으로 보면 오히려 불리하다는 게 의외였다.
- 버전별:
    - 8.0.17까지: 해시 조인 없음. 조인 조건이 나쁘면 BNL 사용 (조인 버퍼보다 크면 드라이빙 테이블을 반복 스캔하는 문제)
    - 8.0.18, 8.0.19: 동등 조인은 해시 조인, 안티/세미 조인은 BNL
    - 8.0.20부터: BNL은 안 쓰고 항상 해시 조인. `block_nested_loop` 스위치와 BNL 힌트도 해시 조인 유도용

```sql
EXPLAIN FORMAT=TREE
SELECT *
FROM employees e IGNORE INDEX(PRIMARY, ix_hiredate)
  INNER JOIN dept_emp de IGNORE INDEX(ix_empno_fromdate, ix_fromdate)
    ON de.emp_no=e.emp_no AND de.from_date=e.hire_date \G
-- -> Inner hash join (e.hire_date = de.from_date), (e.emp_no = de.emp_no)
--     -> Table scan on e
--     -> Hash
--         -> Table scan on de
-- 일반 EXPLAIN의 Extra: Using join buffer (hash join)
```

- 빌드 단계(Build-phase): 건수가 적은 테이블로 메모리에 해시 테이블을 만듦. 이 테이블이 빌드 테이블
- 프로브 단계(Probe-phase): 나머지 테이블(프로브 테이블)을 읽으며 해시 테이블에서 일치하는 걸 찾음
- 일반 EXPLAIN으로는 구분이 어렵고, FORMAT=TREE나 EXPLAIN ANALYZE에서 가장 안쪽(들여쓰기가 가장 깊은) 테이블이 빌드 테이블
- 해시 테이블은 조인 버퍼(`join_buffer_size`, 기본 256KB)에 저장됨. 버퍼보다 크면:
    - 1차: 버퍼가 찰 때까지 해시 테이블을 만들고, 나머지 빌드 테이블 레코드는 디스크에 청크로 저장. 프로브 테이블을 읽어 1차 조인하면서 프로브 레코드도 디스크에 청크로 저장
    - 2차: 빌드 청크를 하나씩 읽어 해시 테이블을 다시 만들고, 대응하는 프로브 청크와 조인. 청크 수만큼 반복
    - 두 테이블을 같은 개수의 청크로 나누기 위해 해시 키용과 다른 2차 해시 함수를 씀
- 메모리에서 다 되면 클래식 해시 조인(Classic hash join), 안 되면 그레이스 해시 조인(Grace hash join)을 하이브리드로 사용
- 해시 키는 빠르고 분포도도 좋은 xxHash64로 만듦

#### **9.3.1.20 인덱스 정렬 선호(prefer_ordering_index)**

- 옵티마이저는 ORDER BY/GROUP BY를 인덱스로 처리할 수 있으면 그 인덱스에 가중치를 높게 줌

```sql
SELECT * FROM employees
WHERE hire_date BETWEEN '1985-01-01' AND '1985-02-01'
ORDER BY emp_no;
-- employees | index | PRIMARY | 300252 | Using where
```

- ix_hiredate로 찾아서 정렬하는 게 보통 나은데, PK를 풀 스캔하며 hire_date를 거르는 계획을 고르는 실수를 가끔 함
- 8.0.20까지는 IGNORE INDEX로 막았고, 8.0.21부터 `prefer_ordering_index`(기본 ON)를 OFF로 하면 됨

```sql
SET SESSION optimizer_switch='prefer_ordering_index=OFF';
SELECT /*+ SET_VAR(optimizer_switch='prefer_ordering_index=OFF') */ ...
```

### **9.3.2 조인 최적화 알고리즘**

- 5.0부터 있던 2가지 알고리즘. 조인 테이블이 많아지면 실행 계획 수립에만 몇 분, 심하면 몇 시간이 걸릴 수 있음

#### **9.3.2.1 Exhaustive 검색 알고리즘**

- 5.0 이전 방식. FROM 절 모든 테이블 조합의 비용을 계산해서 최적 1개를 찾음
- 테이블이 20개면 20!(Factorial)개 조합. 10개만 넘어도 몇 분이 걸리고, 1개 늘 때마다 11배씩 늘어남

#### **9.3.2.2 Greedy 검색 알고리즘**

- Exhaustive의 시간 문제를 해결하려고 5.0부터 도입
    1. N개 테이블 중 `optimizer_search_depth` 개수로 가능한 조합을 만들고 최소 비용 계획을 고름
    2. 그 계획의 첫 번째 테이블을 "부분 실행 계획"의 첫 테이블로 확정
    3. 남은 테이블로 다시 조합을 만들어 부분 실행 계획에 대입해 비용 계산, 다음 테이블 확정
    4. 남은 테이블이 없을 때까지 반복하면 부분 실행 계획이 최종 조인 순서가 됨
- `optimizer_search_depth`(0~62, 기본 62): Greedy 검색 대상 테이블 수
    - 0이면 옵티마이저가 자동 결정
    - 조인 테이블이 설정값보다 많으면 설정값만큼은 Exhaustive, 나머지는 Greedy. 적으면 Exhaustive만
    - `optimizer_prune_level`이 0이라면 4~5 정도로 설정하는 게 좋다고 함
- `optimizer_prune_level`: Heuristic 검색 사용 여부 (1: 사용, 기본값)
    - Heuristic 검색: 비용 계산 중 이미 계산한 순서보다 비싸지면 바로 포기하고, 아우터 조인 테이블을 우선순위에서 빼는 등 경험 기반 최적화
    - 테이블이 몇 개 안 돼도 성능 차이가 크니 특별한 이유 없으면 0으로 두지 말 것
- 테스트: 테이블 30개(tab01~tab30, 각 2,000건 정도)를 조인하는 쿼리로 실행 계획 수립 시간 측정
    - prune_level=1: search_depth 1~62 모두 0.01초 이내 (5.1에선 1초 넘게 걸렸음)
    - prune_level=0: depth가 커질수록 급증하고 15부터는 너무 오래 걸려서 측정 불가
- 8.0은 Heuristic을 끌 필요가 거의 없고, 기본값이 1이라 조인 관련 변수는 더 손댈 필요가 없어 보인다고 함

## **9.4 쿼리 힌트**

- 옵티마이저가 성숙했어도 우리 비즈니스를 100% 이해하진 못함. 그래서 실행 계획을 알려줄 수단이 힌트
- 인덱스 힌트(예전부터 쓰던 `USE INDEX` 등)와 옵티마이저 힌트(5.6부터 추가)로 나뉨
    - `STRAIGHT_JOIN`처럼 애매한 것도 책에서는 인덱스 힌트 쪽에서 다룸

### **9.4.1 인덱스 힌트**

- SQL 문법의 일부로 써야 해서 ANSI-SQL 표준을 지키지 못함
    - 옵티마이저 힌트는 다른 RDBMS에선 주석으로 해석되니 표준 준수. 가능하면 옵티마이저 힌트 추천
- SELECT와 UPDATE에서만 사용 가능

#### **9.4.1.1 STRAIGHT_JOIN**

- 옵티마이저 힌트이자 조인 키워드. SELECT/UPDATE/DELETE에서 FROM 절 순서대로 조인 순서를 고정함

```sql
SELECT STRAIGHT_JOIN e.first_name, e.last_name, d.dept_name
FROM employees e, dept_emp de, departments d
WHERE e.emp_no=de.emp_no AND d.dept_no=de.dept_no;
-- 힌트 없으면 departments(9건) → dept_emp → employees 순
-- 힌트 있으면 employees → dept_emp → departments 순
-- /*! STRAIGHT_JOIN */ 형태로 써도 같음. SELECT 바로 뒤에 써야 함
```

- 옵티마이저는 보통 조인 칼럼 인덱스 여부로 순서를 정하고, 문제없으면 (WHERE 조건을 만족하는) 레코드가 적은 테이블을 드라이빙으로 고름
- 다음 기준대로 안 될 때만 STRAIGHT_JOIN으로 조정:
    - 임시 테이블(인라인 뷰, 파생 테이블)과 일반 테이블: 거의 항상 임시 테이블을 드라이빙으로
    - 임시 테이블끼리: 인덱스가 없으니 작은 쪽을 드라이빙으로
    - 일반 테이블끼리: 양쪽 다 조인 칼럼 인덱스가 있거나 없으면 건수가 적은 쪽, 그 외엔 인덱스가 없는 쪽을 드라이빙으로
    - 여기서 건수는 테이블 전체가 아니라 인덱스를 쓸 수 있는 WHERE 조건을 만족하는 건수
- 비슷한 옵티마이저 힌트: `JOIN_FIXED_ORDER`(STRAIGHT_JOIN과 같음), `JOIN_ORDER`, `JOIN_PREFIX`, `JOIN_SUFFIX`(일부 테이블 순서만 제안)

#### **9.4.1.2 USE INDEX / FORCE INDEX / IGNORE INDEX**

- 인덱스를 가진 테이블 뒤에 씀. 비슷한 칼럼 3~4개짜리 인덱스가 여러 개면 옵티마이저가 가끔 실수함
- 인덱스 이름을 괄호로 묶어 쓰고, 이름 없는 PK는 `PRIMARY`. 비었거나 없는 이름이면 문법 오류
    - `USE INDEX`: 특정 인덱스 사용을 권장. 대부분 채택되지만 항상은 아님
    - `FORCE INDEX`: 더 강한 힌트지만, 저자 경험상 USE INDEX로 안 쓰던 인덱스는 FORCE INDEX로도 안 썼음
    - `IGNORE INDEX`: 특정 인덱스를 못 쓰게 함. 풀 테이블 스캔 유도용으로도 씀
- 용도 지정(선택): `FOR JOIN`(검색까지 포함. MySQL은 테이블 하나 읽는 것도 JOIN이라 부름), `FOR ORDER BY`, `FOR GROUP BY`. 보통 옵티마이저가 잘 고르니 신경 안 써도 됨
- `emp_no=10001` 조회에 `IGNORE INDEX(PRIMARY)`를 주면 5.5에선 실제로 풀 스캔하기도 했고, 무관한 `FORCE INDEX(ix_firstname)`를 주면 PK를 버리고 풀 스캔함
- 전문 검색 인덱스가 있으면 B-Tree를 쓸 수 있어도 전문 검색 인덱스를 고르는 경우가 많음 (PK나 전문 검색 인덱스에 가중치를 둠)
- 저자 의견: 최적 계획은 데이터에 따라 계속 바뀌니 가능하면 옵티마이저에게 맡기는 게 좋음
    - 최고의 최적화는 쿼리를 없애거나 데이터를 최소화하는 것, 그다음은 모델 단순화, 마지막이 힌트
    - 다만 실무에선 앞의 작업이 어려워서 힌트에 의존하는 경우가 많다고 함

#### **9.4.1.3 SQL_CALC_FOUND_ROWS**

- 보통 LIMIT 건수를 채우면 검색을 멈추지만, 이 힌트가 있으면 끝까지 검색하고 `FOUND_ROWS()`로 전체 건수를 알려줌

```sql
-- 방법 1: SQL_CALC_FOUND_ROWS
SELECT SQL_CALC_FOUND_ROWS * FROM employees WHERE first_name='Georgi' LIMIT 0, 20;
SELECT FOUND_ROWS() AS total_record_count;

-- 방법 2: 쿼리 분리
SELECT COUNT(*) FROM employees WHERE first_name='Georgi';
SELECT * FROM employees WHERE first_name='Georgi' LIMIT 0, 20;
```

- 방법 1: 어차피 쿼리 2번. 253건을 전부 읽어야 해서 랜덤 I/O가 253번
- 방법 2: COUNT는 커버링 인덱스라 랜덤 I/O가 없고, 조회는 LIMIT 때문에 랜덤 I/O 20번
- 방법 1이 비교도 안 되게 느림. UNION 쿼리에선 정확한 건수도 못 가져옴
- 성능이 아니라 개발 편의용 힌트. 쿼리/인덱스가 튜닝 안 된 상황에서만 더 빠를 수 있는데, 그럴 땐 튜닝하는 게 맞음
    - 페이징 만들 때 편해 보여서 손이 가는 힌트인데, COUNT 쿼리를 따로 날리는 게 정답이다.

### **9.4.2 옵티마이저 힌트**

#### **9.4.2.1 옵티마이저 힌트 종류**

- 영향 범위별 4그룹: 인덱스, 테이블, 쿼리 블록(힌트가 쓰인 블록에만 영향), 글로벌(쿼리 전체)
    - 구분에 따라 쓰는 위치가 달라지진 않음. 테이블과 인덱스 이름을 다 쓸 수도, 테이블만 쓸 수도 있는 힌트는 양쪽 수준 다 해당

| **영향 범위** | **힌트** |
| --- | --- |
| 글로벌 | `MAX_EXECUTION_TIME`(실행 시간 제한), `RESOURCE_GROUP`(리소스 그룹), `SET_VAR`(시스템 변수) |
| 쿼리 블록 | `SUBQUERY`, `SEMIJOIN`/`NO_SEMIJOIN`, `JOIN_FIXED_ORDER`, `JOIN_ORDER`, `JOIN_PREFIX`, `JOIN_SUFFIX`, `QB_NAME` |
| 쿼리 블록, 테이블 | `BKA`/`NO_BKA`, `BNL`/`NO_BNL`, `HASH_JOIN`/`NO_HASH_JOIN`(8.0.18에서만), `DERIVED_CONDITION_PUSHDOWN`/`NO_DERIVED_CONDITION_PUSHDOWN` |
| 테이블 | `MERGE`/`NO_MERGE`(FROM 절 서브쿼리나 뷰를 외부 쿼리로 병합) |
| 테이블, 인덱스 | `INDEX_MERGE`/`NO_INDEX_MERGE`, `MRR`/`NO_MRR`, `NO_ICP`, `NO_RANGE_OPTIMIZATION`, `SKIP_SCAN`/`NO_SKIP_SCAN` |
| 인덱스 | `INDEX`/`NO_INDEX`, `GROUP_INDEX`/`NO_GROUP_INDEX`, `JOIN_INDEX`/`NO_JOIN_INDEX`, `ORDER_INDEX`/`NO_ORDER_INDEX` |
- 인덱스 수준 힌트는 반드시 테이블명이 먼저: `/*+ INDEX(employees ix_firstname) */`
- 힌트 문법이 틀리면 경고가 1개 더 나옴 (EXPLAIN은 원래 재작성 쿼리용 경고 1개). 익숙하지 않은 힌트는 EXPLAIN으로 확인

```sql
EXPLAIN SELECT /*+ NO_INDEX(ix_firstname) */ * FROM employees WHERE first_name='Matt';
-- 1 row in set, 2 warnings
SHOW WARNINGS;
-- Warning | 3128 | Unresolved name 'ix_firstname'@'select#1' for NO_INDEX hint
```

- 쿼리 블록: SELECT 키워드로 시작하는 (서브)쿼리 영역. 외부 블록에서 지정하려면 `QB_NAME()`으로 이름을 붙임

```sql
SELECT /*+ JOIN_ORDER(e, s@subq1) */ COUNT(*)
FROM employees e
WHERE e.first_name='Matt'
  AND e.emp_no IN (SELECT /*+ QB_NAME(subq1) */ s.emp_no
                   FROM salaries s
                   WHERE s.salary BETWEEN 50000 AND 50500);
-- e | ix_firstname | Using index
-- s | PRIMARY      | Using where; FirstMatch(e)
```

- 서브쿼리가 세미 조인으로 풀릴 걸 예상하고 employees → salaries 순으로 조인하게 한 것

#### **9.4.2.2 MAX_EXECUTION_TIME**

- 유일하게 실행 계획에 영향을 주지 않는 힌트. 최대 실행 시간(밀리초)을 넘기면 실패

```sql
SELECT /*+ MAX_EXECUTION_TIME(100) */ * FROM employees ORDER BY last_name LIMIT 1;
-- ERROR 3024 (HY000): Query execution was interrupted, maximum statement execution time exceeded
```

#### **9.4.2.3 SET_VAR**

- 시스템 변수도 실행 계획에 영향을 줌 (예: 조인 버퍼가 충분하면 조인 버퍼를 쓰는 계획을 고를 수 있음)
- `optimizer_switch` 조정뿐 아니라 조인 버퍼나 소트 버퍼를 일시적으로 키워 대용량 쿼리 성능을 높일 때도 유용
- 단, 모든 시스템 변수를 조정할 수 있는 건 아님

#### **9.4.2.4 SEMIJOIN & NO_SEMIJOIN**

- `SEMIJOIN(DUPSWEEDOUT)`, `SEMIJOIN(FIRSTMATCH)`, `SEMIJOIN(LOOSESCAN)`, `SEMIJOIN(MATERIALIZATION)`
- Table Pull-out은 항상 유리해서 힌트가 없음. 나머지는 상황에 따라 우회하는 게 나을 수 있어서 NO_SEMIJOIN도 있음
- 세미 조인 힌트는 외부 쿼리가 아니라 서브쿼리에 씀 (또는 QB_NAME으로 이름을 붙이고 외부에서)

```sql
SELECT * FROM departments d
WHERE d.dept_no IN
  (SELECT /*+ SEMIJOIN(MATERIALIZATION) */ de.dept_no FROM dept_emp de);
-- 힌트 없으면 FirstMatch(d), 힌트 있으면 <subquery2> + MATERIALIZED

SELECT /*+ SEMIJOIN(@subq1 MATERIALIZATION) */ * FROM departments d
WHERE d.dept_no IN
  (SELECT /*+ QB_NAME(subq1) */ de.dept_no FROM dept_emp de);

SELECT * FROM departments d
WHERE d.dept_no IN
  (SELECT /*+ NO_SEMIJOIN(DUPSWEEDOUT, FIRSTMATCH) */ de.dept_no FROM dept_emp de);
```

#### **9.4.2.5 SUBQUERY**

- 세미 조인 최적화를 못 쓸 때의 서브쿼리 최적화: `SUBQUERY(INTOEXISTS)`, `SUBQUERY(MATERIALIZATION)`
- 세미 조인 최적화는 안티 세미 조인에 못 쓰므로 주로 안티 세미 조인에 쓰임. 쓸 일이 많지 않아 예시는 생략

#### **9.4.2.6 BNL & NO_BNL & HASHJOIN & NO_HASHJOIN**

- 8.0.20부터 BNL은 안 쓰이지만 BNL/NO_BNL 힌트는 해시 조인 유도/방지용으로 계속 쓸 수 있음
- HASHJOIN/NO_HASHJOIN은 8.0.18에서만 유효

```sql
SELECT /*+ BNL(e, de) */ *
FROM employees e
  INNER JOIN dept_emp de ON de.emp_no=e.emp_no;
```

- 조인 칼럼에 인덱스가 적절하면 힌트를 줘도 해시 조인은 거의 안 쓰임. 쓰게 하려면 양쪽 emp_no 인덱스를 제거하거나 못 쓰게 해야 함

#### **9.4.2.7 JOIN_FIXED_ORDER & JOIN_ORDER & JOIN_PREFIX & JOIN_SUFFIX**

- STRAIGHT_JOIN은 FROM 절 순서를 직접 맞춰야 하고, 일부만 고정할 수 없다는 단점이 있었음
    - `JOIN_FIXED_ORDER`: FROM 절 순서대로 (STRAIGHT_JOIN과 동일)
    - `JOIN_ORDER`: 힌트에 명시한 순서대로
    - `JOIN_PREFIX`: 드라이빙 테이블만 강제
    - `JOIN_SUFFIX`: 드리븐 테이블(마지막에 조인될 테이블들)만 강제

```sql
SELECT /*+ JOIN_ORDER(d, de) */ *
FROM employees e
  INNER JOIN dept_emp de ON de.emp_no=e.emp_no
  INNER JOIN departments d ON d.dept_no=de.dept_no;
-- JOIN_FIXED_ORDER(), JOIN_PREFIX(e, de), JOIN_SUFFIX(de, e)도 같은 자리에 씀
```

#### **9.4.2.8 MERGE & NO_MERGE**

- FROM 절 서브쿼리를 외부 쿼리와 병합할지, 파생 테이블(임시 테이블)로 만들지 제어

```sql
SELECT /*+ MERGE(sub) */ *
FROM (SELECT * FROM employees WHERE first_name='Matt') sub LIMIT 10;
-- MERGE   : 1 | SIMPLE | employees | ref | ix_firstname
-- NO_MERGE: 1 | PRIMARY | <derived2> | ALL / 2 | DERIVED | employees | ref
```

#### **9.4.2.9 INDEX_MERGE & NO_INDEX_MERGE**

- 인덱스 머지가 항상 좋은 건 아니라서 제어용

```sql
SELECT /*+ NO_INDEX_MERGE(employees PRIMARY) */ *
FROM employees
WHERE first_name='Georgi' AND emp_no BETWEEN 10000 AND 20000;
-- 힌트 없음      : index_merge | Using intersect(ix_firstname,PRIMARY)
-- NO_INDEX_MERGE : range | ix_firstname | Using index condition
-- INDEX_MERGE(employees ix_firstname, PRIMARY) : index_merge
```

#### **9.4.2.10 NO_ICP**

- ICP는 항상 도움이 되니 ICP 힌트는 없고 NO_ICP만 있음
- ICP 때문에 비용 예측이 틀어질 수 있음
    - 예: A 인덱스가 ICP 덕에 싸게 예측돼 선택됐지만 실제로는 B가 나은 경우. 데이터 분포가 고르지 않아 범위에 따라 다를 수 있음
    - A를 아예 막기보다 ICP만 꺼서 옵티마이저가 더 유연하게 고르게 할 수 있음

```sql
SELECT /*+ NO_ICP(employees ix_lastname_firstname) */ *
FROM employees
WHERE last_name='Acton' AND first_name LIKE '%sal';
-- Using index condition → Using where
```

#### **9.4.2.11 SKIP_SCAN & NO_SKIP_SCAN**

- 선행 칼럼의 유니크한 값이 많으면 스킵 스캔이 오히려 느림. 옵티마이저가 잘못 고르면 NO_SKIP_SCAN으로 막음

```sql
SELECT /*+ NO_SKIP_SCAN(employees ix_gender_birthdate) */ gender, birth_date
FROM employees
WHERE birth_date>='1965-02-01';
-- 힌트 없음: range | Using where; Using index for skip scan
-- 힌트 있음: index | Using where; Using index
```

#### **9.4.2.12 INDEX & NO_INDEX**

- 예전 인덱스 힌트를 대체하는 옵티마이저 힌트

| **인덱스 힌트** | **옵티마이저 힌트** |
| --- | --- |
| `USE INDEX` | `INDEX` |
| `USE INDEX FOR GROUP BY` | `GROUP_INDEX` |
| `USE INDEX FOR ORDER BY` | `ORDER_INDEX` |
| `IGNORE INDEX` | `NO_INDEX` |
| `IGNORE INDEX FOR GROUP BY` | `NO_GROUP_INDEX` |
| `IGNORE INDEX FOR ORDER BY` | `NO_ORDER_INDEX` |
- 인덱스 힌트는 테이블 뒤에 인덱스 이름만, 옵티마이저 힌트는 테이블명과 인덱스 이름을 같이 씀

```sql
SELECT * FROM employees USE INDEX(ix_firstname) WHERE first_name='Matt';
SELECT /*+ INDEX(employees ix_firstname) */ * FROM employees WHERE first_name='Matt';
```
