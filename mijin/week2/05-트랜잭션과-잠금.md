# 5장 트랜잭션과 잠금

> 스터디 정리 | 팀원 공유 자료를 바탕으로 설명 흐름과 예시를 재구성

## 1. 트랜잭션과 잠금은 무엇이 다를까?

- **트랜잭션(Transaction)**: 여러 변경 작업을 하나의 논리적 단위로 묶어, 모두 반영하거나 모두 취소하도록 보장한다.
- **잠금(Lock)**: 여러 세션이 같은 데이터에 동시에 접근할 때 충돌을 제어한다.
- **격리 수준(Isolation Level)**: 동시에 실행되는 트랜잭션이 서로의 변경 사항을 어느 정도 관찰할 수 있는지 결정한다.

세 기능은 함께 사용되지만 목적이 다르다. 트랜잭션이 작업의 **정합성**을 다룬다면, 잠금은 **동시 접근**, 격리 수준은 **변경 내용의 가시성**을 다룬다.

### 1.1 스토리지 엔진에 따른 차이

같은 `INSERT`라도 스토리지 엔진에 따라 실패 시 결과가 달라진다.

```sql
-- id=3이 이미 존재한다고 가정
INSERT INTO example (id) VALUES (1), (2), (3);
```

| 엔진 | 중복 키 오류 발생 시 |
| --- | --- |
| MyISAM / MEMORY | 앞서 삽입된 1, 2가 남을 수 있음 |
| InnoDB | 해당 INSERT 문 전체가 취소됨 |

즉, **InnoDB는 트랜잭션을 지원하지만 MyISAM은 지원하지 않는다.** 다만 한 SQL 문장의 원자성과 여러 SQL 문장을 묶은 트랜잭션은 구분해서 이해해야 한다.

### 1.2 트랜잭션은 짧게 유지하기

트랜잭션을 오래 유지하면 잠금 점유 시간과 대기 시간이 길어질 수 있다. DB 변경과 직접 관련 없는 작업은 가능하면 트랜잭션 밖에서 수행한다.

```text
[외부 API 호출] → [데이터 검증] → BEGIN → [DB 변경] → COMMIT
```

특히 네트워크 호출을 트랜잭션 내부에 넣으면 응답 지연이 DB 잠금 대기로 이어질 수 있다는 점을 주의한다.

## 2. MySQL의 잠금: 어느 범위까지 막을까?

MySQL의 잠금은 **MySQL 엔진 레벨**과 **스토리지 엔진 레벨**로 구분된다. 전자는 스토리지 엔진 전반에 영향을 줄 수 있고, 후자는 해당 엔진 내부에서 동작한다.

| 잠금 | 범위 / 대상 | 주로 쓰이는 상황 |
| --- | --- | --- |
| 글로벌 락 | MySQL 서버 전체 | 서버 전체의 일관된 백업 |
| 테이블 락 | 특정 테이블 | 테이블 단위 작업 제어 |
| 네임드 락 | 사용자가 지정한 문자열 | 애플리케이션 간 작업 동기화 |
| 메타데이터 락 | 테이블·뷰 등 객체의 정의 | 테이블 이름이나 구조 변경 보호 |

### 글로벌 락과 백업 락

글로벌 락은 영향 범위가 크므로 운영 환경에서 주의가 필요하다. MySQL 8.0에서는 백업 도구가 보다 안전하게 동작하도록 **백업 락**도 제공한다.

### 네임드 락과 메타데이터 락

```sql
SELECT GET_LOCK('batch:daily-settlement', 10);
-- 작업 수행
SELECT RELEASE_LOCK('batch:daily-settlement');
```

네임드 락은 특정 테이블의 레코드를 잠그는 것이 아니라 **이름을 기준으로 협력하는 세션 사이의 동기화 수단**이다. 반면 메타데이터 락은 `RENAME TABLE` 등 객체 구조 관련 작업에서 자동으로 획득된다.

## 3. InnoDB 잠금의 핵심은 인덱스

InnoDB는 레코드 기반 잠금을 제공하지만, 실제로는 **인덱스 레코드**를 대상으로 잠금을 관리한다. 따라서 어떤 인덱스를 통해 데이터를 찾는지가 잠금 범위에 큰 영향을 미친다.

### 3.1 레코드 락·갭 락·넥스트 키 락

| 유형 | 잠그는 대상 | 목적 |
| --- | --- | --- |
| 레코드 락(Record Lock) | 인덱스 레코드 | 기존 레코드의 동시 변경 제어 |
| 갭 락(Gap Lock) | 인접 인덱스 레코드 사이의 간격 | 그 구간에 새 레코드가 삽입되는 것 제어 |
| 넥스트 키 락(Next-Key Lock) | 레코드 락 + 갭 락 | 레코드 및 주변 삽입 범위 제어 |

예를 들어 인덱스 값이 `10, 20, 30`이라면, 갭 락은 `10`과 `20` 사이처럼 **값이 아직 존재하지 않는 범위**의 삽입을 제한하는 데 사용된다.

유니크 인덱스로 기존 레코드 하나를 정확히 찾는 경우에는 일반적으로 갭을 제외한 레코드 락을 사용한다. 다만 실제 잠금은 쿼리 조건, 인덱스, 격리 수준에 따라 달라진다.

### 3.2 UPDATE 한 건인데 왜 여러 건이 잠길까?

`first_name`에만 인덱스가 있고, `last_name`에는 인덱스가 없다고 가정한다.

```sql
UPDATE employees
SET hire_date = NOW()
WHERE first_name = 'Georgi'
  AND last_name = 'Klassen';
```

실제 수정 대상은 한 건이어도 `first_name='Georgi'`에 해당하는 **253건의 인덱스 레코드를 탐색하고 잠글 수 있다.** 적절한 인덱스가 없으면 훨씬 넓은 범위에 잠금이 발생할 수 있다.

**핵심:** 인덱스는 조회 성능뿐 아니라 동시성 및 잠금 경합에도 영향을 준다.

### 3.3 AUTO_INCREMENT 락

자동 증가 값을 중복 없이 할당하기 위한 제어 방식이다. `innodb_autoinc_lock_mode` 설정에 따라 동시 INSERT 시 동작이 달라진다.

| 모드 | 특징 |
| --- | --- |
| 0 | 전통적인 테이블 수준 AUTO-INC 락 방식 |
| 1 | INSERT 유형에 따라 가벼운 할당 방식과 테이블 락을 혼용 |
| 2 | INSERT 간 자동 증가 값 할당의 동시성을 높이는 방식 |

## 4. 격리 수준: 다른 트랜잭션의 변경을 언제 볼까?

격리 수준이 낮으면 동시 처리에 유리할 수 있지만, 같은 데이터를 읽어도 시점에 따라 결과가 달라지는 현상을 더 많이 허용한다.

| 격리 수준 | 핵심 특징 | 주의할 현상 |
| --- | --- | --- |
| READ UNCOMMITTED | 커밋 전 변경도 읽을 수 있음 | Dirty Read |
| READ COMMITTED | 커밋된 변경만 읽음 | Non-Repeatable Read |
| REPEATABLE READ | 동일 트랜잭션의 일반적인 일관된 읽기 결과 유지 | 잠금 읽기 등과 구분 필요 |
| SERIALIZABLE | 가장 엄격한 격리 | 동시 처리 성능 저하 |

### 4.1 세 가지 읽기 이상 현상

- **Dirty Read**: 다른 트랜잭션이 아직 커밋하지 않은 데이터를 읽는다. 이후 롤백되면 존재하지 않는 값을 읽은 셈이 된다.
- **Non-Repeatable Read**: 같은 트랜잭션에서 같은 행을 다시 읽었는데 값이 달라진다.
- **Phantom Read**: 같은 조건으로 다시 조회했을 때 조건에 맞는 행의 집합이 달라진다.

### 4.2 InnoDB의 기본값: REPEATABLE READ

InnoDB는 변경 이전 데이터를 **언두(Undo) 영역**에 보관하고, MVCC를 통해 트랜잭션에 맞는 버전의 데이터를 보여준다. 이 덕분에 일반적인 일관된 읽기에서는 같은 트랜잭션 안에서 일관된 결과를 얻을 수 있다.

```text
트랜잭션 A: SELECT → (다른 트랜잭션 B가 UPDATE 후 COMMIT) → SELECT

READ COMMITTED  : 두 번째 SELECT에서 새 값이 보일 수 있음
REPEATABLE READ : 일반적인 일관된 읽기에서는 기존 스냅샷을 유지
```

단, **일반 SELECT의 일관된 읽기와 `SELECT ... FOR UPDATE` 같은 잠금 읽기는 동작이 다르다.** REPEATABLE READ라고 해서 모든 조회가 무조건 동일한 결과를 반환하는 것은 아니다.

## 5. 핵심 정리

1. **트랜잭션은 원자성, 잠금은 동시성 제어, 격리 수준은 변경 내용의 가시성**을 다룬다.
2. **InnoDB는 인덱스 레코드를 잠근다.** 쿼리가 실제 수정하는 행보다 더 넓은 범위를 잠글 수 있다.
3. **갭 락과 넥스트 키 락**은 기존 행뿐 아니라 특정 범위로의 신규 삽입도 제어한다.
4. **REPEATABLE READ는 MVCC와 언두 데이터를 활용**해 일관된 읽기를 지원한다.
5. 운영 관점에서는 **트랜잭션을 짧게 유지하고, 조건에 맞는 인덱스를 설계하는 것**이 중요하다.

- 외부 결제 승인 API를 DB 트랜잭션 내부에서 호출하면 어떤 문제가 생길까?
